### airuleset internals — Discord notify

- **Caveman plugin wiring + statusline** (`maybe_setup_caveman` in `airuleset.py`) — caveman (`JuliusBrussee/caveman`, third-party CC plugin for compressed output) is kept correctly wired on BOTH machines by `install` (so every `push` self-heals it). The managed shim ALSO renders the **Issues segment** (`statusbar.py`, renders `I N` — text label per user, no emoji). #367 (2026-08-11, THIRD footer simplification round) collapsed it to exactly ONE live, decreasing number, dropping four things that used to render alongside `I N`/`Issues N`: the active-run ratio (`run N/T`, fed by `notify --run-card` → `~/.claude/autopilot-progress/<repo>.json`, 6h run window — `autopilot-progress` still exists, still written for watchdog job 20's own goal-evidence read, the FOOTER just no longer reads it), the `core` suffix, the needs-gatekeeper repo-wide badge (spoken `gk-req`, #30/#181 — superseded because `_obligation_quals()` already folds every open `needs-gatekeeper`/`ready-for-review` ticket into the SAME obligation count `I N` renders, so the badge was pure duplicate decoration), and the excluded-from-core badge (#164). This followed the SAME churn #307/#313 already document (see their own bullets in `modules/core/statusline-vocabulary.md`) — too many numbers about the same underlying question. `I N` is now the LIVE OBLIGATION count — **scoped per stream, never automatically the whole repo on EITHER path**: a reduced-authority box (`resolve_authority` != full: david/montalu/marek/simap) counts only ITS OWN slice via `_slice_quals()` (own-account streams: `assignee:@me` ∪ `author:@me` ∪ `label:stream:<user>`; a SHARED-gh-account box — montalu/marek/simap authenticate as the maintainer — uses the stream LABEL alone, since `@me` there resolves to the maintainer and matches nothing assigned; gh error → `open=None`, never a wrong number) — reused verbatim by the `/goal` stop-proof via `airuleset.py slice-quals` (#181: those templates used to hardcode `--assignee @me`, which silently prints `0` on a shared-account box with real work open — the false-stop montalu hit); a full-authority box counts `_obligation_quals()` — the CORE partition (`_core_search_excl()`, MINUS every sub-dev stream's `stream:<user>`-labeled tickets) UNIONED with every open `needs-gatekeeper`/`ready-for-review` ticket regardless of which stream owns it, since only this box can act on those (#181 round 3's own display-partition-vs-obligation-partition lesson: the OLD footer counted only the narrower `_core_search_excl()` set, which is how the footer could read `I 0` while the `/goal` loop it was meant to mirror kept running). Both paths now go through the SAME `_union_open_issues()` helper `airuleset.py core-quals --count`/`slice-quals --count` (the `/goal` stop-proofs) already use — one shared derivation feeding the footer AND the loop, never a parallel one that could drift apart again (the #367 consistency guard, the same shape #181's `slice-quals` fix already established for the reduced-authority side). The render NEVER calls gh inline — it reads `~/.claude/tickets-status/<cwd-key>.json` and spawns a DETACHED `airuleset.py tickets-status --refresh --cwd <dir>` when stale (TTL 120s, spawn-guard 30s). `{{REPO_DIR}}` in the shim is substituted by `render_caveman_shim()` at install — never write the raw constant. airuleset does NOT own caveman's code, only its wiring: it kept half-installing / breaking because the plugin's real statusline script lives under a content-hashed cache dir (`plugins/cache/caveman/caveman/<hash>/…`) that **changes on every `claude plugin update`**, so any hard-coded hash in `settings.json` rots and the statusline silently dies. Fix: airuleset ships a **stable shim** at `~/.claude/airuleset-caveman-statusline.sh` that resolves the current hash at RUNTIME, points `settings.json` statusLine → the shim, ensures `enabledPlugins.caveman@caveman=true` + the marketplace, installs the plugin if its cache is missing, and seeds `.caveman-active` (preserving a valid `/caveman` mode pick, else `lite`). Pure reconcile logic is unit-tested (`tests/test_caveman.py`).

- **Discord notify** (`notify/` package + `hooks/notify-discord*.sh`) — the single device-ping path (mobile-app model: ❓ ask / ✅ done / api-error / autopilot card). **Per-owner thread routing:** each tmux owner (zbynek / marek) is posted to THEIR OWN thread (`claude-zbynek` / `claude-marek`) so two people's pings don't mix — an @mention alone was not enough. `notify.notification_channel(env, owner)` resolves `DISCORD_NOTIFICATION_CHANNEL_<OWNER>` → shared `DISCORD_NOTIFICATION_CHANNEL_ID` fallback → "". A Discord thread IS a channel in the API, so the per-owner id is just a different POST target. Both send paths are owner-aware: the shell `notify-discord-send.sh` (❓/✅) resolves the owner ONCE via `airuleset.py notify --owner` and forces it onto `--mention-prefix` + `--channel-id` (so they can never disagree); the Python `notify.send()` (api-error + run-card) resolves once internally. **Parallel mirror recipients (`DISCORD_MIRROR_<OWNER>`):** a notification for one owner can ALSO fan out to other owners' threads, each with THEIR OWN @mention — so an automated session-persona (e.g. `david` on dev2 running codex-bridge) gets its OWN `claude-david` thread AND the real human `zbynek` is pinged in parallel (`DISCORD_MIRROR_DAVID=zbynek`). Both send paths honour it: `notify.mirror_owners(env, owner)` returns the extra owners; `notify.send()` and the shell loop post one message per target (primary first), skipping a mirror whose thread equals the primary's (no double-post). A normal single-owner box (zbynek / marek — no mirror configured) fans out to exactly one target = unchanged. **Questions get a SEPARATE thread (`DISCORD_NOTIFICATION_CHANNEL_<OWNER>_Q`, #296):** `notification_channel(env, owner, kind="questions")` tries the `_Q` key FIRST, then falls through to the SAME `kind="default"` cascade — `hooks/notify-discord-send.sh` sets `KIND="questions"` only when `ND_EMOJI="❓"`, threaded onto the existing `--channel-id` call for every target (primary + mirrors) via `--kind`; `✅`/card/api-error never pass `kind=` and stay on the owner's normal thread. `notify.provision_question_thread()` (CLI: `notify --provision-question-thread`) creates the thread if missing (as a sibling of the owner's normal thread, same Discord parent channel) — but FIRST searches for an already-existing `claude-<owner>-q` thread (`find_owner_question_thread`, active then archived) before creating one, since the `_Q` id is box-local `.env` config and a second box provisioning the same owner must reuse the first box's thread, never fork a duplicate. Job 7 (`deliver_discord_replies`) needs no `-q` awareness at all — it already fetches from whatever channel a question's own map entry records. Env keys (`DISCORD_BOT_TOKEN`, `DISCORD_MENTION_<OWNER>`, `DISCORD_NOTIFICATION_CHANNEL_*`, `DISCORD_MIRROR_<OWNER>`) live in the LOCAL `~/.claude/channels/discord/.env` (NOT git). Governs via `modules/core/milestone-notifications.md`.

- **Adding a `--flag` early-return to a `cmd_*` dispatcher that has `m.Mock(...)`-based tests:** `m.Mock` auto-creates EVERY attribute as a truthy Mock, so `getattr(args, "flag", False)` is truthy and the new branch hijacks unrelated tests. Pin the new flag `=False` in every `m.Mock(...)` args builder for that command (e.g. the run_card builders for `cmd_notify`).
- **A cross-skill "load the OTHER skill for this lane" pointer is not itself an enforceable instruction — verify with a grep-based acceptance test on the REFERRING skill's own body, never trust the pointer alone.** #47: `autopilot-master` told its own reader to "Load `process-subdev` for LANE 1 / load `autopilot` Step 3 for LANE 3", but neither gatekeeper skill mentioned `run-card` anywhere in ITS OWN text, and LANE 1 (the review pipeline) never dispatches an `autopilot-worker` subagent at all — the one place the instruction actually lived (`agents/autopilot-worker.md`) was structurally unreachable for that lane. Fix pattern: put the instruction directly in the skill body at the point the lane completes (redundant with the pointer, not instead of it), and lock it with a test that anchors past the SPECIFIC lane's own bullet text (`t.index("LANE 1 REVIEW", after_step3_marker)`) — a bare `assertIn` without anchoring past the earlier `/goal` template string (which repeats every lane name too) finds the WRONG occurrence and passes for the wrong reason.
- **A suppression that defers to an UNENFORCED action is a silence generator — gate it on the artifact the action leaves behind, never on the intent to act.** #134: `notify-discord-pending.sh` dropped the idle `✅` whenever a `/goal` was armed, on the premise that the per-ticket run-card covered that ticket. Nothing enforced the card. When workers drifted out of firing it, the guard removed the only remaining signal and the user went five days with ~85 merged PRs, ~103 closed issues and ZERO reports on his phone — noticed only because token spend was 5× higher and results appeared to have stopped. Two properties made it total rather than occasional: an armed `/goal` is close to a permanent state on a loop box (18h+ across 7 re-arms with zero `Goal cleared:`), and the deferred-to action left no trace when skipped. Whenever a guard's justification is "X already covers this", the guard must READ X's artifact. And the artifact has to be the right one: a dedup marker's mere PRESENCE proves a CLAIM, not a delivery — `_dedup_claim` writes it BEFORE the POST, so `notify.marker_delivered` (status recorded after the POST) is the only honest read.
- **The repo NAME for a marker/key comes from `git remote get-url origin`, NEVER the directory basename.** marek's checkout is `~/devel/forestshop/parovanie_produktov` (underscore) while every card marker is keyed `parovanie-produktov` (hyphen), because `_notify_run_card` keys on its `--repo` argument. A directory-derived key matches nothing, which in a "did this get reported?" check reads as "nothing was ever reported" — a silent 100% false-positive rate that looks like a real finding. `notify.repo_name_for` is the single source of truth.
- **Registering a NEW sub-dev stream user (#143, the simap onboarding) touches THREE registries, only ONE of which is generic.** `REMOTE_HOSTS` (deploy target) and `AUTHORITY_BY_USER` (merge rights) must both name the user explicitly — but everything downstream of `AUTHORITY_BY_USER` (`skill_names_for_user`, `statusbar.py`'s `tickets_segment`/`cmd_tickets_status`, the core-slice exclusion at `airuleset.py:2164`) is ALREADY fully generic over that map's keys, so a new entry there wires the statusline and skill scoping automatically — verify with a plain `grep` that no OTHER file hardcodes the existing three names (david/marek/montalu) before assuming a fourth surface needs a matching edit. The THIRD registry is easy to miss because it lives in a hook, not in `airuleset.py`: `hooks/block-subdev-ssh-misuse.sh`'s own docstring promises its ALLOW-list "mirrors airuleset.py's REMOTE_HOSTS exactly" — a REMOTE_HOSTS entry with an `identity` requirement (every subdev user except montalu) that isn't mirrored there leaves a correctly-keyed future ssh from that user wrongly BLOCKED, which is a self-inflicted false positive, not a security gap (the hook fails toward blocking, never toward silently allowing). Checklist for the next stream: `REMOTE_HOSTS` entry (same host+identity shape as its closest sibling), `AUTHORITY_BY_USER[user]` (usually the lowest existing profile — a NEW profile is needed only when no existing one expresses the intended scope), the ssh-hook allow-list entry (`check_target` + the two `echo` help lines), and matching RED tests in `TestRemoteHosts`/`TestBlockSubdevSshMisuseHook`/`TestAuthorityResolution` (`tests/test_airuleset.py`, `tests/test_authority_profiles.py`) — obtained via `git stash push -- <the two impl files>` before writing the tests (the established #77 technique for extending, not creating, a hook/module) so the failures are genuinely observed, not merely presumed. **A FOURTH registry, easy to miss because the #143 ticket never named it: `notify.STREAM_NOTIFY_OWNER[user]` (Discord routing) — see #300's own bullet below for the DISCORD_MIRROR-vs-redirect choice and its verification gaps.** **A FIFTH, provisioning-time-only step (#308, the miva1 incident): BEFORE the new account's first `push`, kill any tmux session already named after it on the subdev box.** `ensure_stream_tmux_session` deliberately never touches an already-existing session (the standing "never resurrect a session the user deliberately killed" rule), and the ssh auto-attach's `tmux new-session -A` silently ignores `-c` on attach — so a session created by manual account provisioning BEFORE registration (even one created by accident, with the wrong cwd) wins every future login forever, with neither mechanism able to correct it. This is a deliberate, human-initiated, provisioning-time action (`no-destructive-remote-actions.md`'s carve-out for the work itself), never an automatic mutation — `ensure_stream_tmux_session` itself only ever REPORTS a cwd mismatch on an existing session (a loud WARNING line), it never kills or re-cwds one.
- **A ticket resolved by CLOSING it with re-verified evidence (no code change) still gets its Discord completion card** — `airuleset.py notify --run-card --repo <owner/name> --issue <N> --goal "..." --achieved "..."` with no `--version`/`--merge-sha` (nothing merged or deployed) sends fine and reports `sent`/rc=0; this is the right shape whenever a ticket's answer turns out to be "already true, verified, closing" rather than "implemented."
- **A marker only means something to a consumer that reads THAT EXACT KEY — grep the key format string across every package before assuming a write is visible anywhere.** #141: `--backfill-digest` sent under `dedup_key="backfill:<repo>:<since>"` (so `notify.send` wrote exactly ONE marker, for that key) while watchdog job 25 filtered on the per-ticket `<repo>#<n>`. Two disjoint namespaces, so no digest — however successfully delivered — could ever affect job 25's verdict, and its tickets stayed flagged for the full 48h `CARD_WINDOW_S`. The tell is free: `grep -rn backfill notify/ watchdog/__init__.py` returned nothing at all. Three companion rules when adding a NEW marker namespace. (a) **Pick a separator that survives `_dedup_path`'s sanitisation** — it rewrites `[^A-Za-z0-9._#-]` to `_`, so a `:`-separated key collapses onto a `_` and can collide with a real repo name; `#` survives and cannot occur in a GitHub repo name, which makes `backfill#<repo>#<n>` collision-proof against the card key `<repo>#<n>` by construction. (b) **Do not reuse an existing namespace to mean a second thing** — `<repo>#<n>` is documented as "this ticket got its OWN delivered card" and is read by `subagent-stop-check-run-card.sh` and `newest_delivered_card`; writing it for a digest would let a worker's genuinely missing card pass the gate. Two facts, two namespaces. (c) **`_dedup_mark_status` does NOT create the marker directory** — only `_dedup_claim` calls `os.makedirs`. Any writer outside the claim path must makedirs itself or it silently no-ops on a box that has never sent anything, which looks exactly like the bug it was meant to fix.
- **The discriminator for "is this prose guarantee a silence generator?" is WHICH WAY NON-COMPLIANCE FAILS — not whether anything enforces it.** Almost no prose is enforced, so "unenforced" alone cannot be the test or every rule in this repo fails it. #134's guard deferred to an unfired run-card and its absence produced SILENCE, which is why it needed a mechanical artifact. #159's (B) is equally unenforced, but a worker that never pastes the proof simply keeps working the backlog — non-compliance costs TURNS, never a lost signal. Apply the test before reaching for a hook: a rule whose failure mode is "does more work" is sound as text; a rule whose failure mode is "a signal disappears" or "a gate opens" needs the artifact.
- **A parse/lookup-failure fallback that reuses an "absence looks like the negative case" idiom (`X.get("field")` is `None` on failure, and `None` also means "false" for some predicate) silently restores the WRONG-direction pre-existing bug the surrounding code was written to fix.** #181 round 2, M11: `_notify_run_card`'s `is_core_ticket = not _ticket_is_stream_labeled(view.get("labels"))` collapsed to `True` on ANY `gh issue view` failure (empty response, malformed JSON, timeout) — `view.get("labels")` is `None` on failure exactly like it is `[]` for a genuinely label-less core ticket, and `_ticket_is_stream_labeled(None)` and `_ticket_is_stream_labeled([])` both return `False`. That is precisely the pre-#164 regression direction (a stream ticket's card wrongly counted as core) with a NEW trigger (a transient `gh` failure) instead of the original one. Fix pattern: track success/failure EXPLICITLY (`"labels" in view`, not `view.get("labels")` truthiness) and pick the SAFE default for the failure branch by asking "which wrong guess merely undercounts vs which one corrupts a cross-population invariant" — undercounting `done` by one is fine; a stream ticket's card inflating a core-scoped ratio is the actual bug class. The same audit turned up a second instance one call away: a **`--dry-run` diagnostic print added alongside a real fix must be gated on `not dry_run`** — `--dry-run`'s contract (silent on stderr, per its own regression test) is easy to break by accident when a NEW best-effort diagnostic is added to a code path dry-run also walks through.

- **A watchdog job callback whose return SHAPE you are widening (a bare list → a shape carrying more information) needs a `_normalize_*()` adapter, not a call-site rewrite, when existing tests already exercise the OLD shape as a legitimate contract.** #224 widened `closed_fetch` from `[n, ...]` to `{n: ts}` (per-ticket timestamps, needed for the new grace period) — `tests/test_run_card_enforcement.py::test_a_repo_that_never_uses_closes_trailers_falls_back_to_the_probe` passes a bare-list lambda (`lambda root, since: [77, 78]`) as a deliberately-preserved simpler contract, and rewriting it to the new shape would have been changing a passing pre-existing test to make a new feature look done, not proving it holds under real callers that still speak the old shape. `_normalize_closed()` accepts a dict, a list of `(n, ts)` pairs, OR a bare list of ints (unknown ts → treated as ALREADY past grace, never "wait forever for a timestamp that will never arrive") — so every existing caller and test kept working unmodified, and the production `_watchdog_closed_fetch` was free to adopt the richer shape (`{number: closed_epoch}` via the `closedAt` field it already fetches) without a matching test rewrite anywhere else.
- **A completion-CARD dedup marker (`<repo>#<issue>`, the one `_notify_run_card` claims to suppress a re-send) must be RELEASED when the user flags the underlying ticket as still-broken, or a re-fixed, re-closed ticket's fresh card is silently suppressed forever by the FIRST (now-known-wrong) card's own claim.** #298 review MAJOR-5: `notify.forget_marker("%s#%s" % (bare_repo, issue))` (the SAME public wrapper #182 already built for "a REOPENED ticket's second fix must not stay deduped against its FIRST close's card") is the right call, keyed with the IDENTICAL basename-only format `_notify_run_card`'s own `dedup = "%s#%s" % (name, issue)` uses (`name = str(repo).rstrip("/").split("/")[-1]`) — a caller building this key any other way (owner-qualified, hyphen-vs-underscore) silently never matches the marker it's trying to release.
- **Registering a new stream's Discord routing (item 4 of the #143/#300 checklist): `notify.STREAM_NOTIFY_OWNER[user] = <target>` (a code-side REDIRECT, deploys automatically on the next `push`) is almost always the right choice over `DISCORD_MIRROR_<USER>` (a per-box LOCAL, non-git `.env` key `notify.mirror_owners()` reads — cannot be provisioned or deployed by this repo's code at all, only by hand on that specific box).** #300 (miva1): the ticket's own text asked for the `DISCORD_MIRROR_DAVID` shape, but david is the ONE stream that genuinely needs mirror semantics (its own separate thread, PLUS a parallel ping to zbynek) — every other stream persona (montalu/montalu2/montalu3/simap/miva1) has NO Discord identity of its own and is correctly redirected outright, matching `STREAM_NOTIFY_OWNER`'s own header comment. A worker with no ssh access cannot verify a REMOTE box's local `.env` (not git-tracked, box-specific) — do not try; pick the redirect default unless the ticket explicitly needs the OWN-thread-plus-mirror shape david has, and say so in a code comment naming the rejected alternative so a future ticket citing the same words does not silently re-litigate it. **Either way, the routing decision alone is NOT sufficient for a real ping to land** — every stream persona's box still needs its OWN local `~/.claude/channels/discord/.env` hand-wired (bot token + the redirect target's `DISCORD_NOTIFICATION_CHANNEL_<TARGET>`), a gap `check_discord_notify_config()` already surfaces loudly at `install` time but does not close; state that residual explicitly rather than claiming the redirect "fully" satisfies a live-delivery requirement.
- **Re-wrapping a markdown bullet's line breaks after editing its prose (to fix a review finding, tighten a sentence, etc.) can split a literal multi-word string a TEST scans for (`assertIn("Each merged", ...)`) across the new line-wrap — even when the phrase was NEVER touched, only re-flowed around it.** #325: fixing several MINOR review findings in `skills/autopilot-master/SKILL.md`'s LANE 3 bullet shifted where lines broke, and `**Each\n  merged ticket...**` (bold-markered `Each` on one line, `merged` on the next after the markdown indent) silently failed `TestRunCardFiredInEveryLane::test_lane3_core_fires_run_card_per_merged_ticket`'s `assertIn("Each merged", lane3_block)` — the exact SAME class this file already documents for a phrase spanning a markdown wrap (see the `t.index()`/`TestBounceMeansOneThingInAllThreeHomes` entries above), just triggered by re-wrapping EXISTING text rather than by adding new prose earlier in the paragraph. Whenever editing prose in a paragraph a test locks a literal multi-word phrase from, re-run that SPECIFIC test immediately after — a full-suite pass later in the session is not enough to catch it fast, and the fix is always the same (nudge the wrap so the locked phrase stays on one physical line).

- **`ops-channel` (#362) is the label a stream applies to a PERMANENT, self-declared "this issue never auto-closes" channel — a teardown/refresh loop, a snapshot-retention alert log (odoo-erp #1861/#3037). It is excluded from the `/autopilot` "qualifying set" at the SAME tier as `autopilot-skip`: `AUTOPILOT_SKIP_EXCL` (`airuleset.py`, near `_core_search_excl`) is the single shared exclusion fragment consumed by `core-quals`/`slice-quals` (the `/goal` stop-proof), the footer's own counts (`cmd_tickets_status` — both the full-authority core/streamy pair and the reduced-authority mine-slice loop + its origin-recovery candidates query), and the Discord run-card's `remaining` count (`_notify_run_card`, both authority branches).** Deliberately NOT extended to the two POSITIVE `label:autopilot-skip` "skipped"-bucket queries (a DIFFERENT question — how many of the qualifying tickets are ALSO explicitly skip-labelled — and an ops-channel ticket without the skip label was never going to appear there anyway), and deliberately given NO statusline bucket of its own (no `· ops K`) — #313 is a direct, repeated user request to SIMPLIFY the footer ("counter chaos"), and a permanent, rarely-applied label is exactly the kind of population a new bucket would be noise for; it stays invisible everywhere except this note and `modules/core/statusline-vocabulary.md`'s own short pointer. Before #362, `core-quals --count` could NEVER reach `0` while a permanent ops-channel ticket stayed open, and the `/autopilot` loop dispatched a full worker onto one that found "nothing to do" (~220k wasted subagent tokens). **#364 (fixed) closed the two OTHER hand-rolled `-label:autopilot-skip` queries #362 itself couldn't reach** (a different file, a different diff): job 8's bounce/gk-request backstop queries (`_fetch_bounce_tickets`/`_fetch_gkreq_tickets`, `watchdog/__init__.py`) and the SEPARATE `autopilot-master` skill's own LANE MASTER `/goal` stop-proof (`skills/autopilot-master/SKILL.md`, a genuinely different mechanism from the regular `/autopilot` skill's `core-quals`/`slice-quals`). **There are now TWO independent copies of the exclusion fragment, both named `AUTOPILOT_SKIP_EXCL`** — `airuleset.py`'s (derived: `"-label:autopilot-skip -label:%s" % OPS_CHANNEL_LABEL`) and `watchdog/__init__.py`'s own (a flat literal, deliberately NOT a cross-import — the two modules' import direction runs `airuleset.py` → `watchdog`, always deferred/local inside function bodies, and `watchdog` is a systemd timer firing every 60s on every managed box, so a reverse import would add ~75% import-time cost, not avoid a circular import that doesn't actually exist today). `tests/test_gk_request.py::TestAutopilotSkipExclConstantsStayInSync` pins the two literal VALUES equal so a future edit to one without the other fails loudly instead of relying on a human `grep -rn ops-channel` — keep BOTH updated together if the label or exclusion shape ever changes.
- **A janitor/prune that HARD-DELETES the only routing key an async inbound channel matches against turns an inference error into a SILENT loss — presume-and-PARK (a bounded grace store the consumer still matches) instead of presume-and-delete, and give the consumer a floor that fires when nothing matches at all.** #449 (david live incident 2026-08-13): `prune_answered_questions`' "any later human prompt in the asking session = answered at the terminal" inference is false for a user typing OTHER things at the terminal while answering the real question on the phone — and the hard `drop_question` made the loss TRIPLE-silent in job 7 (an empty map short-circuits before any fetch; the channels set derives only from entries; an unmatched reply `continue`s with no log — so "zero journal lines" during such an incident is the EXPECTED forensic shape, not proof job 7 didn't run). The reusable fix shape for any future "presumed resolved, so stop tracking" janitor whose subject an ASYNC channel can still legitimately answer later: (1) move to a bounded GRACE store (`notify.grace_question` → `discord-questions-grace.json`, `QUESTION_GRACE_S`=24h) the consumer merges for matching — the presumption's cheap benefit is kept (statusline badge drops immediately; the daily re-ask reads only the main map, so no #407-style ghost) while its failure mode (a late answer) still routes NORMALLY, with the original question wording; (2) expiry lives in the CONSUMER (`_merge_grace_questions`, job 7's load), never the janitor — bare `run_once` tests without a Discord fetcher must never touch the store; (3) a NEVER-SILENT floor for the post-grace tail: remember recently-seen question channels in state (`dreply_channels`, 7d) so an EMPTY map no longer blinds the fetch, and journal + ping the owner (deduped per message id) for any owner answer attempt matching nothing (`_orphan_floor`, scoped to QUESTION channels so main-thread card/✅ chatter never pings). Two adversarial-review traps worth re-using verbatim: a store path derived ONLY from the global resolver leaks into the REAL `~/.claude` for every pre-existing test that sandboxes via the `path=` PARAMETER instead of patching the resolver (derive from the explicit path too — `_grace_path_for`); and `notify.send`'s `"dedup"` status is a CLAIM written before the POST, never delivery confirmation — gate any "done, stop retrying" marking on `marker_delivered()` and RELEASE the stale claim (`forget_marker`) so the next sweep genuinely re-POSTs (#134/#135's marker-vs-delivery trap at a new call site). Companion fact: `record_question`'s #407 supersede now graces the displaced entry too, so a reply to a superseded card or to YESTERDAY's card after the daily re-track routes for 24h — the exact loss #407 documented as its accepted MAJOR-2 residual.
