- **The discriminator for "is this prose guarantee a silence generator?" is WHICH WAY NON-COMPLIANCE FAILS — not whether anything enforces it.** Almost no prose is enforced, so "unenforced" alone cannot be the test or every rule in this repo fails it. #134's guard deferred to an unfired run-card and its absence produced SILENCE, which is why it needed a mechanical artifact. #159's (B) is equally unenforced, but a worker that never pastes the proof simply keeps working the backlog — non-compliance costs TURNS, never a lost signal. Apply the test before reaching for a hook: a rule whose failure mode is "does more work" is sound as text; a rule whose failure mode is "a signal disappears" or "a gate opens" needs the artifact.
- **A parse/lookup-failure fallback that reuses an "absence looks like the negative case" idiom (`X.get("field")` is `None` on failure, and `None` also means "false" for some predicate) silently restores the WRONG-direction pre-existing bug the surrounding code was written to fix.** #181 round 2, M11: `_notify_run_card`'s `is_core_ticket = not _ticket_is_stream_labeled(view.get("labels"))` collapsed to `True` on ANY `gh issue view` failure (empty response, malformed JSON, timeout) — `view.get("labels")` is `None` on failure exactly like it is `[]` for a genuinely label-less core ticket, and `_ticket_is_stream_labeled(None)` and `_ticket_is_stream_labeled([])` both return `False`. That is precisely the pre-#164 regression direction (a stream ticket's card wrongly counted as core) with a NEW trigger (a transient `gh` failure) instead of the original one. Fix pattern: track success/failure EXPLICITLY (`"labels" in view`, not `view.get("labels")` truthiness) and pick the SAFE default for the failure branch by asking "which wrong guess merely undercounts vs which one corrupts a cross-population invariant" — undercounting `done` by one is fine; a stream ticket's card inflating a core-scoped ratio is the actual bug class. The same audit turned up a second instance one call away: a **`--dry-run` diagnostic print added alongside a real fix must be gated on `not dry_run`** — `--dry-run`'s contract (silent on stderr, per its own regression test) is easy to break by accident when a NEW best-effort diagnostic is added to a code path dry-run also walks through.

- **The native Discord PLUGIN transport (`discord@claude-plugins-official` — `<channel source="discord">` inbound + MCP `reply`/`fetch_messages`) CANNOT carry the ❓/reply-routing flow: it is per-session-BOUND with no `message_id`→session routing table, so it is DEFERRED and the custom REST + `discord-questions.json` map + watchdog job 7 transport is KEPT (#418, 2026-08-14; audit #416 candidate verdict was adopt-pilot — this pilot refutes it with evidence).** The plugin's MCP server is spawned by `claude --channels …` and binds inbound to the ONE owning session (lifetime = that session process); airuleset instead fans MANY askers (background autopilot-worker subagents + main sessions, across panes across 4 machines) into ONE shared per-owner `_q` thread and routes each reply back to the EXACT asker via the durable `message_id → {session,cwd,channel}` map (`notify.record_question`) consulted by the always-alive systemd job 7 (`parse_discord_reply`, delivering cross-machine by keystroke). - **A "was this signal just rejected, so suppress it" settle-check built on the OVER-BROAD glob `/tmp/airuleset-*-block-<sid>` scans EVERY one of the 8 stop-gate markers, so an ORTHOGONAL gate firing silently swallows a legitimate signal the settle-check has nothing to do with — scope the settle to the ONE gate whose block is genuinely about the thing being suppressed, and LOG every suppression so silence is diagnosable.** #467 (the reported "pochovaná otázka": a `❓ ASKED` + `⏳ WORKING` ask-and-continue turn NEVER pinged): `notify-discord-pending.sh`'s `send_q` used that broad glob to decide "the last question was rejected and is being rewritten, so drop this ping" (the camera-box 2026-07-05 triple-ping fix). But a `⏳ WORKING` ask-and-continue turn routinely trips `stop-check-working-liveness` (empty `background_tasks` once a dispatched worker has returned — normal in a busy batch), leaving a fresh `airuleset-working-liveness-block-<sid>` marker that `send_q` misread as "the question was rejected" and dropped the ping — with ZERO `notify-delivery.log` line, so the loss was undiagnosable (the incident's log had nothing at all). General class: any "suppress X because Y was just rejected" check whose Y-detector scans a shared namespace of unrelated markers will eventually suppress a legitimate X the moment an orthogonal mechanism writes into that namespace — narrow the detector to Y's own exclusive artifact, and never let a suppression be silent.
- **A "every ❓ turn must leave a delivery-log line" guarantee placed INSIDE a handler function (`send_q`) only covers the turns that REACH that function — the dispatch branches that skip it stay silent.** #466 (the residual #467 did not close, reproduced live against main): #467 added `_pending_log` for the three suppression reasons inside `send_q`, but `notify-discord-pending.sh` only calls `send_q` from two dispatch branches — a `❓ ASKED` body line, or `❓` as the LAST non-empty line. Also silent: the `❓ … vlož … /goal` arm-skip (`exit 0`), and the in-place `--edit-question` reword path inside `send_q` (edits don't ping AND never recorded a line). Fix (logging-only, no ping/edit/dedup decision changed): a `SENDQ_CALLED` flag set inside `send_q` drives a **backstop before the final `exit 0`** — a `❓ NEEDS YOU|ASKED` marker present but not routed to `send_q` writes an `unhandled question-marker-not-dispatched` line. LOG-ONLY backstops are safe to be liberal: a false positive (a `✅` report quoting `❓ NEEDS YOU` as text) is a harmless diagnostic line, NEVER a spurious ping — so enforce a "leave a trace" guarantee at the OUTERMOST boundary, not inside one handler. General class: a "guarantee every X is logged" property must be asserted at the function's single exit boundary (or a post-dispatch backstop), never scattered across the individual handlers — the one handler you forget is the silent path. **Also learned:** the dedup is NOT per-project — `LASTQ` keys on the marker-line CONTENT (already per-question); the per-project `❓:<project>` string is only the send-path LOG key, which is why a per-question `qhash=` (short sha1/cksum of the question, `_qhash`) was added to every `kind=pending` line AND the send hook's `sent`/`not-delivered kind=shell` line (via `ND_QHASH` exported on the POST) — so two DIFFERENT questions are finally distinguishable in `notify-delivery.log`. **Test-harness seam:** the bash-hook integration tests fake `curl` (the send path), but the Python `--edit-question` path uses urllib and can't be faked from a bash test, so the edit-SUCCESS silent path is not directly exercisable there — the RED tests pin the reachable silent paths (`else`-branch trailing-line, arm-skip) + the qhash presence instead.

- **A SUCCESSFULLY-delivered run-card logs ONLY its inner `_send` transport line (`sent kind=python key=<repo>#<issue> reason=-`), NEVER a `kind=run-card` line — the outer `kind=run-card` line (`airuleset.py` cmd_notify, ~:3108/:3120) fires ONLY on refuse/failure/error (#523 triage).** `grep kind=run-card notify-delivery.log` therefore finds only FAILED cards (gk box measured: 2 ever, both failures, vs 189 successful `kind=python key=odoo-erp#N`); a delivered per-ticket card IS the `kind=python key=<repo>#<issue> reason=-` line, because the run-card's `send()` routes through `notify/__init__.py`'s `_send`, whose success log is `log_delivery(status, kind="python", key=dedup_key)` (:2394) with the card dedup_key `<repo-name>#<issue>`.
