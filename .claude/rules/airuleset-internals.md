### airuleset Internals — Development Rules

Hard-won gotchas for airuleset's own code. Claude Code loads this automatically
when a matching file is read, so it costs nothing in a session that never
touches the internals. Moved here VERBATIM from the project CLAUDE.md (#92);
nothing was summarised or dropped.

## Services — what each one is and how it actually works

Moved VERBATIM from the project `CLAUDE.md` (#93): these are per-service
internals, so they belong on the surface that loads when the service's own
files are touched, not in the always-on prefix of every session.

- **File-Drop** (`filedrop/` package, `:8788`) — serves user-facing files as clickable LAN URLs so the user (no direct FS access) can open them. `python3 airuleset.py share <file>` → **one URL per PRIVATE interface** (tailscale + LAN), because the user switches networks; the file DOWNLOAD server + the ephemeral `upload` WRITE endpoint (`airuleset.py upload`, `receive-files-via-upload-url.md`) both bind EVERY private IP from `filedrop.bind_ips()` (tailscale-first; interface-aware via `ip -o -4 addr` so container bridges docker0/cni-podman0 are dropped but real overlays wg*/zerotier kept) and NEVER the box's PUBLIC IP (gatekeeper 88.99.170.148 — the token is the only auth, so a public write-endpoint is banned). The systemd server can't enumerate its IPs under its AF_NETLINK sandbox → the bind list is baked into `Environment=FILEDROP_HOSTS` at install (unsandboxed); a stale baked LAN IP is skipped-not-fatal at bind. Per-file token = the link's auth. Governs via `modules/core/deliver-files-as-urls.md` + `receive-files-via-upload-url.md`.

- **Caveman plugin wiring + statusline** (`maybe_setup_caveman` in `airuleset.py`) — caveman (`JuliusBrussee/caveman`, third-party CC plugin for compressed output) is kept correctly wired on BOTH machines by `install` (so every `push` self-heals it). The managed shim ALSO renders the **Issues segment** (`statusbar.py`, renders `Issues N` / `Issues D/T` — text label per user, no emoji): autopilot `done/total` during a run (fed by `notify --run-card` → `~/.claude/autopilot-progress/<repo>.json`, 6h run window), else the count of open non-`autopilot-skip` GitHub issues — **scoped per stream**: a reduced-authority box (`resolve_authority` != full: david/montalu/marek) counts only ITS OWN slice (open non-skip `assignee:@me` ∪ `author:@me`; gh error → `open=None`, never a wrong number), full-authority boxes count the whole backlog (gatekeeper goal 2026-07-11 — David saw "Issues 16" instead of his 6). The render NEVER calls gh inline — it reads `~/.claude/tickets-status/<cwd-key>.json` and spawns a DETACHED `airuleset.py tickets-status --refresh --cwd <dir>` when stale (TTL 120s, spawn-guard 30s). `{{REPO_DIR}}` in the shim is substituted by `render_caveman_shim()` at install — never write the raw constant. airuleset does NOT own caveman's code, only its wiring: it kept half-installing / breaking because the plugin's real statusline script lives under a content-hashed cache dir (`plugins/cache/caveman/caveman/<hash>/…`) that **changes on every `claude plugin update`**, so any hard-coded hash in `settings.json` rots and the statusline silently dies. Fix: airuleset ships a **stable shim** at `~/.claude/airuleset-caveman-statusline.sh` that resolves the current hash at RUNTIME, points `settings.json` statusLine → the shim, ensures `enabledPlugins.caveman@caveman=true` + the marketplace, installs the plugin if its cache is missing, and seeds `.caveman-active` (preserving a valid `/caveman` mode pick, else `lite`). Pure reconcile logic is unit-tested (`tests/test_caveman.py`).

- **Playbook system** — per-project knowledge capture enforced after every autopilot ticket. Machinery in airuleset: rule module `modules/core/project-playbook-maintenance.md` (routing rule + `📔 Playbook:` marker mandate), `playbook-review` skill (runs post-ticket, inspects what was learnt, emits the gated marker), `playbook-cleanup` skill (one-time consolidation of accumulated notes into canonical how-to sections), and the Stop gate `hooks/stop-check-playbook-review.sh` (blocks completion reports missing the `📔 Playbook:` line). Content lives per-repo in `.claude/skills/<area>/SKILL.md` (per-area skill directories, indexed by a lean `## Playbook router` in the project CLAUDE.md — never in airuleset). Autopilot worker runs `playbook-review` at step 10 (after autopilot-log, before the final evidence block).

- **Discord notify** (`notify/` package + `hooks/notify-discord*.sh`) — the single device-ping path (mobile-app model: ❓ ask / ✅ done / api-error / autopilot card). **Per-owner thread routing:** each tmux owner (zbynek / marek) is posted to THEIR OWN thread (`claude-zbynek` / `claude-marek`) so two people's pings don't mix — an @mention alone was not enough. `notify.notification_channel(env, owner)` resolves `DISCORD_NOTIFICATION_CHANNEL_<OWNER>` → shared `DISCORD_NOTIFICATION_CHANNEL_ID` fallback → "". A Discord thread IS a channel in the API, so the per-owner id is just a different POST target. Both send paths are owner-aware: the shell `notify-discord-send.sh` (❓/✅) resolves the owner ONCE via `airuleset.py notify --owner` and forces it onto `--mention-prefix` + `--channel-id` (so they can never disagree); the Python `notify.send()` (api-error + run-card) resolves once internally. **Parallel mirror recipients (`DISCORD_MIRROR_<OWNER>`):** a notification for one owner can ALSO fan out to other owners' threads, each with THEIR OWN @mention — so an automated session-persona (e.g. `david` on dev2 running codex-bridge) gets its OWN `claude-david` thread AND the real human `zbynek` is pinged in parallel (`DISCORD_MIRROR_DAVID=zbynek`). Both send paths honour it: `notify.mirror_owners(env, owner)` returns the extra owners; `notify.send()` and the shell loop post one message per target (primary first), skipping a mirror whose thread equals the primary's (no double-post). A normal single-owner box (zbynek / marek — no mirror configured) fans out to exactly one target = unchanged. Env keys (`DISCORD_BOT_TOKEN`, `DISCORD_MENTION_<OWNER>`, `DISCORD_NOTIFICATION_CHANNEL_*`, `DISCORD_MIRROR_<OWNER>`) live in the LOCAL `~/.claude/channels/discord/.env` (NOT git). Governs via `modules/core/milestone-notifications.md`.

- **A `{{PLACEHOLDER}}` that is a SUBSTRING of another (`{{HOST_IP}}` ⊂ `{{HOST_IPS}}`) must be `.replace()`d LONGEST-FIRST** — substitute `{{HOST_IPS}}` before `{{HOST_IP}}`, or the shorter replace corrupts the longer one into `<value>S}}`. Discovered wiring the file-drop unit's multi-interface bind list (2026-07-10, filedrop multi-iface commit). Locked by `test_render_unit_bakes_the_bind_list` (`assertNotIn("S}}")`).
- **An HTML/JS page served RAW (`PAGE.encode()`, NOT `.format()`) must have SINGLE braces, never doubled `{{ }}`.** A page string moved out of a `.format()` context keeps its `{{`/`}}` escaping, which then renders LITERALLY in the browser and silently breaks all CSS/JS. Grep a served template for `{{` after any move; assert the SERVED bytes (not the source) have no `{{`. Hit live: `filedrop/upload_server.py` PAGE had 24 doubled braces after the `git mv` from meeting-analysis (david@gk found it live testing #18, 2026-07-10). Locked by `test_served_page_has_no_escaped_brace_leak`.

- **CC hook payload ground truth (live-captured 2026-07-24, #28): `SubagentStop` carries `background_tasks`** — the harness's authoritative live-task list (`{id, type: shell|subagent, status}`), but it is **SESSION-WIDE**: it lists SIBLING workers' tasks too (#29 — a healthy worker was blocked over 5 sibling tasks it could not TaskStop; ownership must come from the agent's OWN launches: the PostToolUse ledger ∪ its transcript), and it INCLUDES a SELF entry for the stopping subagent (`id == agent_id`, always "running" at its own stop — exclude it); `transcript_path` is the PARENT session's file, the subagent's own is `agent_transcript_path`; PreToolUse inside a subagent carries `agent_id` (the subagent-context discriminator). Never trust docs alone for a hook payload — capture one live (`tee -a /tmp/…-debug.log` entry added to the LOCAL settings.json, removed by the next install).
- **A tmux pane's AGENT STRIP rows (`◯ <agent> <label>`) are model-generated ARBITRARY text** — never substring-match viewport "busy" signals (`Waiting for`, `esc to interrupt`) on a raw capture that includes below-prompt chrome; peel it first (`_is_bottom_chrome` / `_above_input_box`, watchdog job 9 gk incident 2026-07-24 — a worker label "Waiting for deploy-prod.yml jobs" blocked goal-autoarm for a day). The agent strip also has a SELECTED-row shape — `❯ ● main` / `❯ ◯ <agent>` — that renders BELOW the real input box and is easy to misread as the input box itself if only `s[0] in "●◯"` is checked (misses the leading `❯`); `_is_bottom_chrome` must also match the `❯ ●`/`❯ ◯` prefix and the strip's `↑/↓ to select · Enter to view` hint (watchdog#36, live david@subdev incident 2026-07-25 — every keystroke gate silently skipped the pane for as long as the strip stayed selected).
- **CC's prompt STASH (Ctrl+S) is SINGLE-SLOT with a SILENT overwrite, and AUTO-RESTORES the parked draft the instant the delivered turn completes — NOT via a second Ctrl+S, despite what the docs imply** (empirically verified against CC 2.1.220, watchdog#35). Before stashing, a capture containing `› stashed` means the slot is ALREADY occupied — stashing over it destroys whatever's parked there, so abort instead. One Escape into a pane holding a draft is safe (shows an "Esc again to clear" hint); a RAPID DOUBLE-ESCAPE permanently deletes the draft — never send two Escapes back to back into a live pane, anywhere. See `deliver_with_stash` (watchdog/__init__.py).
- **Pane-driven automation must NEVER extract a MULTI-LINE payload from the rendered viewport** — CC's renderer HARD-wraps long lines (a 3100-char /goal template rendered as ~8 visual lines; a single-line regex armed 166 chars and the evaluator lost the release/window conditions, gk 2026-07-20). The viewport is for STATE detection (arm question present? idle?); the PAYLOAD comes from the session transcript's exact bytes (`_transcript_goal_line`). `capture-pane -J` does NOT help — it rejoins tmux soft-wraps, not renderer line breaks.
- **Truncating user-visible UTF-8 in a bash hook: NEVER `cut -c` / `awk substr`** — both count BYTES on this stack and chop multi-byte Slovak mid-character (the "…sklad zač" truncated-question incident, 2026-07-04). Use `jq -Rrs '.[0:N]'` (codepoint slice; jq is already a hook dependency). Negative slices (`.[-N:]`) work too and clamp safely on short strings.
- **`set -euo pipefail` + `VAR=$(failing_cmd)` in a hook script: the shell exits IMMEDIATELY, before the next line (e.g. `RC=$?`) ever runs** — bash's `set -e` treats a failing command substitution used in a plain assignment as an unhandled failure, not something the caller "checked". Discovered writing `block-test-skips.sh`/`block-history-rewrite.sh`, which both delegate pattern-matching to an embedded Python script and need its exit code to decide whether to print a block message. Fix: `VAR=$(cmd) || RC=$?` (put it in a tested/`||` context so `set -e` doesn't fire), never a bare `VAR=$(cmd)` followed by `RC=$?` on the next line.
- **Adding a new PreToolUse hook with a genuine RED→GREEN commit pair** (not just presence-of-tests): writing the hook + its tests in one pass never observes real RED, since the file exists on disk regardless of git-tracked state. Get true RED by `mv`-ing the new hook script out of `hooks/` (and `git stash push -- <wiring file> <doc file>` for the settings.json/module-doc changes), re-running the new tests to confirm genuine failures, committing that test-only state as the `[red]` commit, then restoring the hook + wiring and committing as `[green]`. See b6fe3ba/a2b19da/e7105b0 (#7), 88ab805/62d8245 (#10), 0ce0a47/0d3afd4 (#11).
- **An inline bypass marker (`# airuleset:xxx-ok <reason>`) hook: strip QUOTED spans before matching the marker — never a plain substring grep on the whole command.** A real bash `#` only starts a comment OUTSIDE quotes; a naive `grep -q 'marker'` (or a Python regex with no quote-awareness) ALSO matches the marker text merely being MENTIONED inside a commit message body (this hook's own commit messages document its bypass syntax, and got wrongly logged as bypasses — twice, live, while authoring #4). Fix: `re.sub(SQ+"[^"+SQ+"]*"+SQ, "", cmd)` then the same for double quotes (build quote chars via `chr(39)`/`chr(34)` since the whole script is inside a bash `python3 -c '...'` single-quoted block — a literal `'` in the source breaks the outer quoting), THEN search the marker in what's left. See test_block_staged_content_values.py `test_marker_mentioned_inside_a_commit_message_body_is_not_a_bypass`, 0d1d91f→d1fde9b (#4).
- **A Python regex `\b` boundary silently fails right after `_`** (underscore is a `\w` char, so `\b` never anchors between `ghp_` and the token following it) — real leaked tokens are routinely prefixed exactly like that (`ghp_xxx`, `sk_live_xxx`). Don't reach for `\b` or a hand-rolled `(?<![chars])`/`(?![chars])` lookaround to bound a high-entropy-blob regex; a greedy `{N,}` quantifier over a tight character class (e.g. `[A-Za-z0-9+]{32,}`) already stops correctly at the first non-matching char with NO boundary assertion needed — adding one only reintroduces the `_`-adjacency bug. See hooks/block-sensitive-staging.sh `HEX_PAT`/`B64_PAT`, f3d648e (#4).
- **A short-lived CLI process (`python3 airuleset.py <cmd>`) cannot use `os.getpid()`/`os.getppid()` as a "stays alive for the whole campaign" liveness token when the campaign spans TWO SEPARATE Bash tool calls** (e.g. a lock's `acquire` now, `release` much later) — each Claude Code Bash tool call spawns a fresh ephemeral shell that dies the instant that ONE call returns, so `os.getppid()` (the per-call shell) looks "dead" moments after `acquire` prints success. Verified live via `ps`: a Bash tool call's own PPID is the per-call ephemeral shell; THAT shell's PPID is the stable, session-long `claude` CLI process. Walk one extra level via `/proc/<pid>/status`'s `PPid:` line to get a PID that actually persists across the gap. See `_campaign_pid()` in airuleset.py, 74c2660 (#8).
- **subdev VPS runs fail2ban — NEVER probe its ssh with guessed users/keys.** A few wrong-key attempts (default key as `david@`, `root@`, …) ban dev1's source IP for 1h+ on ALL interfaces (tailscale AND public; "Connection refused" = tcp-reset REJECT, not an outage — verify from another vantage, e.g. gk), which then fails every subdev push target. The identities are FIXED in `REMOTE_HOSTS`: montalu = default newlevel key, marek + david = `~/.secrets/gatekeeper_access_ed25519`. Read them from there before any ad-hoc subdev ssh (live self-inflicted incident, 2026-07-25 #35/#36 investigation).
- **Dedup/trim pass on the rule modules: phrase-locks in `tests/` are DELIBERATELY MULTI-HOME — a "restatement" across 2+ modules is often intentional, pinned in each home by a test.** Before assuming a repeated passage is removable, `grep -rn "<phrase>" tests/` FIRST: e.g. `test_question_policy.py` asserts the sleep-window phrases in BOTH `message-status-marker.md` AND `milestone-notifications.md`, and `60`/`UNLIMITED`/`AskUserQuestion` in BOTH `message-status-marker.md` AND `user-questions-slovak.md`; `test_playbook.py` pins `po každom tickete` + `📔 Playbook:`; `test_model_tiering.py` pins the SHAPE/ADVISOR lines in two model files. The genuinely-removable duplication is only the CROSS-DOMAIN kind (a module re-teaching another module's canonical policy) — trim that to a pointer and keep each file's unique angle; never delete the intentionally-multi-homed teaching. Hooks parse the assistant's OUTPUT, not module text, so trimming a banned-phrase enumeration is safe ONLY for the exact phrases the hook regex matches — verify per-phrase and KEEP the uncovered variants (`stop-check-prose-violations.sh`). See #14 (ef9aa9b/7e96662/5cd9228/7db9509/979cda1).
- **A tmux pane's STATUSLINE is frozen at its LAST RENDER — an idle Claude session keeps showing the usage/limit numbers from its last turn, never live account state.** Reading current weekly/session usage % from a pane's footer is WRONG and produced a real misdiagnosis: on 2026-07-25 three panes showed 93% / 47% / 4% weekly for what was actually ONE account plus one separate box (each pane's statusline was simply stale from whenever it last rendered). - **Resolving a transcript for a job that has a specific (sid, cwd) pair (not just a live pane's cwd): reuse `_transcript_for_session(projects_dir, sid, cwd)`, never `find_active_transcript(projects_dir, cwd)`.** `find_active_transcript` returns the NEWEST `*.jsonl` in the cwd's encoded dir regardless of which session wrote it — correct for job 15 (which only ever has a live pane's cwd). - **Testing a watchdog restart that must CONTINUE the same transcript (`claude -c`, not a fresh session): `CLAUDE_CONFIG_DIR=/tmp/<scratch>/config claude` as a ONE-SHOT PREFIX to a single command does NOT persist into a later `/exit`+relaunch typed in the SAME shell — a `VAR=val cmd` prefix scopes the env var to that one child process only, never exports it into the shell's own environment.** `export CLAUDE_CONFIG_DIR=...` FIRST, then launch bare, so it survives every subsequent command in that shell. - **Claude Code COLLAPSES a long literal `tmux send-keys -l` into a single `[Pasted text #N]` row instead of rendering the text — so every "did my keystrokes land" check that matches the typed text (`text.endswith(_input_line_text(cap))`, the shape `deliver_with_stash` has always used) can only ever pass for SHORT payloads.** Live-hit shipping #76's job 20: a 3152-char `/goal` re-arm really did land in the box and was refused twice as "not verified", so the goal was never submitted. Use `_typed_landed(text, itext)` (accepts the literal tail OR the placeholder) for any long delivery, and note the two RENDER RACES around it, which are separate bugs from the placeholder itself: the box does not fill INSTANTLY after `send-keys -l` (a multi-KB paste needs a beat to ingest — an immediate capture shows a bare box and reads as a failed type) and it does not clear INSTANTLY after `Enter` (an immediate capture still shows the placeholder and reads as a SWALLOWED submit, firing a corrective `Escape`+`Enter` into a turn that has just started). Both need the same bounded settle poll (`_await_typed`, returns the moment the box agrees) — never a blind sleep, and a type that genuinely never appears must still be refused rather than submitted truncated.
- **An armed `/goal` SURVIVES `/exit` + `claude -c` (verified live on an isolated session: pid 993139 → 1078067, same transcript, `◎ /goal` lit again on its own) — so a watchdog restart (jobs 12/18) does NOT silently disarm a loop and needs no re-arm patch.** What DOES kill a loop silently is a different failure entirely (#76): the goal stops without CC writing any `Goal cleared:` marker, so the transcript keeps saying "armed" forever. **Never build a goal-state detector on the transcript alone** — and specifically, do NOT reach for `stop_hook_summary.preventedContinuation` as a "goal resolved" signal: montalu's own HEALTHY loop wrote `preventedContinuation: false` every ~19 minutes while working perfectly. The only truths available are CC's `◎ /goal` footer indicator (armed or not, read from the region BELOW the input box) and its `✔ Goal achieved` conversation line (finished legitimately — printed to the screen, NEVER persisted to the transcript). Both are pane-only, so goal decisions read the VISIBLE VIEWPORT (`capture-pane` with no `-S`): scrollback bites BOTH ways — a stale `/goal` line there once armed a wrong goal into a fresh session (gk 2026-07-20, job 9), and a stale `✔ Goal achieved` there vetoes a legitimate heal after a restart (#76).
- **Reading a "does the footer show X" signal: define the footer as everything BELOW the input box (the last real `❯` line, excluding a SELECTED agent-strip row `❯ ●`), NOT as the `_is_bottom_chrome` peel and NOT as "the row starting with `ctx `".** A freshly launched session renders the managed statusline WITHOUT caveman's `ctx …` block — a row `_is_bottom_chrome` does not classify as chrome at all — so the peel stops ABOVE the very row the indicator sits on AND a `ctx `-prefix guard declares the whole pane unreadable (live, #76). The by-product is correct too: a BUSY pane has no `❯` boundary, so the read returns "undeterminable" instead of a wrong "dark".
- **A watchdog job that reads a marker which may be arbitrarily FAR BACK in a multi-hundred-MB transcript should scan INCREMENTALLY from a stored byte offset, not re-tail a fixed window every sweep.** `scan_goal_markers(path, off)` bootstraps from a 4 MB tail on first sight of a session and thereafter reads only the bytes appended since — so montalu's 240 MB single-session transcript costs one small read per sweep and the marker's AGE stops mattering (a fixed tail silently misses a goal armed hours ago). Two invariants: the returned offset must stop after the LAST COMPLETE line (a live-appended transcript's final line is often half-written, and consuming it drops a real marker), and an offset past EOF (truncation/rotation) must fall back to the bootstrap.

- **Claude Code drains its type-ahead keystroke QUEUE only where a turn's Stop is ACCEPTED — a Stop-hook-REJECTED continuation is logged as a fresh turn but does NOT drain it.** So "CC executes queued keystrokes at a turn boundary" is too loose to reason from: under an armed `/goal` loop (whose Stop hook keeps rejecting the stop to force continuation) the queue can stay unexecuted for HOURS across several internal turns. Live-proven on gk 2026-07-26 (#84): the transcript logged 13:25→14:36, 14:36→15:30, 15:30→15:44 as three separate turns, yet `queue-operation enqueue content="/compact"` entries from 14:31 and 15:41 both only `popAll`-ed at 15:44:15, right after the user's manual interrupt — and then fired back-to-back (first really compacted, the rest answered "Not enough messages to compact", which IS the duplicate-compact spam users report). Consequence for any "how long has this session been stuck" detector: read the PANE's own spinner elapsed label, never a transcript-derived turn duration — the pane label runs from the last genuine EXTERNAL input, which is exactly "how long the queue has been unable to drain", while the transcript would report three ordinary turns and miss the incident entirely (`pane_turn_elapsed`, watchdog job 21).
- **An `Agent` dispatch in this Claude Code harness is ASYNC BY DEFAULT — a missing `run_in_background: true` does NOT make it foreground-blocking — so "a foreground subagent dispatch blocked the parent turn" is never a valid explanation for a long-running turn here.** Verified on the #84 forensic read: all five `Agent` tool_use calls in the incident window had NO `run_in_background` key in their `input` and every one still returned in ~100–200 ms with the identical 1062-char `"Async agent launched successfully. ... The agent is working in the background."` payload. When investigating a multi-hour turn, skip that hypothesis and instead histogram the tool_use NAMES across the window (`type=="assistant"` entries' `message.content[].name`) — the #84 answer was an unbroken chain of correctly-bounded foreground `Bash` CI polls, each individually right, with nothing ever yielding control back.
- **Reading the rows CC renders ABOVE the input box (queued commands, the spinner): walk UP from the box and require ADJACENCY — stop at the first non-`❯` content row — never grep the whole capture for the shape.** `_above_box_scan` (#84) skips blank spacers and the box's own top separator, collects the contiguous `❯ …` queued rows, and returns the first other row as the spinner; both `_pane_has_queued_compact` and `pane_turn_elapsed` consume that ONE walk. The adjacency requirement is the guard that a bare substring/regex scan lacks: a session whose CONVERSATION quotes a panel (e.g. one working on this very ticket) has real content BELOW the quoted rows, so the walk terminates before reaching them. This is the above-the-box counterpart to `_is_bottom_chrome`'s below-the-box peel (#36) — together they mean neither the agent strip's arbitrary label text nor quoted transcript content can be misread as live pane state.
- **Adding an integration test for a watchdog job that ALREADY has an established harness in `tests/test_watchdog.py` (jobs 12/15/17/18 → `RestartFakeTmux` + `_seed_context_transcript`): write it THERE, never re-mock the job's inputs ad hoc in a new test file.** Jobs 15/17 resolve their own panes AND derive context from a real seeded transcript AND consult the shared claim before any pane work, so a new-file harness patching just `list_claude_panes`/`find_active_transcript`/`transcript_current_context` silently returns ZERO log lines (every pre-pass bails before the code under test) — it reads like the feature is broken when it is the harness that is wrong. Hit live writing #84's job-17 guard test. Corollary already noted above but worth pairing here: ANY test exercising a `/compact` sender must isolate BOTH `compact_claims_path` and `compact_sync_log_path` in `setUp`, or it races the live systemd watchdog running this repo's working tree every 60s on this box.

- **`/goal <new text>` REPLACES an already-armed goal — no `/goal clear` first (live-verified, CC 2.1.220) — and a `/goal` typed into a BUSY pane writes NO `<local-command-stdout>Goal set:` marker at all.** The queued path logs a `queue-operation` entry instead, so any detector built only on the `local-command-stdout` shape is blind to exactly the arms an automation delivers. BOTH paths write one common record: a top-level `user` entry whose string content STARTS with ``A session-scoped Stop hook is now active with condition: "<payload>"`` — that is the authoritative "what is armed right now", and `/goal clear` then reports that same payload back in `Goal cleared:` (which is how the replace was proven). Two parsing traps: the payload itself contains `"` (every shipped template has `--search "-label:autopilot-skip"`), so terminate on the LAST `". `, never the first quote; and a raw-BYTES pre-filter over the JSONL must stop BEFORE that opening quote, since JSON escapes it to `\"` and the full prefix never matches. Verify with the isolated-scratch-session recipe (`CLAUDE_CONFIG_DIR`, below) — do not reason about `/goal` semantics from the docs.
- **`_typed_landed` structurally CANNOT verify a MEDIUM-length payload — one long enough to WRAP in the input box but too short to collapse into `[Pasted text #N]` — and that refusal is correct, not a bug to loosen.** CC renders a wrapped draft HEAD-first on the `❯` line with indented continuation rows, so the boundary line holds a PREFIX of the typed text; accepting a prefix match is exactly the signature of a TRUNCATED type, which is the #36 disaster the check exists to prevent. Consequence for any new long-keystroke delivery: it verifies only for payloads that either fit one rendered line or exceed CC's paste-collapse threshold. The real autopilot templates (3.1–3.7 KB) collapse and verify fine — but a scaled-down ~450-char stand-in in a test harness silently fails "delivery not verified" forever and looks like a product bug (cost two live runs on #64). Size any live delivery proof at PRODUCTION payload length. Related pane-reading trap seen in the same runs: a stale `✻ Cogitated for 1m 16s` spinner row survives above the box after CC ends a turn via its "hook blocked the turn 9 consecutive times — overriding" cap, so `_classify_boundary` keeps reporting `busy` for a pane that is genuinely idle.
- **Before choosing ANY similarity threshold to decide "is this the same artifact, older version?", measure the real version-distance distribution out of git history — the intuitive answer is routinely wrong.** #64 needed to tell "the autopilot `/goal` template, older version" from "a goal the user wrote". Replaying all 62 commits that touched `skills/autopilot/SKILL.md` showed the two ranges OVERLAP: two CURRENT but different variants sit at ratio 0.7100, while one variant against its own three-week-old version sits at 0.7279 — so no threshold separates them, and a false positive would silently overwrite a live loop's instructions. The working answer was an EXACT hash over a NORMALIZED form (parenthetical citations, backtick spans and punctuation dropped): it absorbs the editorial trimming a printing agent really does (a live loop was 0.9808 from the template and byte-matched NO shipped version, yet normalized to it exactly) without absorbing substance (26 distinct raw historical versions → 25 normalized). Pair it with tracking-by-OBSERVATION (record the variant the first time a session is seen matching a CURRENT version) so anything never observed matching is untouchable by construction rather than by threshold.
- **Live-proving a watchdog job that drives a REAL Claude Code session: two harness traps beyond the documented `CLAUDE_CONFIG_DIR` recipe.** (a) Launch the binary through a symlink NAMED `claude` (`ln -s <versions>/<ver> $SCRATCH/bin/claude`) — invoking the versioned path directly makes tmux report `pane_current_command` as `2.1.220`, which `_reconcile_candidate_panes` correctly rejects, so every sweep silently sees zero panes and the job looks broken. (b) A scratch session armed with an autopilot-SHAPED goal will actually start doing autopilot work — one here spawned background agents and grew to 82 K context inside minutes. Give the throwaway session a stop condition that keeps it idle, and tear it down (`/goal clear`, kill the pane, then confirm no orphan process survives the `tmux kill-session`) the moment the proof lands.
- **A classifier-style hook (allow-list / block-list over real commands) can only be verified by REPLAYING a real command CORPUS through it — unit tests and a hand-written smoke list both miss the shapes that actually occur.** #80: after the unit tests were green and a 15-case smoke list of "realistic" commands passed, replaying ALL 687 of gatekeeper's real main-agent Bash commands from one day (extract them with a small script over the transcript's `isSidechain=false` assistant `tool_use` blocks, then run the hook once per command with the payload built via `json.dumps`) still surfaced three whole false-positive CLASSES that no hand-written case had: an output reducer after a pipe (`gh pr merge … 2>&1 | tail -2` — the single most common coordination idiom in the corpus), a bounded verification peek (`head -5 /tmp/out`, `tail -3 SKILL.md` right after writing it), and an assertion (`grep -c`). Block rate went 18.6% → 14.1% and each class became its own RED→GREEN pair. The corpus replay is also the only honest way to state the blast radius of a classifier change ("14% of a real day's commands would block, and here is what they are") instead of guessing. Do the replay BEFORE `push` — a hook deploys to every managed box and gates every session's Bash.
- **When a guard hook "never fired", read its BYPASS log before concluding the classifier is too lenient — a self-servable PERMANENT escape marker is a session-wide kill switch, and an agent WILL arm it the first time the hook false-positives.** #80's ticket reasoned from the ABSENCE of `/tmp/airuleset-main-exec-block.log` that #66's allow-list was letting everything through; the real chain was `/tmp/airuleset-main-exec-bypass.log` with 332 entries — the main session hit a false positive on the mandated `cat > body.md <<'EOF'` recipe, `touch`ed the documented exception marker at 01:24 with a rationalization in its own transcript ("Hook's documented exception applies… Taking it (it's logged)"), and the hook was fully dead for the next 17 hours. Two design lessons for any future guard: (a) an escape hatch must be ONE-SHOT (honoring it consumes it) so abuse costs a turn each time instead of once, and (b) arming the escape hatch must itself be exempt from every other gate in the same hook, or the guard sits in front of its own only exit. Diagnose in this order: bypass log → block log → classifier.
- **A guard whose acceptance forbids ever stopping the loop should be built as a RATE-LIMITED NUDGE, not a cap: make the block itself reset the counter it fires on.** #80's per-dispatch Bash counter blocks once past N and immediately zeroes, so re-running the same command right after a nudge passes — the worst case is one instructive block per N calls, never two in a row, even if the reset-on-dispatch wiring (`PreToolUse` Agent/Task/Workflow) were to fail entirely. That property is what makes it safe to deploy a behavioral guard to 6 live boxes at once. Related wiring rule: register such a reset on EXACT tool-name matchers (`"Agent"`, `"Task"`, `"Workflow"` as separate entries), never a regex like `"Agent|Task|Workflow"` — an unsupported regex silently never matches, and a counter that never resets is exactly the failure mode the nudge design is insuring against.

- **Where content actually LOADS in Claude Code — settled empirically + from the 2.1.220 bundle (#91), do not re-derive.** A **skill body** enters context ONLY on an explicit `Skill` call; session start carries just a `skill_listing` attachment of name+description (measured 25,401 B ≈ 6.4k tokens for 34 skills — paid every session whether or not any skill is ever invoked). A **`rules/*.md` + `paths:`** file auto-injects its FULL body as a `nested_memory` attachment (`"type": "User"` for `~/.claude/rules`, base = session CWD; `"Project"` for `<repo>/.claude/rules`, base = repo root) — but the trigger is **Read / @-mention / IDE-open ONLY**: `Edit` and `Write` never push `nestedMemoryAttachmentTriggers`, so content that must land when the model is about to WRITE code cannot live there. A **`PreToolUse` hook returning `hookSpecificOutput.additionalContext`** injects on the ACTION and is the only automatic surface for action-shaped content (`gh pr merge`, `git push`, a deploy, an `Agent` dispatch); the same field also works on `UserPromptSubmit`, `PostToolUse`, `Stop`, `SubagentStop`. Gitignore semantics (the `ignore` npm package) apply to `paths:`, a trailing `/**` is stripped, an uncompilable pattern silently matches NOTHING, and `paths: "**"` silently turns the rule back into an always-on file.
- **Proving "does this content reach the context" costs one cheap print-mode run — never assert it, and never test it against the real profile.** `export CLAUDE_CONFIG_DIR=/tmp/<scratch>/config` FIRST (a `VAR=val cmd` prefix does not survive into later commands), rsync the real `~/.claude` in minus `projects/ jobs/ telemetry/ plugins-heavy dirs`, copy `~/.claude.json` + `.credentials.json`, then run the raw binary (`~/.local/share/claude/versions/<ver>`), never the bashrc `claude` wrapper (its `_has_conversation()` reads the REAL `$HOME`). Make the probe **falsifiable in both directions**: ask for a fact that exists ONLY in the candidate body (`grep` it to 0 hits in `modules/**` and `~/.claude/CLAUDE.md` first) and, in the same run, a fact from a body that should NOT have loaded — a one-sided "it knew the answer" proves nothing, since the model may know it from the always-on rules. The transcript then shows the structural proof: an `attachment` entry of type `hook_additional_context` (`hookEvent`/`hookName`) or `nested_memory`.
- **Measuring the session-start prefix: `claude -p "Reply with exactly: OK" --output-format json`, then `cache_creation_input_tokens + cache_read_input_tokens + input_tokens`.** That is the real number from the API's own `usage`, not a bytes/4 estimate — and dense technical rule prose tokenizes far worse than 4 chars/token (the 69,286 B `## Development Rules` block measured 26,423 tokens, ~2.6 B/token, where a chars/4 estimate said 17k). Run it in the REPO whose prefix you care about: a project `CLAUDE.md` only loads in its own repo, so the same config measured 127,698 tokens in a bare dir and 162,726 in this one.
- **A hook that classifies a COMMAND must strip what the command CARRIES before matching — heredoc bodies first, then quoted spans.** Re-learned the hard way within an hour of shipping `inject-situational-rule.sh` (#91): a `gh issue comment -F body.md <<'EOF' … EOF` whose body merely DESCRIBED the trigger table matched nine topics and injected 65.3 kB into the live session. Same class as #80's `cat > body.md <<'EOF'` false positive, and it will recur in any new command-matching hook. Pair it with a total-size cap per call that **defers** rather than consumes (leave the dedup marker unset for what you drop, so its own action can still load it later).
- **`.claude/` is gitignored here, and a directory-pattern ignore cannot be negated from inside it** — git never descends, so `!.claude/rules/x.md` alone does nothing. The working carve-out is `.claude/*` followed by `!.claude/rules/` (#92).
- **Before concluding from a transcript corpus that a mechanism "never fires", check WHEN the mechanism was wired.** A 7,941-transcript / 4.5-month sweep found zero `rules/*.md` injections and read as proof the surface was dead; the user-level symlinking (`2fc29a6`, #40) had actually landed 25 hours before the sweep, so the corpus could not contain a single hit. ## pre-write-script-check.sh — why it exists and what it scans

## The measure → change one thing → re-measure cycle (#130)

**This repo's changes are judged on the LIVE long-running goal-armed runs, not
on the ticket's own replay.** Four days of cost work shipped before anything
could tell whether any of it made things cheaper, because every ticket was
graded on its own isolated evidence. `airuleset.py delegation` is the standing
instrument that closes that gap; this is how to use it.

```bash
python3 airuleset.py delegation --hours 12                  # this box
python3 airuleset.py delegation --hours 12 --host all       # the whole fleet
python3 airuleset.py delegation --hours 12 --host all --tickets   # + cost per closed ticket
python3 airuleset.py delegation --hours 12 --json           # machine-readable
```

**The cycle, and a change is not finished until it has been round-tripped:**

1. **Measure** the live runs over a window that contains real work (`--hours
   12` is the window both hand measurements on #130 used). Save the `--json`
   output — it is the baseline, and without one there is nothing to compare to.
2. **Change ONE thing.** Two changes in a window are unattributable; the
   measurement cannot tell you which one moved the number, and the temptation
   is then to credit the one you preferred.
3. **Re-measure the SAME runs over a comparable window.** Same `--hours`, same
   projects, ideally the same time of day — these boxes are not uniformly busy.
4. **Keep or revert on the number.** A change that cannot be shown to move a
   live-run number is not finished. Reverting on the number is the point of the
   loop, not a failure of it — the alternative is what this ticket was filed
   about, a ruleset accumulating unverified changes.

**Reading the output honestly:**

- **The cost unit is RELATIVE, never a price.** The weighting
  (`input x1.0 + cache_write x1.25 + cache_read x0.1 + output x5.0`,
  `burn.COST_UNIT_WEIGHTS`) is printed on every render for exactly this reason.
  It is the Opus row of `burn.PRICE` divided by 5, so it is deliberately
  TIER-NEUTRAL: it measures VOLUME, and model-tier drift is a separate signal
  that must not be silently folded in here.
- **A subagent turn is not a main turn.** A subagent's tokens are mostly cache
  reads of a smaller prefix while a main turn re-sends a 200–350K context — so
  compare `ctx/turn` alongside `units`, and state the weighting whenever
  quoting a ratio. Whichever way a number falls, that confound is stated, never
  buried.
- **`per closed ticket: —` means zero tickets closed, not cheap.** A window
  with real spend and no closed ticket is a materially different finding from a
  low cost-per-ticket, and `burn.units_per_ticket` returns None rather than
  letting the two blur.
- **`--tickets` is opt-in** because it needs network + `gh` auth; the base
  measurement must never depend on them. A project whose repo does not resolve
  (`repo: null`) shows no per-ticket line rather than borrowing a denominator.

**It is an instrument, and it stays one.** It reports; it does not gate, block
or threshold anything, and it deliberately leaves `burn.scan()` and every
alert baseline untouched. Enforcement is a separate decision to be taken
against a baseline, once one exists.

- **A remote box collected by invoking its OWN `airuleset.py <cmd> --json` returns the MERGED shape, not the per-box raw shape — a coordinator that reads only the raw shape drops every remote silently, with no WARN.** #130: `_delegation_remote` parsed each remote reply cleanly and contributed nothing, because `cmd_delegation --json` prints `merge_splits()` output (`by_project`, keyed `<host>:<project>`) while `merge_splits` itself consumed `split_report()` output (`projects`). The failure is invisible by construction: an UNREACHABLE box WARNs, but a reachable one contributing zero is indistinguishable from an idle one, so the coordinator printed a dev1-only table under a fleet heading and the number would have shipped as a fleet total. `burn`'s own `merge_reports` survives the same round-trip only by coincidence (it reads `by_model`/`by_day`/`by_project`, which the merged shape happens to carry — though `host` is lost, so remote rows land under `?`). Two rules for any future remote collector: make the merge accept BOTH shapes (`_split_rows_of`) rather than making the remote emit a special one — that also keeps a fleet report working mid-rollout when boxes are on different deploys — and take the row's OWN host over the collector's, or the work gets attributed to the box that asked. Catch it by checking a remote directly (`ssh <box> 'cd ~/devel/airuleset && python3 airuleset.py <cmd>'`) and confirming its rows appear in the coordinator's output; a zero-row remote is the tell, and "the boxes were idle" is the assumption that hides it.
- **`burn.scan()` is blind to subagent transcripts, and the consequence is a FALSE answer rather than a missing one (#130, separate ticket for the reconciliation).** The existing #108 bullet above notes the two-level glob finds ~1% of the corpus; the specific damage here is that `isSidechain` appears ONLY in `<proj>/<sid>/subagents/agent-*.jsonl`, which `scan()`'s `<root>/*/*.jsonl` never opens — so `main_vs_sidechain` returns three `main|*` rows and zero sidechain rows on a box where subagents are 82% of the spend. Use `airuleset.py delegation` for any MAIN-vs-SUBAGENT question; `burn` answers the by-model/by-day/by-project questions and its `main_vs_sidechain` bucket should not be quoted at all. Note why the fix was NOT folded into `scan()`: it feeds `hourly_snapshot()` → the watchdog's `snapshots.jsonl` → `compare_changes()`, the fleet feed and `hourly_burn_alert()`'s live thresholds, so including subagents would roughly double every hourly figure against a history recorded without them and re-fire the alerts on the discontinuity — a threshold change wearing a bug-fix costume.
- **Composing a long `gh issue comment` body as a WORKER: `cat > body.md <<'EOF'` in Bash, not the Write tool** — Write refuses a scratchpad file that looks like a findings/report document ("Subagents should return findings as text, not write report files"), which is correct policy and a dead end for a comment body. The quoted heredoc is also what keeps backticks, `$` and `%` intact per `gh-cli-recipes.md`. **For a COMMIT MESSAGE the opposite applies:** write it with the Write tool and `git commit -F <file>`, because `block-commit-without-design.sh` scans the whole Bash command text and a heredoc-bodied message citing any bare `#N` (context tickets, a sibling issue) demands a design marker for each of them — the message file keeps the numbers out of the command entirely, and the trailer still records them in the commit.
- **Verify a derived/sensitivity figure by COMPUTING it before it goes in a ticket comment, even when it only supports a conclusion you have already measured.** #130's draft asserted that reweighting cache_read to 1.0 moved the MAIN/SUB split from 17.8/82.2 to "17.4/82.6"; the actual recomputation gave 16.0/84.0 (and 21.9/78.1 at weight 0). The real numbers made the point STRONGER — the conclusion is invariant across the whole plausible weighting range — so the invented figure was both wrong and weaker than the truth. Any "the choice of constant is not doing the work here" claim is a three-line recomputation; make it, and quote the band.

## Reading a transcript for TOKEN measurements (#131)

- **A transcript LINE is not a turn — dedupe by `requestId` before counting anything.** Claude Code writes ONE assistant API response as SEVERAL lines, one per content block (`thinking`, then each `tool_use`), and every one of them carries a COPY of the same request-level `usage`. Measured on `agent-a8f4affe3e4d342cb.jsonl`: **236 usage lines, 111 distinct `requestId`s** (2.13x), with one request spread over 9 lines each restating `cache_read_input_tokens: 118,307`. Line-counting therefore inflates `turns` ~2x AND multiply-counts the same input tokens; it also silently distorts any per-turn mean, because a request written across 9 lines gets weighted 9x. Key on `requestId`, fall back to `message.id`, and keep the LAST usage snapshot per request — the trailing block carries the response's real `output_tokens` while earlier blocks carry partial values, and the input side is identical on every line. This is why `burn.scan_split()` over-counts (filed separately); `burn.read_dispatch` is the correct shape.
- **A `<synthetic>` entry has a usage block of four zeros and a UUID where a `requestId` would be — drop it, keyed on the ZERO USAGE, never on the model string.** Counted as a request it becomes a dispatch's LAST one and reports a context of 0; live that produced a growth of **-117,959** on 1 of 301 dispatches. `burn.scan()`'s own `by_model` already has a `<synthetic>` bucket, so the shape is not new — it just never mattered until something read first-vs-last instead of a sum.
- **A subagent transcript carries much of its own injected floor, exactly measurable.** Line 0 is `type: "user"` with the dispatch prompt as a plain STRING in `message.content`; then two `attachment` entries — `skill_listing` (with the full `content`, and a `skillCount`) and `deferred_tools_delta` (`addedNames`). What is NOT in the transcript: the base system prompt, the loaded tool schemas, the agent definition, and CLAUDE.md — those must be read off disk (`burn.import_closure_chars` resolves the `@import` closure, each file once, cycle-safe) or left in a NAMED residual. Never fold an unmeasurable part into an attributed one.

- **A batch of literal `str.replace(..., 1)` edits over one file silently no-ops when an earlier replacement moved the anchor — and lands in the WRONG function when two functions share identical code.** #144 hit both in one pass: two edits meant for `cmd_secret` never applied (the health-probe fix was half-live, still sending the token) and a third landed in `cmd_upload`, which has a byte-identical readiness loop, pointing an unrelated command at a `/healthz` route its server does not have. - **A CLI that hands a secret to a child must not hand it the parent's fd 1/2.** `subprocess.run(cmd, env=...)` with no `stdout=`/`stderr=` gives the child the agent's transcript, so `secret exec DB -- env` was a one-command exfiltration and any verbose child did it by accident. - **Pass a capability token to a detached child through the ENVIRONMENT, never argv.** `/proc/<pid>/cmdline` is 0444 (every uid on the box) while `/proc/<pid>/environ` is 0400. These boxes host foreign uids by design, so an argv token is readable by all of them for the endpoint's whole lifetime. Same reason a liveness probe must target a token-free route (`/healthz`, 204): probing the token URL hands the token to whatever won the pick-a-port race.
- **`O_EXCL` refuses a planted symlink (EEXIST); `O_TRUNC` FOLLOWS one and truncates the target.** A metadata write sitting next to a value write looked equally safe and was an arbitrary same-uid file-destruction primitive (`secrets/X.meta -> ~/.ssh/authorized_keys`). - **An env var documented "tests only" is enforced by nothing.** Gate such an override on a property an attacker cannot arrange (path under `tempfile.gettempdir()`), report the refusal on stderr, and the tests keep working because they already run under a temp dir. - **`build_opener(ProxyHandler({}))` DROPS the handler from `.handlers`** — an empty proxies dict registers no `*_open` methods, so `add_handler` never keeps it. A structural assertion for "our opener carries an empty ProxyHandler" therefore fails on correct code; assert BIDIRECTIONALLY instead (a default `build_opener()` in the same environment DOES carry the variable's proxies, ours carries none). A live control is impossible on loopback: urllib bypasses proxies for 127.0.0.1, the only address a test endpoint should bind.

- **Adding a watchdog job: the docstring is load-bearing and tested.** `tests/test_no_session_kill.py` parses the header (`N numbered jobs per poll — L LIVE and R RETIRED`), requires an entry per number with no holes, and cross-checks the retired count against entries marked REMOVED. - **A PreToolUse guard registered on the `Bash` matcher alone leaves the `Read`, `Grep` and `Glob` TOOLS completely unguarded — and for anything an agent might want to LOOK AT, those are the more reflexive route, not the fallback.** Issue #153's first green version hard-blocked `cat ~/.claude/secrets/DB_PASS.secret` and every shell shape around it, while `Read` with `file_path` pointing straight at the same file sailed through untouched; a fresh-context adversarial review rated it the one CRITICAL finding, on the grounds that an agent asked what is in a file reaches for `Read` long before `cat`, and a prompt-injected one has a route no Bash-matched hook can see. The hook's own header had written that gap down as "outside its reach by construction", which was a design choice phrased as a law. Register the extra matchers by **EXACT tool name, one settings entry each** (`Read`, `Grep`, `Glob`) — this repo already registers `Write` and `Edit` as separate entries for the same reason, and an alternation regex matcher has been observed here to silently never match, which is the worst outcome available: a guard that never runs still reads as coverage. Payload fields differ per tool (`file_path`, `notebook_path`, `path`, `glob`), and one discrimination is load-bearing: **`Glob`'s `pattern` IS a path pattern and must be inspected, while `Grep`'s `pattern` is a regex to search FOR and must NOT be** — treating Grep's pattern as a path blocks searching the repo for the guard's own subject matter, a false positive with no security value whatsoever.
- **An allowlist of "provably metadata-only" commands is almost never what it says — two independent shapes break it, and both look harmless in the list.** (a) A head that accepts a **file as a NAME LIST** reads content and echoes it back in its own error text: `file -f <path>` and `du --files0-from=<path>` both print the file's first line as `cannot open '<CONTENT>'`. (b) An allowlisted head **loses its meaning when PIPED** — `ls <dir>/* | xargs cat` makes `ls` a name source, not a listing, so the exemption has to be conditional on the segment's terminator, which means a quote-aware splitter must return `(segment, terminator)` pairs rather than bare strings. Two further entries that read as metadata and are not: `cd`/`pushd` (the Bash tool's working directory PERSISTS between calls, so an allowed `cd` in one call makes a bare `cat *` in the NEXT call invisible to any stateless single-command check — refusing the `cd` is the only thing that closes it), and `chmod`/`chown`/`rm`/`shred`/`touch`, which are mutations rather than reads and, on a box hosting foreign uids by design, hand a 0600 file to another account. What survived audit for #153 was exactly `ls`, `stat`, `test`, `[` — and `ls -l` plus `stat` answer every legitimate metadata question anyway.
- **A minimum-length floor on a redaction/matching filter must be tested against the VALUE, never against each derived FORM, because encodings and escapings EXPAND.** #153 extended an output filter with escaped renderings and introduced a regression the unit tests could not see: the existing per-FORM `len(form) >= 4` guard let a 1-byte value `"` through as its 6-byte HTML rendering `&quot;`, so every `&quot;` in a child's ordinary output became the redaction marker while the function's own docstring promised short values are left alone. The general rule: whenever a filter derives N representations from one input, any length/entropy precondition belongs on the INPUT, or the derivations quietly re-admit exactly what the precondition excluded.
- **Proving a replacement assertion "can now fail" requires mutating the code path the test actually EXERCISES — mutating the function the test is named after is the easy way to certify a still-tautological test.** #153 replaced a test whose `calls = []` was local and never wired in. - **`sudo -n -l` reporting `(ALL : ALL) NOPASSWD: ALL` for the agent's uid settles every "could this live somewhere the agent cannot read" question on these boxes with a flat no — and the honest consequence has to be written into the shipped artifact, not just the ticket.** A root-owned 0400 store, a dedicated service account and a setuid helper are each one `sudo cat` away, so uid separation buys nothing here and implementing it would imply a boundary that does not exist. What a hook genuinely delivers in that situation is worth stating precisely, because it is still worth having: the unsafe path is refused BY DEFAULT so the leak cannot happen by reflex or by prompt injection, and any deliberate circumvention has to leave an artifact (an audit line, or its own removal in git). - **A text-matching guard over command STRINGS is inherently self-tripping, and the fix is documentation plus a Write-tool workflow, never a heredoc-body exemption.** #153's guard refuses any command whose text merely NAMES the protected path, so `grep -rn '\.claude/secrets' hooks/` and a commit or issue body quoting the path are blocked although they read nothing — the same shape `block-sensitive-staging.sh` has had for years, with the same remedy (describe the path in prose, or write the body to a file with the Write tool and `cat` it in). - **A path-matching guard must decide on what the shell can EXPAND a component into, not on how it is typed — and the anchor that separates a path from a REGEX is the component's literal PREFIX, never a literal run anywhere in it.** #156: `block-vault-store-read.sh` matched the literal characters `.claude/secrets`, so `cat $HOME/.cl*/sec*/*` read a credential and was allowed — globbing is an entire expansion layer between the spelling the hook reads and the path the shell resolves. - **A lock test that forbids a literal has a SECOND failure mode beyond matching its own prose: forbidding a token the CORRECT FIX must legitimately contain.** The playbook already warns that a `assertNotIn("time.sleep(0.6)")` matches the docstring explaining it. #156 hit the other shape: a lock asserting `not isinstance(payload, dict)` never appears — written to kill a dead conjunction — which no correct implementation could satisfy, because a top-level guard rejecting a non-object payload IS the fix and contains that exact token. - **`airuleset.py secret`'s own guard hook makes THIS repo self-tripping in a specific way worth planning around.** Any Bash command whose text names the store — a probe script, a `gh issue comment` heredoc, a `git commit -m` message quoting the path — is refused, by design. It also correctly flagged a claim as too strong (an audit "reference" is whatever the pattern matched, so a VALUE shaped like a store filename lands in the log) — a class of defect no test suite catches, because the code does exactly what it says and what it says is wrong.
- **When a guard's rule needs a head that "walks a tree by construction", require the ACTION as well, and measure both spellings before choosing.** #156: adding `find` to the recursive-sweep trigger closed a real leak and cost 90 real commands, essentially all `find ~/.claude -name ...` name listings — the same trade already declined once for `du -sh ~/.claude/*`. Classifying the corpus by shape gave the answer without another full replay: the `-exec`/`-delete` family costs **5** commands (3 of them the session's own probes) while any-`find` costs **104 more** that only ever listed names. So the action form is blocked and the piped form (`find <parent> -type f | xargs cat`) is ADMITTED — deciding it would mean enumerating reader commands, the enumeration the guard rejects on principle, and the header already carried an `xargs`-fed-a-name-list gap that just needed to name this shape. A classifier rule that costs 20x more to close the second half of a class is two rules, not one.
- **A shared stdout channel between a matcher and its wrapper is an INJECTION channel — sanitize at the source, and make the real record win by position.** #157: the matcher emits its audit fields on a `#AUDIT# ` line the bash wrapper splits out with `grep`, which turns everything ELSE the matcher prints into a way to forge that line. The general shape: any time a hook passes STRUCTURED data back through a channel that also carries UNTRUSTED text, the untrusted half needs a sanitizer, not the structured half a cleverer parser.

The general shape — a gate that reads a file the same blocked command was going to produce — will recur for any hook that inspects `-F`/`--body-file` content.

- **An evidence protocol must name a command whose SUCCESS state prints something — otherwise it cannot distinguish a proof from an omission.** #159: `gh issue list --state open --search "-label:autopilot-skip"` prints NOTHING when the backlog is empty, so "paste the output showing none remain" asks for a blank space, which is byte-identical to never having run the command. - **`pgrep -f "<pattern>"` inside a poll loop MATCHES THE LOOP'S OWN SHELL, so a "did my job die?" liveness check answers yes forever.** The playbook already documents this for `pkill -f` (which kills the calling shell); the `pgrep` form is worse in a different way — it fails SILENTLY and inverts the wait's meaning. - **A harness `<status>killed</status>` on a background task does NOT mean the OS process died — and the two cases need opposite responses.** Twice in one session the notification said the suite was stopped while the run was genuinely gone; the general shape is the documented one (the handle is dropped, the process may survive), so the correct move is to re-derive from the DURABLE artifact — the output file's size/mtime and its own terminal line — never to relaunch on the notification alone.
