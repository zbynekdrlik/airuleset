### airuleset internals — File-Drop / upload

Hlbší archív airuleset-internals je v `.claude/rules-reference/internals-archive.md` (on-demand). NOVÉ File-Drop / upload lekcie pridávaj SEM.

- **Durable credential persistence (#529, `filedrop/vault.py` + `cli_vault.py` + watchdog job 29) reuses the vault framework rather than forking it, and the durable home `~/.secrets/<name>` is DELIBERATELY a different tree from the vault store `~/.claude/secrets/` — so `hooks/block-vault-store-read.sh` (which guards `.claude/secrets`/`.secret`) never touches it, and the vault lifecycle (`forget`/`purge`) NEVER deletes it (the durable copy is the whole point — it outlives the ≤24h delivery buffer).** Four reusable sub-lessons. (1) A NEW sensitive on-disk write reuses the store's own `O_EXCL|O_NOFOLLOW` + 0700-dir/0600-file discipline from day 1 (#271): `persist_durable(path, value, overwrite)` validates the location (no symlink at the final component, no git-repo ancestor — the `assert_safe_store_dir` reasoning) THEN writes O_NOFOLLOW, `O_EXCL` for write-if-absent (exec self-heal) / `O_TRUNC` for overwrite (paste-time). The durable filename keeps natural HYPHENS while the vault NAME is underscore-only (`NAME_RE`), so `--persist` takes an EXPLICIT operator path — never mechanically derived from the name (#443 naming-context trap). (2) Paste-time persist lives in `store_value` (the single choke point where the value lands), reading `durable_path` out of the meta that `register_request(durable_path=)` recorded — LOUD-but-never-fatal on failure (the vault copy already succeeded, so a durable-write error must not report the credential unstored; it runs in the `vault_server.py` child so its stderr goes to the endpoint log, and the periodic backstop + `secret status durable=…(MISSING)` are the session-visible nets). (3) The #134 artifact-gate backstop is a PURE READ (`durable_backstop()` checks file EXISTENCE for `ready` names with a durable target — it never opens the value, so `read_value`'s single-caller invariant holds) → it is dry-run-safe by construction and re-fires every hour while missing (NOT a one-shot latch, so the #516 dry-run-latch trap does not apply). (4) FOLD the backstop into the EXISTING hourly job 29 (`vault_purge_job` via a second injected `backstop_fn`, same "wired = on" convention as `purge_fn`) rather than a NEW `_add` job — no `EXPECTED_STANDALONE`/`CANONICAL_SWEEP`/docstring-header-count change (the job LABEL is unchanged), the #486 net-LOC direction. The run_once signature grew (`vault_backstop=None`), which re-pins the `test_vault_purge_job.py` mutation anchor's FIRST LINE (`vault_purge=None` mutation target itself untouched — same re-pin shape as #440/#461/#516). One-trailing-newline durable bytes (`_durable_bytes`) — don't double an SSH key's existing `\n`.

- **File-Drop** (`filedrop/` package, `:8788`) — serves user-facing files as clickable LAN URLs so the user (no direct FS access) can open them. `python3 airuleset.py share <file>` → **one URL per PRIVATE interface** (tailscale + LAN), because the user switches networks; the file DOWNLOAD server + the ephemeral `upload` WRITE endpoint (`airuleset.py upload`, `receive-files-via-upload-url.md`) both bind EVERY private IP from `filedrop.bind_ips()` (tailscale-first; interface-aware via `ip -o -4 addr` so container bridges docker0/cni-podman0 are dropped but real overlays wg*/zerotier kept) and NEVER the box's PUBLIC IP (gatekeeper 88.99.170.148 — the token is the only auth, so a public write-endpoint is banned). The systemd server can't enumerate its IPs under its AF_NETLINK sandbox → the bind list is baked into `Environment=FILEDROP_HOSTS` at install (unsandboxed); a stale baked LAN IP is skipped-not-fatal at bind. Per-file token = the link's auth. Governs via `modules/core/deliver-files-as-urls.md` + `receive-files-via-upload-url.md`.

- **The file-drop port MUST be DETERMINISTIC per uid (`filedrop.default_port_for_uid(uid) = DEFAULT_PORT + uid%1000`), NEVER a racy first-free probe from the shared `DEFAULT_PORT` — on a multi-user box (the ~12 subdev streams share one tailscale IP) the probe reflects only a TRANSIENT instant, so under a fleet push (every `install` restarts the unit, so servers bounce) every account bind-tested :8788 momentarily-free and piled onto it; only ONE server survived, the other ~10 died on Errno 98, and every loser's `share` STILL advertised :8788 → 404 off a stranger's store whose token dir was empty (#493, 2026-08-15 — live: 12 accounts, only 2 servers listening box-wide, montalu's service `failed "could not bind :8788"`, its minted token 404ing while the file sat in `~montalu/.claude/filedrop/<token>/`).** The share side (`filedrop.PORT` fallback) MUST derive from the SAME function (`persisted_port() or default_port_for_uid()`), so the URL advertises exactly the port the per-uid server binds — a share/server DISAGREEMENT is itself a 404. `_choose_filedrop_port` re-anchors on `want = default_port_for_uid()`; the persist/probe machinery survives ONLY as the collision/legacy (#33) fallback. **Live-debugging tell for this class:** the file EXISTS in the invoking user's own `~/.claude/filedrop/<token>/` while its server is `failed` and `ss -tln | grep :878x` box-wide shows only the race WINNERS — a per-user store/server mismatch, never a missing file.
- **An `our_active` "trust our own port, skip the bind-test" shortcut in a per-uid port chooser MUST distinguish "the port OUR live service holds" from "a port a FOREIGN instance holds" — a bind-test reads BOTH as EADDRINUSE, so a blind `if our_active: return want` re-introduces the 404 during the old→new fleet MIGRATION** (#493 review MAJOR, caught by a fresh-context adversarial reviewer, invisible to a green suite): an account whose live service sits on a legacy port while a foreign account holds `want` would bake a `want` it cannot bind → restart fails → dead service → `share` still advertises `want` → 404 off the stranger, non-self-healing. Fix: read our unit's own baked `FILEDROP_PORT` (`_filedrop_current_served_port` via `systemctl show -p Environment`) and treat a port as SERVEABLE iff `port == served OR _filedrop_port_bindable(port)` — apply that ONE predicate uniformly to persisted/want/probe, and fail-safe to `served` (persisted so share agrees) rather than a foreign `want`. Test-teeth trap in the SAME fix: the share-side `PORT = ... or default_port_for_uid()` wiring is a TAUTOLOGY on the uid-1000 push box (both terms equal 8788), so a behavioral test can't catch a mutation reverting it — lock the WIRING structurally (`inspect.getsource`, assert the `PORT =` line names `default_port_for_uid`).

- **A `{{PLACEHOLDER}}` that is a SUBSTRING of another (`{{HOST_IP}}` ⊂ `{{HOST_IPS}}`) must be `.replace()`d LONGEST-FIRST** — substitute `{{HOST_IPS}}` before `{{HOST_IP}}`, or the shorter replace corrupts the longer one into `<value>S}}`. Discovered wiring the file-drop unit's multi-interface bind list (2026-07-10, filedrop multi-iface commit). Locked by `test_render_unit_bakes_the_bind_list` (`assertNotIn("S}}")`).
- **An HTML/JS page served RAW (`PAGE.encode()`, NOT `.format()`) must have SINGLE braces, never doubled `{{ }}`.** A page string moved out of a `.format()` context keeps its `{{`/`}}` escaping, which then renders LITERALLY in the browser and silently breaks all CSS/JS. Grep a served template for `{{` after any move; assert the SERVED bytes (not the source) have no `{{`. Hit live: `filedrop/upload_server.py` PAGE had 24 doubled braces after the `git mv` from meeting-analysis (david@gk found it live testing #18, 2026-07-10). Locked by `test_served_page_has_no_escaped_brace_leak`.
- **An endpoint on a box with a PUBLIC IP (gatekeeper) must bind PRIVATE interfaces individually, never `0.0.0.0`** — especially a WRITE endpoint whose only auth is an unguessable token. `filedrop.bind_ips()` is the single source of truth (tailscale + RFC1918, interface-aware, public/loopback/docker excluded); verify with `ss -tlnp` that the public IP is absent from the listen set.
- **`host_ip()` is NOT a second selection — it delegates to `bind_ips()[0]` (#438).** Two parallel enumerations of "which address to use" WILL drift: `host_ip()` used to walk `_ordered_ips()` with a CIDR-only, interface-BLIND `_is_private` filter, so a `10.88.*` `cni-podman0` bridge (RFC1918, so it passed) was returned even though `bind_ips()` drops it BY INTERFACE NAME (`_VIRT_IFACE`) and the server never binds it — a URL / health-probe target pointing at nothing (the #434-review residual). Fix: `host_ip()` = `FILEDROP_HOST` override, else `return bind_ips()[0]` — `bind_ips()`'s `_bind_priority` order (tailscale → `10.77.*` → other private) is identical to the old three loops, it is interface-aware, and it is guaranteed non-empty (`out or ["127.0.0.1"]`) so `[0]` never raises. Whenever a "primary address" and a "bind list" are computed separately for the SAME machine, make the scalar the list's head, never a parallel filter. The 4 `TestHostIp` tests then need `_iface_ips = lambda: []` in `setUp` (the exact `TestBindIps.setUp` pattern) — without it, `bind_ips()` calls the REAL `ip -o -4 addr` subprocess first and the box's live interfaces leak past the `_ordered_ips` mock, breaking hermeticity on a real dev box. Mock the low-level enumeration PRIMITIVES, never `bind_ips()` itself (that turns the test into a tautology that never exercises the delegation). Locked by `TestHostIpDelegatesToBindIps` (two independent revert-kills: the podman-bridge interface-drop + a no-tailscale `_bind_priority` alignment).
- **A greyed CC UI placeholder (e.g. "Press up to edit queued messages") renders through the SAME `❯ <text>` boundary shape as a real user draft — normalize it at the ONE shared resolver (`_find_boundary_line`), never in each caller.** #65/#67: every keystroke-sending job (`_has_free_prompt`, `_input_line_text`, `_classify_boundary`) already funnels through `_find_boundary_line`; patching the normalization there (strip the exact placeholder text down to a bare `❯`) fixed all three callers in one place instead of three parallel patches that could drift. Reuse this pattern for any FUTURE CC UI hint text that might get misread as user content.
- **Claude Code COLLAPSES a long literal `tmux send-keys -l` into a single `[Pasted text #N]` row instead of rendering the text — so every "did my keystrokes land" check that matches the typed text (`text.endswith(_input_line_text(cap))`, the shape `deliver_with_stash` has always used) can only ever pass for SHORT payloads.** Live-hit shipping #76's job 20: a 3152-char `/goal` re-arm really did land in the box and was refused twice as "not verified", so the goal was never submitted. Use `_typed_landed(text, itext)` (accepts the literal tail OR the placeholder) for any long delivery, and note the two RENDER RACES around it, which are separate bugs from the placeholder itself: the box does not fill INSTANTLY after `send-keys -l` (a multi-KB paste needs a beat to ingest — an immediate capture shows a bare box and reads as a failed type) and it does not clear INSTANTLY after `Enter` (an immediate capture still shows the placeholder and reads as a SWALLOWED submit, firing a corrective `Escape`+`Enter` into a turn that has just started). Both need the same bounded settle poll (`_await_typed`, returns the moment the box agrees) — never a blind sleep, and a type that genuinely never appears must still be refused rather than submitted truncated.
- **A refused Stop is recorded as a top-level `user` entry whose string content starts with `Stop hook feedback:` — that prefix is the ONLY durable rejection signal, and `stop_hook_summary.preventedContinuation` is NOT one.** Measured across all 94 local transcripts (#109, 2026-07-27): 20,257 `system`/`stop_hook_summary` entries, `preventedContinuation` is `false` on every single one — it never reports a rejection, so any detector built on it reads "accepted" forever (this sharpens the earlier warning above, which only said not to use it as a *goal-resolved* signal — the field is useless for the *accept/reject* question too). Each blocking hook contributes its own feedback entry as it returns, so the entry for an EARLIER hook in the same Stop batch is already on disk when a LATER hook in that batch runs — which is the only reason an enqueue-time "was this boundary already refused" gate is possible at all. It makes the Stop-hook ORDER in `settings/hooks.json` load-bearing: `notify-compact-request.sh` USED TO need to stay after every `stop-check-*.sh` gate for exactly this reason (pinned by `TestCompactHookRunsAfterTheStopGates`). A hook that runs LATER than ours — the session-scoped `/goal` hook does, ~5 s later, and it DOES block Stops — is structurally invisible to such a gate; say that rather than implying full coverage. (#400, 2026-08-12: `notify-compact-request.sh` is now a permanent no-op with no enqueue-time gate left to protect — the ordering lock survives as a harmless historical invariant on an inert placeholder, not because it still matters functionally.)
- **A non-daemon background thread in a short-lived CLI silently converts every `sys.exit(msg)` into a delayed exit 0 — `threading.Timer` inherits `Thread.daemon = False`, and CPython joins every non-daemon thread before the interpreter can finish.** #114 (`filedrop/upload_server.py`): the TTL self-shutdown timer was armed 150 lines above the bind loop, so when nothing bound, the `SystemExit` raised by `sys.exit("upload: no address …")` was parked for the whole TTL and the timer's own `os._exit(0)` ended the process instead — a server that bound nothing and served nothing reported **success** to its caller (6.06s/rc=0 at ttl=6, vs 0.07s/rc=1 at ttl=0). Any `Timer`/`Thread` a CLI arms for housekeeping (TTL expiry, watchdog, heartbeat) must set `daemon = True` — it changes nothing while the process is meant to live (a daemon thread is only killed AT interpreter shutdown, which never comes while `serve_forever()` holds the main thread) and it stops the thread from outvoting the main thread's exit status.
- **A "is this resource free?" probe must ask on the SAME addresses the real operation will use — a probe set disjoint from the bind set is blind 100% of the time, not occasionally.** #115: `cmd_upload` scanned for a free port with `connect_ex(("127.0.0.1", cand))` while `upload_server.py` binds exactly `filedrop.bind_ips()` — which `_is_private` EXCLUDES loopback from, and which never contains `0.0.0.0` because a WRITE endpoint must not listen on a box's public IP. So a fully live endpoint answered on none of the addresses the scan asked about: five listeners on `:8799` and the scan still returned 8799, after which the second `airuleset.py upload` bound nothing and its readiness probes hammered the FIRST server with the NEW token (`"GET /<new-token>/" 404` ×20, written into the other endpoint's log). Replace a connect probe with a BIND probe over the operational address list (`_pick_free_port(ips, ports)`): it answers the server's own question, sees a socket that is bound-but-not-listening, and needs no per-address timeout budget for an unroutable IP. Two details that make it match the server rather than merely resemble it — set `SO_REUSEADDR` (mirrors `HTTPServer.allow_reuse_address`, and with it a live LISTEN still yields `EADDRINUSE`), and reject a candidate ONLY on `EADDRINUSE`: `EADDRNOTAVAIL` from a stale/departed interface must be tolerated, because the server itself skips such an address and requires just one success, so treating it as "occupied" would let a single stale IP reject all 21 candidates on a box that serves fine.
- **A test-file constant spelled `TOKEN = "<literal>"` trips `block-sensitive-staging.sh` — the KV_PAT gate reads it as a real credential assignment.** The pattern is `(password|passphrase|secret|token|api[_-]?key)[ \t]*[=:][ \t]*(['"])[^'"$<{\n]{8,}\2`, matched case-INSENSITIVELY, so a perfectly innocent `TOKEN = "toktoktoktoktok116"` in a test class is indistinguishable from a leaked one; `is_placeholder()` does not save it either, since a repeated-syllable fixture is not `(.)\1{3,}` filler. Every earlier test in `test_upload_url.py` passed its token INLINE (`_serve(self, "toktoktoktoktok27", …)`), which is why the gate had never fired here before. The harness reports it as the opaque `PreToolUse:Bash hook error: … No stderr output` (the hook really exited 2 with its reason on stdout — same shape the B64_PAT CamelCase bullet above describes). Fix by RENAMING the attribute (`TOK = …`) exactly as that bullet renames an identifier, never by reaching for `# airuleset:secret-ok`: the bypass is for content that genuinely cannot be renamed, and a test fixture always can. Diagnostic note: reproducing the block by hand is awkward because any diagnostic command containing the literal `git add`/`git commit` re-triggers the same hook on ITSELF — build the payload with the Write tool and run `bash hooks/block-sensitive-staging.sh < payload.json`, and keep git verbs out of the diagnostic's own command line.

- **`filedrop/upload_server.py`'s filename handling is a SECURITY boundary, not cosmetics — and the decode is scoped to ONE segment on purpose (#116).** `unquote()` is applied to the filename segment inside `do_PUT`, never inside `_parts()`: `_parts()[0]` is compared against `TOKEN`, which is this write endpoint's only auth, so decoding it too would let `%74ok…` authenticate as `tok…`. `safe_name()` is a KEEP-list (Unicode L/M/N + `" ._-()"`), so separators, NUL, C0/C1 controls and the whole Cf class (U+202E extension spoofing) are excluded by construction rather than by a blacklist; NFC normalisation comes FIRST because a macOS-origin name arrives decomposed and the combining accent would otherwise be a separate codepoint. Three things a character filter structurally cannot see, each needing its own guard: `..` (dots are legal in a filename, and `os.path.join(DEST, "..")` is DEST's PARENT), a leading `-` (reads as a flag to whatever CLI touches the file next), and length (ext4 caps a NAME at 255 BYTES and the stream lands on `<name>.part` first — 400 Slovak characters are 800 bytes, so the clip must count bytes, not characters). Do NOT "simplify" this by reusing `filedrop.share.safe_name`: that is the DOWNLOAD direction's sanitizer and `filedrop/server.py:20` pins the download URL's name alphabet to its ASCII output — and `upload_server.py` is launched by PATH, so `sys.path[0]` is `filedrop/` itself and `import filedrop` raises ModuleNotFoundError.

- **`PAGE` in `filedrop/upload_server.py` must stay a self-contained single string — an icon/asset goes INLINE, never a route.** #117 removed the `GET /favicon.ico` 404 by declaring `<link rel=icon href="data:image/svg+xml,…">`, so the browser never issues the root request. Answering that path instead would mean an **unauthenticated** route on a WRITE endpoint whose only auth is the path token (a favicon request carries none), and a file on disk would be install-location dependent because this module is launched BY PATH (`sys.path[0]` is `filedrop/`). The companion lock `test_favicon_path_is_still_refused_by_the_token_gate` pins that `/favicon.ico` keeps 404-ing — assert the page's SERVED BYTES, never the `PAGE` source string, or the test stops being about what a browser receives.

- **`gh api graphql`'s `{owner}`/`{repo}` placeholder expansion works ONLY through `-F`/`--field` (typed), NEVER through `-f`/`--raw-field` (string) — confirmed empirically, both ways, before writing #230's fix.** `gh api graphql -f query='...' -F owner='{owner}' -F name='{repo}'` resolves from the cwd's git remote with no extra `gh repo view` call; the identical invocation with `-f owner=... -f name=...` returns `Could not resolve to a Repository with the name '{owner}/{repo}'` every time (a mutant this exact swap survived 12/12 tests until the assertion was fixed — see the next bullet). Note this is the OPPOSITE of what the flag names suggest at a glance ("raw" sounds like it should pass through literally) — `gh api --help` is the ground truth: `-F/--field` = typed parameter, `-f/--raw-field` = string parameter. Reuse `-F` for any future `gh api` call that needs `{owner}`/`{repo}`/`{branch}` resolved from context.
- **A test asserting a flag/value PAIR must check they are ADJACENT in argv, not merely that both appear somewhere in the command.** #230's own first test only asserted `"-F" in args` and `"owner={owner}" in joined_string` separately — a mutant that fully swapped `-F`↔`-f` between the query and the two placeholders (the exact "backwards" shape a typo would produce) passed all 12 tests untouched, caught only by a fresh-context adversarial review that built the mutant and ran the suite against it. Fix: `self.assertEqual(args[args.index(placeholder) - 1], "-F")`. Same family as this file's existing `blocked()`-helper and `count_hook_blocks` traps — presence is not pairing, and the review's own recipe (copy the source, apply ONE targeted `str.replace`, assert the mutation actually changed something, run the suite, restore) is worth reaching for on any argv-shape claim before trusting it.
- **A Fable/Opus adversarial-review dispatch given a DETAILED PROSE digest (root cause, chosen approach, exact commit SHAs, function names to read) instead of a literal pasted diff still works correctly — it re-derives the diff itself from the named commit range in one cheap `git log -p`/`git show` call, which is a legitimate, bounded ADVISOR-shape read, not a "re-read the whole repo" violation.** #266/#177: the dispatch prompt for this review accidentally sent a literal `PASTE_DIGEST_HERE` placeholder instead of the intended pasted diff (an authoring slip, not by design) — the reviewer read the real source via the named function names + `git show`/`git log -p` on the four given commit SHAs anyway and produced a complete, well-evidenced report (0 CRITICAL/0 MAJOR/4 MINOR/3 THEORETICAL, all with file:function locations and mutation-proven test teeth). - **Bake a per-BOX config constant (`MANAGED_MODEL`, `REPO_DIR`, …) into the `CAVEMAN_SHIM_CONTENT` embedded shim at RENDER time via a `{{PLACEHOLDER}}` + `render_caveman_shim().replace(...)`, never via a per-render lazy `import airuleset` inside the segment function — the render path executes on EVERY prompt of every session.** #133 MINOR-1, measured (7 fresh interpreters, median): `import statusbar` alone 44.3ms steady-state / 79.8ms cold; adding `import statusbar, airuleset` 57.4ms / 167.3ms — airuleset.py is normally run as a script (`__main__` never writes a `.pyc`), and `push` rewrites the file on every deploy, invalidating any cache that did exist. Keep the lazy-import fallback (`_managed_model()` here) ONLY for callers that genuinely don't have the baked value available (CLI/test callers of the segment function directly) — the render path itself should never touch it.
- **Dispatching a fresh-context adversarial review with a digest that literally contains an un-substituted placeholder (`PASTE_DIGEST_HERE`) still degrades gracefully — but the reviewer will ALSO independently re-derive facts from the LIVE box rather than trusting only the diff text, and can find something the diff-reading pass alone would have missed.** #279's dispatch accidentally sent the placeholder instead of the pasted diff (an authoring slip); the reviewer re-read the two real commits via `git show` per the fallback instruction already baked into the prompt (see this file's earlier #266/#177 entry on the same shape) AND, unprompted, independently re-checked dev1's own live `claude plugin list` + marketplace `.git` state and reproduced the fix's self-healing claim end-to-end in an isolated scratch `CLAUDE_CONFIG_DIR` profile — catching the false per-box enumeration (previous bullet) that a diff-only read could never have caught, since the false claim was about LIVE FLEET STATE, not about the code. When dispatching a review of a fix whose comments assert facts about the live fleet, explicitly ask the reviewer to independently re-verify at least one of those facts live rather than trusting the diff's own prose — this is a stronger, more general instruction than merely "give it a digest".

- **A GraphQL-batched "did this candidate set ever/last carry label X" test whose fixture stub answers with an UNRELATED value (a different user, a placeholder string) passes regardless of whether the bounding/guard logic under test is even present — mutation-test EVERY such guard by making the stub answer with the ACTUAL identity the test computes (`getpass.getuser()`, not a hardcoded stranger).** #191 MAJOR M5: two Part-B statusbar tests used `"stream:whoever"`/`"stream:x"` as their GraphQL stub's answer while asserting "the count must stay 0" — since the stub never matched anything the test's own identity, deleting the bounding checks they existed to guard (the current-owner skip, the own-account slice-shape skip) left both tests green. The fix, and the reusable pattern for any future stub of this shape: make the fixture's fake response carry the SAME value the test computes for its own assertion (here, `"handed-by:%s" % getpass.getuser()`) — only then does removing the guard actually change the observable count, which is what a mutation (backup, targeted `str.replace`, confirm the paired test now fails, restore) proves directly rather than by inspection.
- **A test fixture's `if "view" in j: return <title/labels shape>` classifier for a fake `gh` call is a substring-collision trap this repo's OWN `MAINTAINER_ACTION_LABELS` vocabulary walks straight into — `"ready-for-review"` LITERALLY CONTAINS the substring `"view"` ("re-**VIEW**").** #382: extending `TestRunCardRemainingScopedToStream`'s fixture to also union in `_obligation_quals()`'s new `label:ready-for-review` qual made that qual's OWN query get misclassified as the `gh issue view` title/labels lookup — it silently returned the placeholder string `"T"` instead of a JSON array, `json.loads("T")` raised inside `_union_open_issues`, and the whole union came back `failed=True` even though the OTHER two per-qual calls (core, needs-gatekeeper) had genuinely succeeded and populated `seen` correctly — the symptom looked like a total failure ("ostáva" line missing entirely from the rendered card) rather than the wrong-branch mismatch it actually was. Fix: match `gh issue view` by ARGV POSITION (`len(a) > 1 and a[0] == "issue" and a[1] == "view"`), never by a substring on the space-joined command text — the SAME "mention vs use" discriminator this file already documents for hook-level command classifiers (`block-vault-store-read.sh`'s path-prefix anchoring, `_is_ssh_auth_failure`'s argv-shape check), just recurring one level down in a Python unit-test's own mock. Any future `_gh_out`/`gh` test fixture in `tests/test_authority_profiles.py` or `tests/test_airuleset.py` that checks `"view" in j` on the joined-args string is one `label:ready-for-review` qual away from this exact silent misclassification — grep for the pattern before adding a NEW qual to `_obligation_quals()`/`MAINTAINER_ACTION_LABELS` that might introduce another "view"-containing word (e.g. any future label containing "preview", "overview", "interview").
## Size ratchet — growth-only file/function size cap on airuleset's own source (#404 point 1)

airuleset enforces a ~1000-line/file cap on TARGET repos (`architecture-first.md`) but
had nothing enforcing it on itself — `watchdog/__init__.py` and `airuleset.py` grew
unboundedly across every ticket, with no mechanical stop. `scripts/size_ratchet.py` +
`tests/size_ratchet.json` + `tests/test_size_ratchet.py` (#404) close that gap, narrowly:
a GROWTH-ONLY cap, "the same discipline we require of targets, applied to ourselves."

**What it does.** `tests/size_ratchet.json` snapshots TODAY's exact line count for every
tracked file (repo-root `*.py`, `watchdog/**/*.py`, `notify/**/*.py`, `filedrop/**/*.py`,
`burn/**/*.py`, `tests/*.py` — deliberately NOT `hooks/*.py`/`scripts/*.py`, out of the
ticket's own explicit scope) and every function currently >=200 lines (via `ast`, keyed on
a stable qualname like `Class.method`/`outer.<locals>.inner`, never `path:lineno` — an
unrelated edit shifting a function's start line elsewhere in the file must never look like
growth). `tests/test_size_ratchet.py::TestCurrentTreePassesTheShippedSnapshot` — a
`unittest.TestCase`, genuinely collected by `cmd_push`'s `unittest discover -s tests` gate
(unlike a bare pytest-function file) — is the actual gate: it is PURE READ, comparing a
fresh `measure()` against the committed JSON; growth past a stored ceiling (or past the
flat default for a brand-new, untracked item — `FILE_DEFAULT_CEILING=1000`,
`FUNC_DEFAULT_CEILING=300`) fails with an actionable "split before it lands" message.

**This is DELIBERATELY strict, by the ticket's own literal wording** ("kazdy subor a
kazda funkcia moze len klesat alebo stagnovat" — every file/function may only decrease or
stagnate): once tracked, an item has ZERO headroom even if it is well under the default
cap — not "may grow up to 1000 lines like a target repo's file would", but frozen at
EXACTLY today's size. A fresh-context adversarial review flagged this as a CRITICAL
finding ("blocks ordinary development on day two — adding one test to any existing
`tests/*.py` file is enough") and it is a correct, deliberately-accepted characterization
of the design, not a bug: the whole point of "okamzita zastava rastu" (immediate growth
stop) is that further growth in an ALREADY-oversized file requires either shrinking
elsewhere in the same commit, or a HUMAN hand-editing one number in the JSON with the
reason stated in the commit/PR message (JSON has no comment syntax) — a visible,
reviewable diff, never a silent default. Loosening a ceiling through any automated path
(the test itself, `--update`) is structurally impossible.

**Tightening is an EXPLICIT command, never a test side-effect.** The dispatch instructions
for #404 offered two equally-valid designs — "the test itself auto-rewrites the JSON on
every run when it improves" vs "an explicit regeneration path" — and the SECOND was
chosen: a test silently mutating committed source as a side effect of an ordinary
`pytest`/`unittest discover` run (including inside `cmd_push`'s OWN fail-closed gate,
which runs against the exact working-tree state about to be pushed) was judged too
surprising and blurs "did the suite pass" with "did it also rewrite a file." Tightening
after a genuine shrink:
```
python3 scripts/size_ratchet.py --check    # read-only, same comparison the test runs
python3 scripts/size_ratchet.py --update   # min(stored, current) per item — tightens on
                                            # shrink, NEVER raises an existing ceiling
                                            # even if current > stored (a violation is
                                            # never silently "fixed" by loosening); refuses
                                            # (no write) a brand-new item already over its
                                            # own default cap
```

**`--bootstrap` (only with `--update`) is the ONE-TIME seed-from-scratch act** — every
tracked item captured at TODAY's real size VERBATIM, with NO default-cap refusal (the
default-cap refusal is a GOING-FORWARD policy for a genuinely new item appearing AFTER a
real baseline already exists, never the baseline itself). A fresh-context adversarial
review live-reproduced that the FIRST shipped version was not actually one-time at all —
re-running `--update --bootstrap` against an already-seeded snapshot silently blessed a
brand-new 9000-line file at full size with zero refusal, since bootstrap mode's own
per-item loop never checked whether the snapshot already had anything in it. Fixed by
refusing the WHOLE operation outright (nothing written at all) whenever `--bootstrap` is
combined with a non-empty stored snapshot, enforced at BOTH `regen()` (so a direct/test
caller is protected too, not just the CLI) and `main()` (so the CLI never even attempts a
write) — the general lesson: a flag whose docstring/help-text calls itself "one-time" is
not actually one-time unless something checks the PRECONDITION "is this genuinely the
first time", not just the flag's own presence.

**Known, deliberately-accepted residual: a same-commit rename+grow can regain headroom.**
Because the snapshot is keyed by path/qualname (not content or git rename-tracking),
renaming a tracked file/function in the same commit it grows lets the growth land as a
"brand-new item" governed by the flat default cap, rather than by the old, possibly-much-
tighter ceiling — an inherent limitation of any name-keyed ratchet without semantic rename
detection. Flagged as a MAJOR finding by the same adversarial review; deliberately left
unfixed as out-of-scope for this narrow, mechanical point-1 test (semantic rename-tracking
is real complexity that belongs to a separate, bigger investment) — grep this file's own
existing "accepted residual" precedents (#124, #331 F3/F4) for the established shape of
documenting rather than chasing a low-practical-severity gap in a trusted-developer
environment.

**How a TARGET repo adopts the same template.** The mechanism has no airuleset-specific
dependency beyond stdlib (`ast`/`json`/`argparse`/`tempfile`) — copy `scripts/size_ratchet.py`
verbatim, adjust `TRACKED_DIRS` (and the repo-root/`tests/*.py` glob shape in
`tracked_files()`) to that repo's own module layout, copy the `unittest.TestCase`-based
gating class from `tests/test_size_ratchet.py` (`TestCurrentTreePassesTheShippedSnapshot`
is the load-bearing part; the rest of that file is testing the MECHANISM itself and only
needs porting if the target wants the same depth of self-test), then run
`python3 scripts/size_ratchet.py --update --bootstrap` ONCE to cut the day-one snapshot
and commit it. `FILE_DEFAULT_CEILING`/`FUNC_DEFAULT_CEILING`/`FUNC_TRACK_THRESHOLD` are
free to retune per target (this repo's own 1000/300/200 mirror the standard already
enforced fleet-wide, e.g. camera-box #234's own driver.rs cap) — the assert pinning
`FUNC_TRACK_THRESHOLD <= FUNC_DEFAULT_CEILING` must hold or a freshly-bootstrapped
function between the two values would fail check() on day one, which a ratchet must never
do.

**The module split this ratchet exists to eventually force** (points 3-4 of #404 —
`watchdog/__init__.py` → per-service modules, `airuleset.py` → per-CLI-area modules,
`run_once()` → a job-registry dispatch) is explicitly OUT of this ratchet's own scope and
lands separately, after #403 (goal-machinery collapse) shrinks the file further first. The
ratchet's whole job until then is simply: stop the wound from getting deeper.

- **airuleset.py splits (#433 H/K) live in a DIFFERENT import topology than the watchdog package splits — the script runs as `__main__`, so a new sibling module referencing anything back in airuleset.py at ITS OWN module level is a guaranteed CLI-mode crash, and the safe default is a FULLY SELF-CONTAINED leaf.** Trace of the crash shape (worked out at design time, #433 cluster H/K design comment): `python3 airuleset.py` executes the file as module `__main__` → the facade `from cli_vault import ...` starts cli_vault's init → a top-level `from airuleset import REPO_DIR` there finds NO `airuleset` in sys.modules (the running instance is registered as `__main__`, not `airuleset`) → Python imports airuleset.py a SECOND time as module `airuleset` → ITS facade line re-enters cli_vault, which IS in sys.modules but mid-init with the target name not yet bound → `ImportError: cannot import name ... from partially initialized module`. This is the C/D circular-import hazard (entry above) wearing script-topology clothes. The clean resolution used for both #433 airuleset clusters: make the leaf self-contained by (a) moving a needed helper IN and facade-re-exporting it back for the resident caller (`_pick_free_port` → cli_vault.py, re-exported for `cmd_upload`'s bare-name call — the proven cards.py `_git_*` reverse-arrow shape), and (b) duplicating a one-line canonical path const (`REPO_DIR = Path(__file__).resolve().parent` in cli_vault.py — same directory, identical value; `CLAUDE_DIR = Path.home() / ".claude"` in cli_autopilot_lock.py — the exact expression watchdog/goal.py + watchdog/compact.py already inline locally). Deferred `import airuleset` inside function bodies DOES also work here (module level of airuleset.py is pure: docstring + idempotent filedrop try-import + `__main__` guard — verified by AST), but in CLI mode it triggers a full second module-instance execution and it cannot cover a coupling that lives in a module-level CONST VALUE at all — reserve it for clusters whose coupling is genuinely many resident FUNCTIONS (C/D class), never pay it for a one-line const.
- **`hooks/block-sensitive-staging.sh` refuses to stage ANY filename containing "secret" or "credential" (substring, line 117) — a module split of the secret/vault CLI cluster cannot be named `cli_secrets.py`, period.** Hit live on #433 cluster H's first commit attempt; renamed to `cli_vault.py` (the domain's other established name — filedrop/vault.py, vault_server.py, tests/test_vault_*.py). Do NOT reach for the `# airuleset:secret-ok` bypass for a permanent filename — every future stage of that path would need it again; the hook constraint is a naming constraint, treat it as one at design time.
- **A vault secret NAME (`airuleset.py secret request/exec/forget <NAME>`) must match `filedrop/vault.py`'s `NAME_RE = ^[A-Za-z_][A-Za-z0-9_]{0,63}$` — underscores only, NO hyphens (it doubles as an env-var name; `check_name` exits 2 before doing anything on a hyphen).** #443 (the cloudflare-api-tokens skill) shipped a first draft telling sessions to run `secret request cloudflare-<project>` with a HYPHEN — it would hard-fail on its own example; caught only by the fresh-context adversarial review, not by validate/ratchet/tests (none exercise the vault CLI's name check). When a doc/skill/command names a secret, the vault NAME is underscore-only (`cloudflare_spinbike`), while the ON-DISK `~/.secrets/cloudflare-<project>` file and any third-party dashboard label keep their natural hyphens — three different naming contexts, easy to conflate into one. Related same-area trap: `hooks/block-vault-store-read.sh` matches the guarded credential-store path even when it appears only as a PROSE MENTION inside a Bash command — a `gh issue comment` heredoc body that merely NAMES that path (e.g. to say a skill does NOT use it) gets the whole `cat` denied; reword to avoid writing the literal guarded path in any Bash command text.
- **A janitor-PRIVATE constant referenced only by the moved cluster can be LEFT resident (deferred-read as `watchdog.<CONST>`) rather than moved, when the ticket scopes the cluster to functions only and moving the constant would drag in a fresh counter-coupling.** #433 cluster C kept the 4 `JANITOR_*` tuning constants resident (5 of its 16 `watchdog.` back-references) even though nothing but the 7 moved functions uses them — the adversarial reviewer flagged this as a MINOR cohesion nit and it was DROPPED with reasoning (#311): the ticket names cluster C as exactly the 7 functions, the constants sit non-contiguously (separated from the functions by two non-cluster helpers), and pulling the adjacent `_looks_like_own_stuck_content` helper along would need `watchdog._PASTED_PLACEHOLDER_RX` back — moving the coupling, not removing it. Relocating just the 4 constants into the leaf is a valid cohesion follow-up for a LATER cluster (e.g. D if it touches the same region), never a blocking defect. The general rule: a private-const-left-resident is a defensible, explicitly-documented cohesion trade, not a bug — do not expand a verbatim-functions-only cluster's scope to chase it, and do not file a gate-less follow-up ticket for it.

- **The moment a CLI/job path starts writing a DURABLE marker where it previously wrote none, every test that reaches that path must isolate the marker store (`notify._claude_dir`) — the #141/#385 lesson recurs the instant a new terminal-skip/dedup marker is added.** #474's `_notify_run_card` content refusal now writes a `refused#<name>#<issue>#<fp>` marker (a per-content terminal-skip so an external caller re-firing the IDENTICAL contentless card short-circuits before the gh fetch + re-log — the 3502x/33h x#457 spam). Two fingerprint gotchas the fix also settled: the content fingerprint (`_run_card_content_fp`) must guard `None -> ""` BEFORE `_run_card_norm` (which folds `str(None)="None"` to `"none"`, colliding an absent field with the literal placeholder word "none"), and the `refused#…#…#…` namespace's THREE `#` separators are what keep it collision-proof against the card key `<repo>#<n>` (one `#`, repo names can't contain `#`) and `backfill#<name>#<n>` (two) through `_dedup_path`'s `[^A-Za-z0-9._#-]→_` sanitisation.
