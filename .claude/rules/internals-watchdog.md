## Reading a transcript for TOKEN measurements (#131)


- **A "the SUPERVISOR already handled it, stop nudging" resolution signal keyed on the target's transcript must be CAUSAL — PROVE the specific nudge LANDED (as a `user` turn) AND that a genuine assistant turn FOLLOWED it — never a mere "a genuine assistant turn is DATED after the nudge".** #491 (`_nudge_dying_subagent` / `supervisor_responded_to_nudge`): the dead-subagent nudge (jobs 1b / 4a-sub) re-fired the full `max_nudges` cycle even after the supervisor took over the dead worker and REPLIED to nudge#1, because the detector keyed ONLY on the frozen subagent transcript tail (append-only, stuck on the api-error forever, so it never changes) and never read the SUPERVISOR's own acknowledgement — #287 had bounded the never-recover infinite-nudge#1 case but left the salvageable full-cycle waste, whose only workaround was a 244k-token `SendMessage`-resurrect of the dead agent just to change its tail. The FIRST-CUT fix (a genuine assistant turn timestamped after `nudges[-1]`) was adversarial-review-REFUTED and reproduced: the nudge send is UNVERIFIED (`send_continue`, no submit-verify) AND a `/goal` loop emits genuine post-nudge assistant turns turn-after-turn INDEPENDENTLY of ever seeing the nudge, so a SWALLOWED nudge + one `/goal` re-fire satisfied a timestamp-only check and permanently suppressed BOTH the retry nudges AND the human escalate-ping while the supervisor was still blindly waiting for the worker. The causal fix requires the nudge to appear as a landed `user` turn (CC writes it the instant it ACCEPTS the submit; a swallowed submit writes NOTHING — the same signal `_submit_confirmed`/#490 documents) FOLLOWED BY a genuine assistant response, skipping `isMeta`/`isCompactSummary`/`tool_result` user entries (a `/compact` summary can QUOTE a prior nudge) and `isApiErrorMessage`/`_SENTINELS` responses (a supervisor that itself died on an api-error is job 1's to auto-resume, not an acknowledgement). Reusable rule for ANY future watchdog "the human/supervisor saw it, stop" resolution: prove the SPECIFIC message landed AND was answered — a `/goal` loop's own independent turn-production makes any timestamp-after / "activity happened since" signal a false-positive generator, and pairing that with an unverified send makes the false-positive suppress the very escalation the mechanism exists for. Place the resolution BEFORE the busy/idle branch so a resolved target is silent on BOTH paths; share the match signature with the send builder (`_subagent_nudge_signature`) so the two can't drift; make the state sticky (a `resolved` flag + refreshed `last_seen`) bounded by the existing `SUBAGENT_NUDGE_STATE_TTL_SECONDS`. Test both halves DIRECTLY (a landed-nudge-plus-response resolves; a `/goal` re-fire with NO landed nudge does not; a landed nudge with only an api-error / no response after does not) — a run_once fixture that omits the landed `user` turn silently exercises the wrong path (exactly how #287's marker-gap test masked this).
- **Adopting `send_verified` at a SHORT (<200c) bare-box send site (#497 batch 2 — jobs 1 api-error / 6 session-limit / 7 reply-pointer) is simpler than the batch-1 chunk-typed cross_stream sites — NO two-phase persist and NO janitor prefix — BUT a persist-on-verified-success reorder has ONE trap that BOTH adversarial rounds caught: it can gate an ESCALATION COUNTER on verified-only and make the give-up STRUCTURALLY UNREACHABLE (the #442-F2 class, at a new address).** These three sites persist NOTHING before the send (jobs 1/6 mutate decide/session state in place + run_once saves at sweep end; job 7's `ptr.pop(sid)` is a POST-send one-shot), so the minimal correct change is "record continued/attempts/ping (job 6) or pop the one-shot (job 7) ONLY on a verified True" — strictly SAFER than the old unconditional post-send pop, never a #193 regression. And <200c means the FULL literal is typed, so `send_verified`'s own `_undo_and_release_slot` backs a swallowed send off the bare-verified box — no partial residue, so NO `_JANITOR_OWN_PREFIXES` registration is needed (that is precisely why these three, and not the chunk-typed ones, are batch 2). **THE TRAP (my design got this WRONG for job 6; the review overturned it): when the reorder gates a state field that ALSO drives an escalation counter, the give-up can become unreachable.** Job 6's `SESSLIMIT_MAX_TRIES` give-up counts `attempts`; after "bump attempts only on verified True", a PERSISTENTLY swallowed `continue` (input genuinely wedged, `send_verified`→False every window) never bumps `attempts` → the give-up ping never fires AND `last_try` stayed unset → 60s re-type spam. - **Reading a commit's DATE/age via a per-ref `git fetch origin <ref>` + `git show FETCH_HEAD` on a SHARED main checkout is a DATA RACE — `FETCH_HEAD` is process-global and a concurrent `git fetch` (a human, `session-start-fetch.sh`, or the sweep's own base fetch) clobbers it between the fetch and the read, so a YOUNG tip reads as OLD → a wrong age-based action.** #504 (`watchdog/wip_ref_sweep.py`, the orphaned `refs/autopilot-wip/*` reclaimer, watchdog job 30): BOTH fresh-context adversarial reviewers INDEPENDENTLY found this against the never-delete-a-salvageable-copy invariant (one PoC-reproduced a young unmerged ref getting DELETED). Fix: after `git fetch origin <ref>` (which brings the object local), read the SPECIFIC classified sha — `git show -s --format=%ct <sha>` — NEVER `FETCH_HEAD`; a moved/absent tip returns rc 128 → treat as unknown → fail-safe KEEP. GENERAL RULE for any watchdog git-age read: read the exact sha you're deciding about, never a shared SYMBOLIC ref (`FETCH_HEAD`/`ORIG_HEAD`) that another process mutates. Companion architecture win the reviewers endorsed: make a safety-critical decision a PURE function (facts-in / verdict-out — `classify_wip_ref(sha, ref, merged, age, max_age_s)`) and move ALL git I/O (merged check, local-age read, BUDGETED per-ref fetch) into the caller, so the invariant is a trivially-auditable pure decision a reviewer can attack directly. Two more low-severity findings both worth the reflex on any future reclaimer: (a) an env-override threshold that gates a DELETE needs a FLOOR clamp (`max(env, 1-day)`) — `=7` meaning 7 DAYS reads as 7 seconds and deletes everything (mirror `_repo_sweep_batch`'s own knob clamp); (b) per-repo NETWORK fetches need a BUDGET (`AIRULESET_WIP_REF_MAX_AGE_FETCHES`, past it → KEEP + re-age next sweep) so one heavily-leaked repo can't blow the 120s systemd `TimeoutStartSec` (#172 class).
