- **Reading a commit's DATE/age via a per-ref `git fetch origin <ref>` + `git show FETCH_HEAD` on a SHARED main checkout is a DATA RACE — `FETCH_HEAD` is process-global and a concurrent `git fetch` (a human, `session-start-fetch.sh`, or the sweep's own base fetch) clobbers it between the fetch and the read, so a YOUNG tip reads as OLD → a wrong age-based action.** #504 (`watchdog/wip_ref_sweep.py`, the orphaned `refs/autopilot-wip/*` reclaimer, watchdog job 30): BOTH fresh-context adversarial reviewers INDEPENDENTLY found this against the never-delete-a-salvageable-copy invariant (one PoC-reproduced a young unmerged ref getting DELETED). Fix: after `git fetch origin <ref>` (which brings the object local), read the SPECIFIC classified sha — `git show -s --format=%ct <sha>` — NEVER `FETCH_HEAD`; a moved/absent tip returns rc 128 → treat as unknown → fail-safe KEEP. GENERAL RULE for any watchdog git-age read: read the exact sha you're deciding about, never a shared SYMBOLIC ref (`FETCH_HEAD`/`ORIG_HEAD`) that another process mutates. Companion architecture win the reviewers endorsed: make a safety-critical decision a PURE function (facts-in / verdict-out — `classify_wip_ref(sha, ref, merged, age, max_age_s)`) and move ALL git I/O (merged check, local-age read, BUDGETED per-ref fetch) into the caller, so the invariant is a trivially-auditable pure decision a reviewer can attack directly. Two more low-severity findings both worth the reflex on any future reclaimer: (a) an env-override threshold that gates a DELETE needs a FLOOR clamp (`max(env, 1-day)`) — `=7` meaning 7 DAYS reads as 7 seconds and deletes everything (mirror `_repo_sweep_batch`'s own knob clamp); (b) per-repo NETWORK fetches need a BUDGET (`AIRULESET_WIP_REF_MAX_AGE_FETCHES`, past it → KEEP + re-age next sweep) so one heavily-leaked repo can't blow the 120s systemd `TimeoutStartSec` (#172 class).
