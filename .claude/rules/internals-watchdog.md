The message text was already identical; only the key had drifted, and a green test suite that only counts `len(sent)` never sees it (a fresh-context adversarial review's MINOR finding, live-reachable during that one deploy tick, self-heals after). General rule for THIS repo's dedup work: when adding a new segment to any deployed `dedup_key`, preserve the exact legacy key for whatever value the pre-deploy marker was written under (usually the first/count==1 case), and LOCK the first occurrence's message + key with a test that captures the `dedup_key` kwarg (not just the message), mutation-verified against a revert of the branch — `len(sent)`-only assertions have no teeth on key shape.

- **When a job persists a decision as STABLE-forever based on a verify call (e.g. "this ticket was verify-REJECTED, stop re-checking it"), the verify's own empty result is NOT enough — you must distinguish a GENUINE measured answer from the verifier's OWN failure/degrade sentinel, or you persist a TRANSIENT failure as permanent.** This is a sharper form of the recurring "an empty read means unmeasurable OR genuine-negative" class (#199/#88/#172), now for a PERSISTED decision rather than a one-sweep one. Job 25 `card_reconcile` (`watchdog/cards.py`) gained a persistent `rejected` map (parallel to `pinged`) so a candidate a `closed_fetch` verify rejected is never re-verified/re-logged every sweep — but the load-bearing correctness point is: `_normalize_closed(None)` and `_normalize_closed({})` BOTH yield an empty confirmed set, yet `None` is `_watchdog_closed_fetch`'s documented degrade-sentinel (it returns `None` on `gh returncode != 0`, "degrade to the local answer rather than silence") while `{}` is a genuine measured "nothing merged-closed this window". Fix shape, reusable for any future verify-and-persist: capture the RAW return, set `verify_ok=False` on BOTH a raised exception AND a `None` (unmeasurable) return, and PERSIST the rejection only when `verify_ok` (a genuine measured answer, even an empty dict). A transient failure persists NOTHING, so the finding is retried once the verifier recovers — proven by the boom-verifier regression test (raises) AND the `_watchdog_closed_fetch`-returns-None regression test (gh failure); the two look identical to a `try/except`-only guard, which is exactly why a `None`-specific check is needed alongside it.
