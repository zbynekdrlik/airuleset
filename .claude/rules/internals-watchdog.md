## Reading a transcript for TOKEN measurements (#131)

- **`card-unreported <repo> n=N` (watchdog job 25) is a REPO-scoped metric over the shared tracker, never evidence that THIS box's session is active** — on marek@subdev it read n=29 while the session had produced zero turns for six days (the same stuck candidate set re-verified every sweep); the session-scoped truths are the transcript's own last timestamp and the presence marker mtime (#247).
- **An enrichment step that can UPGRADE a value must respect WHY an earlier step already overrode it — not just consult its own independent evidence class.** #391: `_slice_mine_and_handed`'s comment-fallback walk kept the LAST comment signal in creation order and, if it read True, unconditionally set `handed[n_num] = True` — discarding the EARLIER `prio:bounce` label override (which forces `handed=False` specifically because a bounce means "not actually done") the moment a bounce was applied via a BARE label with no accompanying gatekeeper-shaped comment (the sanctioned Discord nudge-lane bounce shape, `skills/autopilot/SKILL.md`) — a stale pre-bounce READY-FOR-REVIEW comment then silently re-flipped a genuinely-still-open bounce back to handed, a false "nothing left to do" for the reduced-authority `/goal` stop-proof. A fresh-context adversarial review caught it live via a fixture with a comment thread carrying ONLY the stale hand-off (no bounce comment at all) — none of the PRE-EXISTING bounce tests exercised this, because every one of them either had an empty comment list (verdict stayed at its label-derived default) or a comment thread that ALREADY contained a recognizable bounce comment. Fix: track which rows are currently bounce-labeled (`bounce_numbers`), and during the comment walk ALSO track whether a recognized gatekeeper-authored comment (`_comment_readiness_signal` returning `False`) was seen anywhere in the SAME thread (`saw_gatekeeper_comment`) — a bounce-labeled row may only be upgraded to handed when the bounce is itself VISIBLE in the comments (a genuine post-bounce re-hand-off); an invisible bounce (label-only, no comment) fails toward "still unhandled", the safe direction for a stop-proof. General lesson for any future recovery/fallback mechanism layered on top of an existing override: before letting a later signal overwrite an earlier one, ask whether the earlier signal was itself an OVERRIDE with its own justification (here: "this specific ticket was bounced") — if so, the later signal must independently confirm that justification no longer holds, not just win on its own terms.
- **A write-once anchor field for a bounded HOLD/grace window (stamped the first time a block is observed, read back on later sweeps to measure "how long has this been blocked") must also be explicitly CLEARED the moment the block itself lifts — never just left to be silently overwritten or preserved forever like a PRESERVE-across-re-record field (`deferred_since`, `not_boundary_since`'s own preservation logic) legitimately is.** #394-review F1: `not_boundary_since` (job 14's marker-hold grace anchor, #394) was stamped once and then only ever PRESERVED (mirroring the sibling `deferred_since`'s own correct "never reset across a re-record" shape) — but nobody ever cleared it when the marker genuinely recovered (a real boundary again) on a sweep that still didn't deliver for an unrelated reason (e.g. the pane was busy). A LATER, genuinely NEW hold episode then silently inherited the OLD, already-elapsed anchor and could deliver on a hold that had barely started — precisely the outcome the whole grace mechanism exists to prevent. The two field-lifecycle shapes are NOT interchangeable: a preserve-field answers "has this REQUEST ever needed extra time" and correctly never resets; an episode-anchor answers "how long has THIS SPECIFIC ongoing condition persisted" and MUST reset the instant the condition it's timing stops being true, or its later re-arm inherits a stale, already-elapsed clock. When adding a NEW anchor of this second shape, pair the `if not_set: stamp` branch with an `elif blocked_is_now_false and set: clear` branch in the SAME place, and add a dedicated 3-sweep test (hold → recovers-for-an-unrelated-reason → a brand-new hold) proving the anchor value at sweep 3 differs from sweep 1's, not just that delivery/refusal is correct at each individual sweep in isolation — a per-sweep-only test suite can (and did) stay green while the underlying anchor value was already wrong.

- **A NEW function that reads a WINDOW-BOUNDED slice of the SAME transcript file another function already reads with an established window constant must default to that SAME constant (or read the whole file) — never invent its own smaller ad-hoc window.** #393-review MAJOR-1 (independently re-verified, live-reproduced): `_goal_autopilot_reinvoked_after`'s own `tail_bytes=2_000_000` default was SMALLER than `GOAL_MARK_TAIL_BYTES = 4_000_000`, the window `scan_goal_markers` uses to bootstrap the very clear-marker this function was asked to check release evidence FOR — so a genuine release-proving entry sitting 2–4 MB from EOF was structurally unreachable even though the marker referencing it was in view. This is the SAME shape the #173 bullet elsewhere in this file already documents (a "fresh, independent re-derivation" reading only a tail window misses evidence a long-lived, continuously-writing session pushed past it) — the NEW angle worth naming explicitly: the bug here was not "should this read the whole file", it was "two functions reading the SAME file for related purposes silently disagreed about how much of it counts", which is easy to miss because each function's OWN window looks individually reasonable. When adding a function that reads a transcript slice a SIBLING function already scans, grep for that sibling's own tail-window constant and compare numbers before picking a default.
- **An open ALLOWLIST character class (`[ \w()]{0,N}`) sized to reject a KNOWN bad example is not equivalent to matching the actual small, enumerable set of real shapes it exists to recognize — when the real vocabulary is closed and short, write the closed-form pattern instead.** #393-review MINOR-1 (independently re-verified, live-reproduced): `_GOAL_HEADER_INDICATOR_RX`'s first cut (`[ \w()]{0,40}`, meant to reject a wrapped-prose continuation with real punctuation) still accepted 7 of 8 constructed continuations that simply had NO punctuation in their first 40 chars ("◎ /goal armed", "◎ /goal active and the loop keeps going") — the allowlist correctly rejected the ONE reported live incident (which had a comma) while leaving the whole surrounding class of unpunctuated false positives open, because "narrower than before" was mistaken for "narrow enough". The real render vocabulary here is tiny and fully known (bare, " active", " active (Nh/Nm)" for N up to 3 digits) — replacing the allowlist with `( active(\s\(\d{1,3}[hm]\))?)?` closed it against every constructed false positive while still matching every shape this repo's own corpus has ever rendered. Prefer a closed-form pattern over an allowlist whenever the thing being matched has a small, genuinely enumerable real vocabulary — an allowlist is the right tool only when the real vocabulary is itself open-ended.
- **A closed-form pane-render regex tuned to a repo's OBSERVED vocabulary WILL false-negative when Claude Code changes its render — #393 MINOR-2's own "widen only on a live render" clause is a promissory note, and #487 called it in.** gk's armed pane settled to `› stashed · ◎ /goal active (1d)`, breaking `_GOAL_HEADER_INDICATOR_RX` from TWO simultaneous new shapes: CC prepended the stash-slot marker (`STASH_MARKER` + " · ") onto the glyph's own header line (so `^`-anchor missed), and the age crossed to DAY granularity (`[hm]` rejected `(1d)`). The resulting `pane_goal_armed` False killed the #442/#481 lane-fill guard. Three reusable moves when widening such a regex: (1) derive any literal prefix from the repo's OWN constant (`re.escape(STASH_MARKER + " · ")`), never a hand-retyped copy; (2) verify the exact separator by HEXDUMP of the real render, not by eye — the middle dot was U+00B7 (`c2 b7`), trivially mis-typed as `.`/`*`/a plain space; (3) audit EVERY parser of the same rendered line first (`grep` the glyph across `watchdog/` + `hooks/`) — here only the ONE anchored regex needed the widening, because the two other consumers (`cross_stream.py` `"◎ /goal" in captured`, `notify-discord-pending.sh` `grep -qF`) are SUBSTRING checks that tolerate prefix/suffix render-drift for free. Direction rule: a substring `in`/`grep -qF` check absorbs render drift automatically; an anchored regex must be explicitly re-widened, so it is the only shape a render change can silently break. (Secondary #487 finding — the janitor never reclaims a stash parked >6h ago because its provenance mark expires while the parked draft persists — is filed as its own security-boundary ticket, NOT folded here.)
- **A newly-added UNCONDITIONAL gate (e.g. #400 FIX 5's live-tasks skip) must be re-verified against the FRESHEST capture at every send point that already has a "raced since the sweep" re-verify — reusing that existing re-verify, not adding a parallel one.** #400-review MAJOR-1 (live-triggered by the reviewer's own repro): job 14's idle-send and `deliver_compact_now`'s sync-send both already re-captured the pane immediately before typing (the pre-existing #333-review "raced" check) but only re-classified that fresh capture for BOUNDARY kind (input/draft) — never for the NEWLY-added live-tasks signal, so the live-tasks gate one block above still read a capture that could be stale by the actual moment of the send. Fixed by threading the SAME fresh capture (`captured=fresh`) into `_session_has_live_bg_tasks` at both send points — zero extra tmux round-trips. Reusable check for any future unconditional gate added to a file that already has an established "re-verify against a fresh capture right before the irreversible action" pattern: extend that SAME re-verify to cover the new signal, don't assume the older re-verify's scope automatically covers it.

- **A send/delivery function with MULTIPLE branches (e.g. job 14's idle-send vs stash-send) needs its OWN dedicated test coverage per branch for every cross-cutting property — a property proven on one branch is NOT proven on a sibling branch that reaches the same helper calls through a different code path.** #400-review MAJOR-2: job 14's STASH branch (`_compact_stash_attempt`) had zero test coverage for FIX 4's cooldown timestamp-mark and FIX 6's SEND log line, even though the IDLE branch had both locked down — two of the reviewer's own mutations (removing `mark_compact_delivery_ts` from the stash branch; removing its `_log_compact_sync` call) left the ENTIRE existing suite green. When adding a new claim about "every delivery path does X", write a test PER branch that can actually deliver, not one test on whichever branch was easiest to drive.

- **A log-before-the-real-action comment ("logged before anything downstream can throw and swallow the record") must be checked against the ACTUAL statement order, not trusted from the comment text — the same bug can independently exist on multiple branches even after one is fixed.** #400-review MINOR-6: job 14's stash branch wrote its SEND line to `compact-sync.log` AFTER five other calls (`reqs.pop`, `mark_compact_delivered`, `compact_claim_set`, `mark_compact_boundary`, `mark_compact_delivery_ts`) despite its own comment claiming the opposite; `deliver_compact_now`'s independent send point had the identical ordering bug, undetected until fixed for consistency. Grep for the actual line order around a "logged first" claim rather than trusting the adjacent comment.

- **When a caller must decide whether to suppress a SIBLING nudge shape based on "did my own diagnosis apply this sweep", have the callee return an EXPLICIT boolean — never let the caller re-derive it by sniffing the callee's own LOG TEXT for substrings.** #365-review M2 (fresh-context adversarial review, 2026-08-12): job 20's `_goal_lane_occupancy_nudge` used to return only `logs`, and its caller inferred ownership as `bool(lane_logs) and not any("-> occupied" in ln or "no measurable open backlog" in ln for ln in lane_logs)`. That worked right up until the give-up branch's own one-shot ping dedup (`if not rec.get("lpinged"): ... append log`) meant a SECOND-and-later give-up sweep appended NOTHING — an empty `lane_logs` read by the old heuristic as "did not own this sweep", which let the sibling `_goal_stall_nudge` (no subagent-liveness check, no recent-human-activity gate of its own) resume typing "continue" into a session already diagnosed and escalated on. Fix: the function now returns `(logs, owns)`, with `owns` set the instant the diagnosis genuinely applies (both counts known, neither escape fired) and held `True` on EVERY subsequent return path regardless of whether new log text was appended that sweep. Any function whose SIDE EFFECT (what it typed, whether it "claimed" a sweep) a caller needs to know should say so explicitly in its return value — inferring caller-visible state from a callee's own logging is a hidden coupling that silently breaks the moment the callee's logging becomes conditional (a dedup, a rate-limit, a give-up).

- **A "re-capture fresh, right before send" guard (this file's own established `#176-F3` pattern, used whenever a blocking fetch sits between a sweep's stale `captured` snapshot and the eventual keystroke) must re-verify EVERY precondition the ORIGINAL stale check verified, not just the ones that happen to occur to you first.** #365-review round-2 MINOR (fresh-context adversarial re-review of an already-reviewed-and-fixed diff — SAFE TO SHIP AS-IS overall, but this one gap had zero test coverage): the round-1 fix added a fresh recapture that re-checked ONLY at-rest-ness (`_classify_boundary`/`pane_at_idle_prompt`), mirroring `_goal_template_drift`'s pattern by memory rather than by re-reading it — but that sibling ALSO re-checks `pane_goal_armed(fresh) is not True`. The blocking `_cached_backlog_count` fetch can span a whole final turn; if the loop finished and disarmed WHILE it ran, the pane returns to a bare, at-rest prompt (passes the narrower check) but the goal itself is gone, and the nudge would still get typed into a session that should never receive one. When copying an established "re-verify against a fresh capture" pattern from a sibling function, diff your new check against the SIBLING'S actual code (grep it, don't recall it) — a re-check that verifies fewer things than the pattern it's modeled on is a silent regression with no distinguishing symptom until the exact race window is hit live.

- **Adding a NEW "X never blocks the stop" disclaimer to a `/goal` template's PROOF section must be cross-checked against every OTHER clause in the SAME giant single-line template that talks about the SAME evidence — an `assertIn`-shaped test suite only proves each clause is PRESENT, never that two clauses agree with each other.** #384/#395-review MAJOR-1: fork-no-merge's pre-existing REVIEW-WATCH clause said an open hand-off ticket "is NOT done — REVIEW-WATCH: stay alive", while the SAME ticket's own new (B) proof disclaimer said the identical evidence (a nonzero `gk N`, i.e. an open ticket carrying my hand-off comment) "never blocks 🏁" — a direct behavioral contradiction the shipped test suite could not see, because it only ever checked each phrase's presence in isolation (`assertIn("REVIEW-WATCH", fk)`, `assertIn("never blocks", fk)` — both true, simultaneously, for two clauses that disagree). The sibling branch-merge template did NOT have this bug, because its REVIEW-WATCH trigger is scoped to something its OWN proof genuinely enforces ("release still pending", checked by the RELEASED command) — copying that phrasing onto fork-no-merge would have been dishonest, since fork's RELEASED proof cannot see an unmerged hand-off the same way. General check for any future template edit that adds a new "X is/isn't blocking" claim: grep the WHOLE template line for every OTHER place the same underlying fact is discussed, and read them side by side as plain English — a test suite proving each clause exists says nothing about whether they're mutually consistent.
- **`except OSError` is NOT sufficient to catch a broken gzip stream — `EOFError` (truncated compressed data) and `zlib.error` (corrupt deflate stream) are BOTH raised from inside Python's own `gzip`/`zlib` decompressors and are NEITHER an `OSError` subtype.** #410 review F3/F4 (MAJOR, live-triggered both times — claude-history's `_read_jsonl()` AND `_compress_transcript_file()`'s own verify-decompress step had the identical gap): a truncated `.jsonl.gz` escaped uncaught past a bare `except OSError`, crashing with a raw Python traceback instead of the SAME controlled "cannot read" message every other broken-input case in the same function produces. `BadGzipFile` (a bad MAGIC header) genuinely IS an `OSError` subtype and is caught fine by the naive form — which is why a test using bogus, non-gzip bytes (`b"not a real gzip stream"`) never reaches this gap at all; proving the fix needs a REAL, valid gzip stream (`gzip.compress(...)`) TRUNCATED mid-body. Catch `(OSError, EOFError, zlib.error)` (needs `import zlib`) on any code reading a gzip stream whose integrity you cannot fully trust.
- **A "the newest item in this group is protected/excluded" check must compare by the ORDERING VALUE (mtime, timestamp, whatever `sort()` keyed on), never by OBJECT IDENTITY of the item `sort()` happened to place first — a genuine TIE silently protects only the one row `sort()`'s (implementation-defined, stable-but-arbitrary) placement favoured.** #410 review F5 (MINOR, live-reproduced): `discover_old_transcript_candidates()`'s newest-in-directory exclusion did `newest_path = rows[0][1]; if p == newest_path: continue` after an mtime-descending sort — two files last written in the identical wall-clock second (a real, unremarkable occurrence, not an adversarial input) left the SECOND one eligible for compression, directly contradicting the function's own docstring ("the newest... is NEVER a candidate", which for a tie means BOTH are equally "the newest"). Fixed by comparing `mtime == newest_mtime` (the VALUE) instead of `p == newest_path` (the IDENTITY) — this excludes every row tied for newest, not just the first one `sort()` returned. Whenever writing this "protect the extremum of a group" pattern, capture the extremum's VALUE, not a reference to one specific row that happens to hold it.
- **A "fix a MINOR review finding" pass must be checked against ANY existing test that ALREADY locks a stricter, opposite-direction invariant in the SAME function — a fix that reads cleanly in isolation can directly violate a #400-class ("never refresh a stale anchor") lock the reviewer never saw because it wasn't in their digest.** #402-review MINOR-2 proposed resetting `record_compact_request`'s preserved `ts` when the PRIOR entry was already past the age cap (so a genuinely fresh boundary doesn't inherit a corpse) — implementing it broke `test_ts_is_never_refreshed_across_a_re_record` (a PRE-EXISTING, deliberately-locked #400 regression test asserting the anchor is NEVER refreshed "no matter how stale it genuinely is"). Tracing the actual failure mode showed the "gated" reset was a WEAKER form of the exact #400 bug it risked reintroducing: a session producing genuine boundary events more often than `COMPACT_REQUEST_MAX_AGE_S` apart, forever, would keep resetting the anchor just past each expiry and never let the hard age cap fire — an 11-hour-stale request surviving via periodic auto-reset instead of continuous refresh, same shape, slower cadence. REJECTED the fix, reverted the code, and — because `deliver_compact`'s condition (e) is checked FIRST and unconditionally on EVERY sweep (~60s cadence, no pane resolution needed) — the real residual is only a narrow, self-healing window (<=60s) rather than a structural gap: the NEXT genuine boundary event after the sweep clears the dead entry gets a fully fresh `ts` regardless. **When a proposed MINOR fix conflicts with an existing locked test, don't just delete or weaken the test to make the fix pass — trace whether the fix's OWN failure mode reproduces the exact incident the locked test protects against, at a different frequency; if so, keep the lock and document the REJECTED fix's reasoning at the point a future reader would otherwise re-propose it.**
- **A watchdog sweep test that FREEZES `now` across a loop and relies on per-iteration state accumulation silently breaks the moment that sweep gains ELAPSED-TIME throttling (a backoff, cooldown, or park window) — the fix is to ADVANCE the clock past each window per iteration, NEVER to weaken the assertion.** #479: adding `goal_lane_occupancy_nudge`'s stash-abort backoff park (`rec['lnpark']`, staged `120/300/900/1800s`) broke `test_busy_undersaturated_stash_abort_still_reaches_giveup`, which looped 7× on a fixed `now=100000` expecting the abort streak (`rec['lna']`) to reach the give-up cap by iteration count alone; once the first abort parks every subsequent sweep, the streak never accumulates and the give-up never fires. The test's INTENT (a permanently-aborting lane still reaches the ONE give-up ping) was unchanged and still asserted verbatim — only its time model was wrong. Fixed in its OWN commit by advancing `now`/`tmtime` by a step larger than the biggest backoff each iteration (passes on both the pre- and post-#479 implementation, so it is an orthogonal test-model correction, not a weakening). Many goal-sweep tests share this fixed-`now` shape, so any future cooldown/debounce/backoff added to a sweep function should expect to update the clock model of the EXISTING tests, not just add new ones.
- **The request-store `ts`-reset decision is TRANSITION-dependent — a blanket "never reset `ts`" over-generalized from the #402 lesson two lines up would silently re-break a legitimate case (#478 confirmed both halves of the compact pattern on the SIBLING `goal.record_goal_request`).** #402-review MINOR-2 REJECTED resetting `ts` on a SAME-origin automatic re-record past the age cap (the #400 refresh-forever trap). #478 CORRECTLY resets `ts` on an origin UPGRADE (weak `dark-rearm` → strong `self-callback`): that upgrade is a genuinely NEW user request (an explicit `/autopilot`), so it needs a fresh anchor or the user's brand-new arm is judged expired against the stale watchdog anchor within minutes — and it CANNOT drive refresh-forever because each upgrade requires a genuine human action, unlike an automatic re-record. Same store, same field, OPPOSITE correct answer per transition: reset on a weak→strong human upgrade, never on a same-origin automatic re-record. #478 also made `goal.record_goal_request` the SECOND live instance of the #402 origin-downgrade guard (line above: a `dark-rearm` never clobbers a pending non-`dark-rearm` entry) — the pattern is now REPEATED across the two sibling request stores (compact + goal), so any THIRD store or any store gaining a SECOND writer should carry both halves (downgrade-refused + human-upgrade-ts-reset) by default, and its dark/watchdog-initiated origin must additionally honour the recent-human gate + fail-closed on unprovable state (no transcript → `skip:no-transcript`, not a blind keystroke).
- **A function that resolves an expensive resource (a filesystem walk to LOCATE a file, not read it) UNCONDITIONALLY before calling a cheap early-exit check that was ALWAYS going to refuse for most callers anyway is paying for work its own precondition already knows is wasted — gate the resolve on the SAME condition the downstream check gates on, not just on "do we already have it".** #402-review MINOR-3: `_session_has_live_bg_tasks` resolved the transcript PATH unconditionally right before calling `_compact_self_reported_complete(origin, tpath)` — even though that function's own FIRST line refuses any non-self-callback `origin` before ever touching `tpath`. The docstring claimed "the caller never even pays anything" for a non-exempt origin, which was true only for the transcript TEXT read (inside the exemption check itself), not for the PATH resolve one level up. Fix: `if tpath is None and origin == _COMPACT_SELF_CALLBACK_ORIGIN: tpath = _resolve_tpath()` — mirror the downstream check's own precondition at the call site, not just at the point where the value is finally used. Reusable check for any future "the caller never pays for X in the common case" cost claim: trace whether ALL of X's resolution steps are actually gated on the SAME precondition the consumer checks, not just the LAST one before the consumer runs.

- **`scan_goal_markers`'s own correct "only bytes appended since the given offset" incremental contract is WRONG for a caller that wants to know "is the transcript's newest marker STILL X" across MULTIPLE sweeps — CC writes a `Goal set:`/`Goal cleared:` marker exactly ONCE, at the moment it happens, never again while a loop silently runs or dies, so a caller that re-derives its verdict ONLY from each sweep's own (usually empty) delta sees the marker exactly once and then loses it forever.** #403 (`goal_dark_watch`'s own 2-sweep debounce): the off_state originally tracked only `{"off": new_off}`; a second sweep with no NEW appended transcript content got `mark=None` back from `scan_goal_markers`, which the caller's own `if mark is None: <reset the whole debounce>` branch treated as "the marker went away" — so the 2-sweep-before-pinging design could never actually reach its second sweep in real operation. Fix: persist the LAST-KNOWN marker alongside the offset (`off_state[sid] = {"off": new_off, "mark": new_mark if new_mark is not None else prior_mark}`) and fall back to it whenever a sweep's own delta is empty — cost stays the same one-small-incremental-read-per-sweep the function's own docstring promises, since only the BOOKKEEPING widens, not the read. Found by the ticket's own new regression test (`test_debounced_across_two_sweeps_before_pinging`), not by review — a second, independent bug in the SAME test (not passing a SHARED `state=` dict between the two `goal_dark_watch(...)` calls, so each call built its own fresh empty state internally) masked the first one identically; both had to be fixed before the test told the truth. Whenever writing ANY future incremental-`scan_goal_markers` consumer that must answer "is X still true" (not just "did X just happen"), persist the derived FACT, not merely the read cursor — and when testing it across multiple sweeps, thread ONE shared `state=` dict through every call, or the test measures nothing about persistence at all.

- **`deliver_goal()`'s condition ORDER means `pane_goal_armed()` (the tri-state already-armed check) runs BEFORE `_classify_boundary()` (busy/input/no-input-line) — a genuinely BUSY pane (a spinner, no `❯` visible anywhere) is therefore UNDETERMINABLE for the armed check FIRST (no box to read at all), so it resolves to `"skip:undeterminable"`, never `"skip:busy"`, even though `"skip:busy"` is a real, separately-reachable branch in the same function.** #403: a first-draft test asserted a plain busy-spinner fixture reaches `"skip:busy"` and got `"skip:undeterminable"` instead — not a bug, the correct consequence of the documented check ordering (armed-status is resolved before boundary classification, since dropping an already-armed request is cheaper and safer to decide first). To exercise the busy-KIND branch in isolation, mock `pane_goal_armed` to return a determinable `False` directly rather than trying to construct an organic fixture where BOTH `pane_goal_armed`'s whole-capture "❯" scan and `_classify_boundary`'s bottom-up chrome-peel-based box search would need to disagree in exactly the right way (they usually agree, since both ultimately look for the same glyph) — that combination is real but genuinely hard to construct honestly, and mocking the earlier check is the honest way to test the later one in isolation.

- **A symbol SHARED between an already-extracted cluster and a not-yet-extracted one is NOT automatically the same circular-import risk class as a cluster genuinely COUPLED to `__init__.py`-resident code (the C/D finding above) — the direction of the dependency is what decides, and #433 cluster F shows the SAFE direction resolves for free via the SAME facade re-export every earlier cluster already uses.** Cluster F's `merged_closes`/`card_reconcile` call a git-primitive trio (`_default_git_run`/`_git_first_line`/`_git_base_ref`) that is ALSO used by cluster E's `delivery_state`/`_repo_label` (not yet extracted, still resident in `__init__.py`) — the earlier F/C/D investigation comment on this ticket flagged this as needing the SAME `watchdog.`-prefixed deferred-import workaround C/D need. Live-verified it does NOT: moving the trio INTO `watchdog/cards.py` (where F's own new code needs it to run standalone) and re-exporting it back into `__init__.py` via the established `from watchdog.cards import _git_first_line as _git_first_line, ...` facade means every STILL-RESIDENT `__init__.py` caller (`_git_commit_ts`, `delivery_state`, `_repo_label`) keeps calling it as a bare name, resolved through `__init__.py`'s own module globals AFTER the facade import runs — Python's late name binding means source-line ORDER between the facade import and the caller `def`s never matters, only that the import has executed by the time the caller is actually INVOKED, which it always has (module-load completes fully before `run_once()` is ever called). Confirmed empirically: `fn.__globals__ is watchdog.__dict__` True for every one of `_git_commit_ts`/`delivery_state`/`_repo_label`/`run_once`, and `python3 -c "import watchdog"` raises nothing. **The actual test that separates the two classes**: which side of the move needs something from the OTHER side? C/D's hazard is a NEW leaf module needing OLD `__init__.py`-resident symbols (a `from watchdog import X` inside the new module would try to import from a `watchdog` package still mid-initialization — genuinely circular).
