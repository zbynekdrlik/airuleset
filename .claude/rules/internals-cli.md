### airuleset internals — airuleset.py CLI (install/push/plugins)

Staršie/hlbšie airuleset.py CLI (install/push/plugins) lekcie (archív) sú v `.claude/rules-reference/internals-archive.md` (on-demand, bez `paths` — grepni ho). Sem pribúdajú NOVÉ lekcie, kým súbor neprekročí ratchet strop, potom sa najstaršie presunú do archívu.

- **"Never touches an EXISTING session" is not the same claim as "never RESURRECTS a session" — a check gated on has-session alone cannot tell "never provisioned" apart from "a human deliberately killed it".** #263's `ensure_stream_tmux_session` (bootstrap a subdev stream account's tmux session on every `install`/`push`) correctly never touched a session that WAS still alive — but a session a human killed on purpose (out of token budget, done for the day, a VPS reboot) ALSO reads as "doesn't exist" to `has-session`, so the old code would silently re-create it and auto-launch `claude` into it on the very next push. That is exactly the standing, already-recorded user complaint in this file about NOT touching a deliberately-stopped session (see the `feedback_never_touch_stopped_sessions` entry) — just one level up: not "don't type into a stopped pane", but "don't even RE-CREATE a session that once existed and is now gone". General fix shape for any future "provision X if it's missing" job that could plausibly run against something a human deliberately removed: gate the WHOLE decision behind a ONE-TIME-EVER sentinel (a marker file written the MOMENT the decision is made, before acting, so even a failed first attempt never retries) rather than re-deriving "should I act" from current absence on every run.
- **Sizing a "raise this timeout" fix: the new bound must exceed the SUM of every INNER timeout the same call can burn through, not just be "bigger than the old number".** #263's `REMOTE_DEPLOY_TIMEOUT_S` (bounding a single `ssh user@host 'python3 airuleset.py install'` call) was first raised 60s → 300s — better, but still LESS than the real worst case: `check_runtime_deps()`'s `apt-get install` (300s PER missing package) + a new `ensure_claude_cli_installed()` curl-install (180s) + `ensure_playwright_browsers()`'s npx install (300s) — up to ~780s of best-effort network work alone inside ONE remote install, before any of the ordinary steps. On the EXACT scenario the ticket existed for (a fresh account missing both the claude binary and the Playwright cache), the outer bound would still fire first, SIGHUP the remote's own still-running install mid-way, and silently skip every step scheduled after the kill point. Before raising an outer timeout that wraps a call which can invoke several INNER best-effort steps, sum every inner step's own worst-case bound and set the outer one comfortably above that sum — not above the previous outer value.
- **Writing a NEW idempotent marker-block function (bashrc/conf-file add-or-remove-between-markers): use the SAFE positional left-to-right span scan from day one, never the older `START.*?END` lazy-regex shape** — this repo already has BOTH in production: `apply_tmux_history_limit`'s `_clean_tmux_block_spans` (safe, #235's own fix) and `apply_ultracode_launcher` (still the older buggy shape, deliberately left unfixed and tracked as its own follow-up, #237). A new function copying the MORE COMMON existing pattern (`apply_ultracode_launcher`, since it's the one most other code in the file resembles) would silently reintroduce the exact corruption class #235 already found and fixed elsewhere in the SAME file. #263/#264's `apply_stream_ssh_attach`/`_stream_marker_block_spans` used the safe shape from the start — cheap when writing fresh code, and it closes the WORST failure of that class (a stray leftover START silently eating real content up to a LATER genuine block's END). Note the honest residual even the safe scan doesn't close: a single ISOLATED stray start/end pair with no OTHER marker literal between them is structurally indistinguishable from a real block to ANY purely positional scan, and its content IS still lost on rewrite — document that limitation explicitly rather than overclaiming "self-heals" (an adversarial review caught exactly this overclaim in the first draft of both functions' docstrings).
- **A `cmd_install()` step that can now `sys.exit()` needs the SAME "track it, don't abort the loop" treatment `cmd_push()`'s remote-deploy loop already has for its OWN failures — and it is easy to add the exit without noticing the caller never catches it.** #273's adversarial review: `cmd_push()`'s "2. Install locally" step called `cmd_install(args)` in-process with no `try/except` at all; giving `cmd_install()` a new `sys.exit(1)` path (to make a still-failing managed-plugin install a loud, non-zero deploy failure — the ticket's own explicit ask) meant that `SystemExit` propagated straight out of `cmd_push()` BEFORE the remote-deploy loop (step 3) ever ran. Since `git push` to GitHub happens in step 1 (strictly before step 2), main had ALREADY advanced by the time the local install died — so the fix would have deployed to `main` and then silently deployed to **zero** of the 9 remote hosts, including the very montalu2/montalu3/montalu4 accounts the ticket exists to fix. The general check, worth running on ANY future change that adds a `sys.exit()`/raise to a function ALREADY called from inside a bigger orchestrator: grep every call site of that function and ask whether IT already has failure-tolerant wiring around ITS OWN peer steps (here, the remote loop's `try/except subprocess.TimeoutExpired` + `failed.append(...)` + `continue` pattern) — if the orchestrator's sibling steps are already resilient to failure but the NEW exit-capable call isn't wrapped the same way, that asymmetry is the bug. Fix: wrap the local step in `try/except SystemExit`, feed the SAME `failed` list the remote loop appends to, and hoist `failed = []` above BOTH steps so one shared list tracks every failure across the whole `cmd_push()` run.
- **A "safe read that never crashes" helper (`read_file_safe`) only guards against a MISSING path — swapping a filesystem glob for a direct file read in an existing check needs its OWN crash-safety audit, because a glob genuinely never raises on a directory/permission/encoding weirdness where a `path.read_text()` call does.** #276's own adversarial review: `_plugin_registry_keys()`'s docstring promised "unreadable file -> empty set", but `read_file_safe()`'s `exists()` → `read_text()` shape only catches the FIRST of three ways a path can fail to be read — a directory-shaped path raises `IsADirectoryError`, a permission-denied file raises `PermissionError`, invalid UTF-8 raises `UnicodeDecodeError`, and all three propagated UNCAUGHT. The raise escaped `_managed_plugin_built()` at `setup_managed_plugins()`'s own `if _managed_plugin_built(key): continue` — sitting OUTSIDE the per-plugin `try/except` that only wraps the `subprocess.run` install call — so `cmd_install()`'s outer try/except silently swallowed it as "(non-fatal)": remaining plugins and `ensure_playwright_browsers()` never ran, yet "Install complete." was still reported. This is a STRICT REGRESSION vs the code it replaced (`glob.glob()` never raises for any of those three shapes) — a genuine, if low-probability (needs a root-owned/corrupt/dir-shaped file on a managed box), silent-forever-skip reintroduction of the EXACT bug class the ticket existed to kill. Fix: `try: raw = read_file_safe(path)\nexcept (OSError, UnicodeDecodeError) as e: print(...); return set()` — `OSError` covers `IsADirectoryError`/`PermissionError`/`FileNotFoundError` in one catch. General lesson: replacing a glob (which structurally can't raise on read-permission/shape problems — it just returns no matches) with a direct file read is not a drop-in swap; audit every way the NEW read call can fail that the OLD glob call structurally could not, and check whether the raise would escape into an unguarded caller.
- **A per-user binary provisioned onto the no-sudo subdev stream accounts must land in `~/.local/bin`, never `~/bin`** — only `~/.profile` (a LOGIN shell) adds `~/bin` to PATH, and a Claude Code Bash tool call is not a login shell. `~/.local/bin` is the ONE directory this repo's own managed claude launcher (`CLAUDE_LAUNCH_SCRIPT_CONTENT`, see the `case ":$PATH:" in ...` line, "claude installs to ~/.local/bin") already prepends to PATH on every session start, so every Bash tool call inside that session inherits it for free — no new PATH machinery needed. #275 adversarial-review MAJOR-2, caught only because a fresh-context reviewer checked WHICH shell actually reads `~/.bin`'s PATH addition; a green test suite could not have caught it, since the tests never exercise a real login-vs-non-login shell distinction.
- **Mutation-verifying a small, self-contained fix without the full mutation-testing skill's machinery: `cp` the target file aside, apply ONE targeted `str.replace()` with an `assert mutated != src` guard (so a no-op replace never silently "passes"), run ONLY the specific new test the finding is about, confirm a genuine failure (not an unrelated crash), then `cp` the backup back and re-run the file's full test class to confirm byte-identical restoration.** #133 used this for all 4 of its adversarial-review-driven fixes (drop `str()` coercion, drop the `"other"`-managed-tier guard, no-op the shim append, drop `_managed_model`'s `try/except`) — every one was independently confirmed KILLED before the GREEN commit landed. This is the same recipe several earlier tickets in this file already document (#186, #235's `test_apply_ultracode_launcher_never_...`, the mutant-testing bullets throughout) — worth reaching for on ANY adversarial-review finding whose fix is a one-or-two-line diff, since it costs seconds and directly answers "does the new test actually catch what it claims to catch" rather than trusting that a green suite implies teeth.
- **A single-plugin "why does the version differ across accounts" investigation needs the FULL version-source hierarchy, not just "git-backed checkout vs not" — a plugin can ALSO declare its own version directly, which wins first and needs no git at all.** #279: reading real `plugin.json` files across several plugins in the SAME marketplace checkout (`discord@claude-plugins-official` declares `"version": "0.0.4"` in its own manifest and shows exactly that; `playwright`/`context7`/`frontend-design` declare no version field at all and fall through to whatever the CHECKOUT provides — a git-derived commit sha if it's a real `git clone`, else the literal `"unknown"`). A reviewer catching this by reading SIBLING plugins' manifests inside the same investigation, not just the one plugin the ticket named, is what surfaced the missing first tier of the hierarchy. Whenever explaining a Claude Code plugin's displayed "version", check the plugin's OWN `.claude-plugin/plugin.json` for a declared field before reasoning about the marketplace checkout's git state at all.
- **A widened structural "this call chain must never gain gate X" scan needs to cover EVERY function in the chain a hypothetical gate could naturally land in — not just the CLI entry point, which is rarely where a future editor would actually add one.** #228: the first-draft test scanned only `cmd_compact_request`'s `--self` branch for an `agent_type` check; a fresh-context review's own mutant — a gate inserted at the TOP of `deliver_compact_self` (the function that actually resolves the session, and so the more natural place for a future "only for the worker" restriction) — passed the test clean. Widening the scan to `inspect.getsource()` on all three functions in the chain (`cmd_compact_request`'s branch, `deliver_compact_self`, `resolve_self_pane`), then re-running the SAME mutant, is what actually proved teeth. When a mechanism's safety rests on "no gate anywhere in this call chain", enumerate the chain explicitly rather than anchoring on the single function a ticket happened to name.

- **Which grouped tmux session survives a multi-member `destroy-unattached` cleanup sweep is ITERATION-ORDER-ARBITRARY, not "the first-created" or "the exact-username-named" one.** Live-verified on an isolated `-L` scratch server: a 2-member group (`zbynek`, never attached + `zbynek-dup`, attached then detached) converged to `zbynek-dup` surviving, NOT `zbynek` — the opposite of what "the base session survives" intuition predicts. This matters because the managed launcher's `tmux new-session -A -s "$(whoami)"` only ever checks for a session with that EXACT name (never searches the whole group) — if a cleanup sweep destroys the exact-username-named session while a differently-named sibling survives, the next launcher invocation silently creates a fresh EMPTY session instead of reattaching to the surviving, populated one. Confirmed this is a PRE-EXISTING condition, not something #254's own fix introduces: this box's own real live sessions right now are `zbynek-4`/`marek-0` (no bare `zbynek`/`marek`), under the CURRENT unfixed default `off` conf. Filed as #284 (Scope-gate: needs-user-decision) rather than fixed, since the right answer needs the actual external mechanism that creates grouped duplicates identified first — grepping this repo's own `airuleset.py` end to end confirmed neither the dev1/dev2 launcher nor the subdev ssh-auto-attach block ever calls the `new-session -t <existing>` shape that links a session into a group, so whatever creates `zbynek-1..4` is external to this repo entirely.
- **An UNVERIFIED `identity:` assumption in a NEW `REMOTE_HOSTS` entry is a fail2ban risk, not just a maybe-wrong config value — the difference between "mirror simap's shape" (safe: a data-only registration, inert until `push` runs) and "assume simap's IDENTITY is also this new account's identity" (unsafe: the very next push is a genuine, untested ssh auth attempt against a box that bans on a few wrong-key tries, collateral-damaging every OTHER already-working subdev target in the same run) is worth stating explicitly whenever mirroring a sibling stream's registration.** #300 (miva1): the ticket said "same phase-1 isolated shape as simap" for the REGISTRATION, but never confirmed miva1's `authorized_keys` actually accepts the same operator key — unlike simap's own #143 commit, which recorded a LIVE-VERIFIED fact ("simap's authorized_keys are the SAME operator keys as marek"). A worker banned from ssh cannot close this gap itself; the correct move is registering the entry (inert data) AND filing a follow-up naming the exact pre-push verification needed (confirm the identity via the sanctioned `root@subdev` hop, or gatekeeper's own confirmation), so the supervisor's post-merge push does not become the first live test of an unverified auth assumption. The account's OWN `~/devel/airuleset` checkout is a SEPARATE, lower-stakes gap — `cmd_push` has no clone-if-missing bootstrap, so a target with no checkout yet just fails cleanly (`rc=1`, reported, not dangerous — the SAME expected shape every brand-new stream hits) until it's cloned (the repo is public, no credential needed).
- **`tmux display-message -p -t "=<session>"` (the SAME `=name` exact-match anchor `has-session`/`list-panes` correctly use for a SESSION target) silently resolves to NO PANE and still exits 0.** `display-message`'s `-t` wants a PANE target; a bare `=<session>` with no `:<window>` qualifier never resolves to one, so every `#{pane_*}` field expands to EMPTY with rc=0 — indistinguishable from "genuinely can't determine". Live-verified against this box's own tmux 3.7b: `tmux display-message -p -t "=marek-0" '#{pane_current_path}'` on a real, live, non-empty session returned "" at rc=0, while `tmux list-panes -s -t "=marek-0" -F '#{pane_current_path}'` correctly returned the real cwd. This shipped once, silently: #308's own first cwd-mismatch check used `display-message` and was completely INERT in production — every session, live or stray, read back as "inconclusive" and stayed quiet — and it was invisible to the unit-test suite because the fake `run` doubles matched on `argv[:2]` shape and returned canned stdout regardless of whether the real target string was even valid (a fresh-context adversarial review caught it by mutating the target to a bogus string and watching all 6 tests still pass). **Any FUTURE "read a live pane's state" helper needs `list-panes -s -t "=<session>"` (or a real pane id, `resolve_pane_cwd`'s own established pattern at `airuleset.py:1001`) for a SESSION-level query — `display-message -t` is only trustworthy against an ALREADY-RESOLVED pane target — and its own regression test must assert on the ARGV actually sent, not just on canned stdout, or a wrong-target regression can hide behind the fixture forever.**

- **`find_active_transcript(projects_dir, cwd)`'s well-documented "newest `.jsonl` in the cwd's dir, regardless of which session wrote it" ambiguity (see the earlier #65/#105-era entries in this file) bites a BRAND-NEW candidate path just as hard as an existing one the first time it is used to decide "which PANE do I act on" rather than merely "which transcript do I read from".** #320-review MAJOR-2 (reasoned trace, not yet observed live): a NEW per-pane job that resolves a transcript purely from `cwd` and then acts on the CALLING PANE (not merely reads state) is unsafe the moment two live panes can share one cwd — routine multi-window use on these boxes. The general fix, reusable for any future per-pane action gated on `find_active_transcript`: precompute a per-sweep `collections.Counter` over the caller's OWN already-fetched full pane list (`list_claude_panes`/`_reconcile_candidate_panes` — no new tmux call), and refuse the action outright whenever the acting pane's cwd count is `> 1` — ambiguous pairing is refused, never guessed at just because "same-repo templates are near-identical" (the #266-era residual note this repo already accepted for a DIFFERENT, text-only decision does not transfer to an arm-vs-never-arm decision).

- **A user-facing remedy line in a WARNING/error message is a factual claim about what ACTION actually fixes the state — verify it against the code's own real behavior, not just write what sounds plausible.** #309-review MINOR: `ensure_stream_tmux_session`'s cwd-mismatch WARNING has always said "kill it manually and re-run push", but a push can never re-create an already-bootstrapped account's session (the sentinel's own "never re-created" branch always wins) — the remedy text was simply never true, shipped originally in #308 where the WARNING was rarely reached, and only became consequential once #309 made it reachable for the whole fleet. The real remedy — the account's NEXT SSH LOGIN, via `apply_stream_ssh_attach`'s `tmux new-session -A ... -c "$__airuleset_cwd"` (`-c` is honored only on genuine CREATE, i.e. only once the killed session is truly gone) — was traced by reading that OTHER function (airuleset.py ~line 1700), not assumed. A fresh-context adversarial review caught this by asking "does the stated remedy mechanism actually work", not by re-deriving the WARNING's logic. Reusable check for any future error/warning-text review: read the SPECIFIC downstream code path the remedy claims will happen, don't trust that the sentence sounds right.
- **A comment/docstring claiming "X is a direct port of Y's own contract" (or any cross-file/cross-language parity claim) is a load-bearing, FALSIFIABLE assertion — grep for every OTHER file making that SAME claim before considering a contract-widening fix done, or the claim silently goes stale the moment the original changes.** #340-review MAJOR-2: `airuleset.py`'s `_READINESS_GATEKEEPER_FIRST_LINE_RE`/`_is_readiness_comment` (feeding the statusline's `gk`-count fallback, #313 pt 2) is an independent Python re-implementation of `subdev-handoff-match.sh`'s exclusion, whose own docstring says "a direct Python port of that script's own matching contract" — #340's shell-script widening silently made that claim false, and NOTHING caught it until a dispatched review went looking specifically because the docstring's own wording promised parity. `grep -rn "same contract\|direct.*port\|mirrors.*own" <file>` across the repo is the cheap way to find every OTHER place a fix like this needs to land, before closing a ticket that only touched one of them.
- **Classifying "did ssh itself fail auth" from a captured ssh call's stderr must check for ssh's OWN client-side message shape, never a bare substring — a REMOTE COMMAND's stderr is forwarded verbatim through `capture_output=True` and can legitimately contain the same words.** #341: `cmd_push()`'s deploy loop originally checked `"Permission denied" in ssh_result.stderr` to decide whether to skip a subsequent probe of the same account — but a real `git pull` hitting a root-owned file under `.git/` (`error: cannot open '.git/FETCH_HEAD': Permission denied`) or an `airuleset.py install` traceback can contain that exact substring with ssh auth completely intact, a fresh-context adversarial review live-reproduced this against the shipped code. openssh's client itself, when it exhausts every configured auth method, ALWAYS exits **255** and ALWAYS prefixes its own message with the literal `<user>@<host>: ` (`sshconnect2.c`'s `permission_denied()`, stable for decades) — two properties no remote process has any reason to reproduce. The fix (`_is_ssh_auth_failure(returncode, stderr)`) requires BOTH `returncode == 255` AND a regex anchor (`(?m)^\S+@\S+: Permission denied`) — reuse this exact discriminator for any future code in this file that needs to tell "ssh itself refused auth" apart from "the remote command's own output happens to mention permissions".
- **Never re-probe the SAME host for two unrelated purposes in one `push` run without sharing what the first probe already learned.** `provision_subdev_soniox_key()` used to run completely independently of `cmd_push()`'s own deploy loop, re-contacting every subdev stream account a SECOND time with zero knowledge of which ones the deploy loop, moments earlier in the same run, already saw fail auth — for N newly-registered-but-unprovisioned accounts this doubled (before #341's ssh-retry-capping fix, up to 6x'd) the auth-failure log lines against subdev, which is what tripped fail2ban and refused every LATER ssh call in the run (#341). The fix threads a plain per-run `set()` of host names through an existing function call (`skip_names=`) — no new persisted state, no separate probe call (which would have ADDED a third connection instead of removing one of the two that already existed); the deploy loop's own real, already-necessary first attempt IS the de facto probe. Reuse this shape (a function-scoped set passed to a sibling function, never a new file/marker) for any future "two independent phases of the same run must not duplicate work against a known-bad target" problem in this repo.
- **A "did a real SLASH COMMAND get invoked" detector anchored on a BARE TEXT PREFIX regex (`^/autopilot\b`) is dead on arrival — Claude Code never stores a slash command as bare text at all.** #393-review CRITICAL-1/2 (fresh-context adversarial review, 2026-08-12, independently re-verified against 1787 real local transcript files / 1127 real occurrences of the substring "/autopilot": ZERO matched). A SKILL command (one defined by a `skills/<name>/SKILL.md`, e.g. `/autopilot`, `/review`, `/issue-planner`) is written as a fixed two-tag sequence with `<command-message>` FIRST — `<command-message>autopilot</command-message>\n<command-name>/autopilot</command-name>` — the OPPOSITE tag order from a BUILTIN command (`/exit`, `/compact`, `/model`, `/goal`), which this file's own `_EXIT_CMD_MARKER` already correctly matches `<command-name>`-first. The bare-prefix regex was simultaneously WRONG in the other direction too: `\b` matches on a hyphen (a non-word char), so `^/autopilot\b` also matched ordinary prose merely NAMING the worker (`/autopilot-worker died mid-run…`, a real, plausible sentence in this repo) — a "mention vs use" failure this file has hit before for OTHER slash commands, just never for a SKILL command's own inverted tag order. Fix: anchor on the CONFIRMED real tag pair (`re.escape` both tag literals, matched via `.match()` from position 0), never a bare `/word\b` prefix — and before writing ANY future "did the user invoke slash-command X" detector, grep `~/.claude/projects/**/*.jsonl` for the real occurrences FIRST (a 20-line throwaway script over the corpus, seconds to run) rather than guessing the wire format from how the command LOOKS when a human types it.
- **`push` nemá `--host` — single-host deploy neexistuje ako flag.** Grep `--host` v airuleset.py patrí iným príkazom (stats/collect); fixture noise v push logu ho zvádza priradiť k push. Per-box deploy leg sa robí ručne = presne to, čo push robí na každý remote: `ssh <box> 'cd ~/devel/airuleset && git pull --ff-only && python3 airuleset.py install'` z čistého committed ref (2026-08-12, spinbike bootstrap #408).
- **Extracting a `cmd_install()`-style orchestrator STEP's own gate into its own small, separately-callable function (`sweep_fn=None` injection point) is what makes its wiring test non-tautological — a test that RE-IMPLEMENTS the same gate logic inside itself and calls a mock DIRECTLY proves nothing about what the real orchestrator does.** #410 review F2 (MAJOR): the pre-fix test computed `live_compress = os.environ.get(...) == "1"` INSIDE the test body and called `sweep_old_transcripts(dry_run=not live_compress)` itself — mutation-confirmed to survive UNCHANGED even when the real `cmd_install()`'s own step 12 was mutated to hardcode `dry_run=False` unconditionally (a genuine, fleet-wide-dangerous bug the "passing" test gave zero warning of). Fix: `_run_transcript_compress_step(sweep_fn=None)` factored out as the EXACT function `cmd_install()`'s step calls, defaulting `sweep_fn` to the real production sweep when uninjected — the test then calls THIS function with `sweep_fn` mocked, and a hardcoded-`dry_run=False` mutant in the real function immediately fails it. Reusable pattern for ANY future `cmd_install()`/`cmd_push()` step whose own gating logic needs a genuine (non-self-referential) test: extract the gate+call into its own top-level function with an injectable dependency, never test the orchestrator's inline code by re-deriving its logic in the test.
- **A ticket's own explicit design mandate ("no retry loop") and a genuinely load-bearing correctness gate the DELETED retry loop used to enforce (the #238 same-turn-dispatch race, via `COMPACT_MIN_REQUEST_AGE_S`) can look mutually exclusive at first read — they are not, once the deleted loop's OWN behaviour is measured rather than assumed.** #402-review MAJOR-1: `deliver_compact`'s too-young floor compares the request's `ts` against `now` at the exact instant `deliver_compact` runs; when the record and the synchronous delivery-check happen in the SAME call (`cmd_compact_request --self`/`--record`, both new #402 entry points), that delta is provably ~0, so the floor refused EVERY fresh request unconditionally — silently reverting a previously-fixed, previously-MEASURED #238 regression ("18 of 87 real sends... took the slow path"). The fix, `_compact_sync_attempt` (`watchdog/compact.py`): record, then ONE bounded one-shot `time.sleep()` sized to just clear the floor (computed from the REQUEST's own recorded `ts`, so a re-record whose anchor is already old enough sleeps zero), then ONE `deliver_compact` call — reading the OLD (deleted) `_compact_retry_until`'s own code comment first ("attempt 1 always fails too-young at t=0, attempt 2 [after one sleep] succeeds") showed the retry loop's REAL behaviour was ALSO never a zero-latency first attempt; it just achieved the same 2s+ wait via a generic retry-until helper instead of one explicit sleep. Reproducing the OLD MECHANISM's real observable effect with the NEW design's simpler primitive (no loop, no six tuning constants) satisfies both the deletion mandate and the correctness guarantee — read a deleted mechanism's OWN comments for what it ACTUALLY did before assuming its removal is safe just because the removal was explicitly requested.
- **A NEW watchdog fake tmux's `list-panes` handler must reply with the EXACT field count the specific query asked for — two real production call sites (`list_claude_panes`'s 4-field `#{pane_id}\t#{pane_current_command}\t#{pane_current_path}\t#{pane_pid}` and `_reconcile_candidate_panes`'s 3-field query with no `#{pane_pid}`) coexist in this file, and a fake that always returns 4 fields silently gives the 3-field consumer ZERO candidates (its own `len(parts) != 3: continue` guard drops every line).** #403: `goal_dark_watch`/`goal_lane_sweep`'s own sweep_deadline tests reported an empty `logs` list from a REAL 3-pane fixture — the tell was that several OTHER tests in the same class (`sent == []`-style assertions) stayed GREEN throughout, because an empty-candidate-set sweep trivially satisfies "nothing was sent" for the WRONG reason (the exact vacuous-test shape this file already documents elsewhere: a check that only proves absence is indistinguishable from a check that never ran at all). Fix: branch the fake's `list-panes` reply on whether `"#{pane_pid}"` appears in the requested format string, and reply with 3 or 4 tab-separated fields to match.
