- **The established backup/mutate/run-test/restore mutation-verification technique (this file's own dozens of prior entries) has a sequencing trap: taking the "clean" backup snapshot MUST happen from a freshly-restored, KNOWN-GOOD state — taking it while a PRIOR mutation is still live silently bakes that mutation into every "restore" for the rest of the session.** #409-review-fix: after mutating away one fix to prove its test's teeth, a SECOND `cp airuleset.py .../backup.py` was taken (intending to snapshot the current, believed-clean state) WITHOUT first restoring the prior mutation — so every later "restore from backup" for the rest of that verification pass silently re-applied the STILL-MUTATED (broken) code, and the real fix had to be re-derived and re-applied from scratch once `grep -c "the fix's own marker string"` on the "restored" file came back empty. Fix habit: verify the restore itself immediately after every `cp <backup> <target>` (a cheap `md5sum -c <saved-checksum-file>` or a `grep -c <marker>` on the just-restored file), not just after the LAST one — and never chain "mutate -> run test -> take a NEW backup" without an explicit restore in between; the backup call itself does not know or care whether the file it's copying FROM is currently clean.
