## pre-write-script-check.sh — why it exists and what it scans

Moved VERBATIM from `modules/quality/script-failure-policy.md` (#92 item 4):
hook internals, not a rule a session acts on.

`ruff check .` (the push gate) already catches bare `except:` for free (pycodestyle E722, in ruff's default rule set) — but NOT `except Exception: pass` (that needs the separate `S110` rule, which is NOT enabled: this repo's own code has 24 pre-existing `except ...: pass` sites that would all break the gate). Instead, a `pre-write-script-check.sh` PreToolUse(Write|Edit) hook blocks it going forward: any NEW Python content (Write's full file, or Edit's inserted text) introducing an `except` clause whose sole body is `pass` is blocked — pre-existing files are never retroactively scanned. The same hook blocks a brand-NEW `.sh` file (Write only) that's missing `set -euo pipefail` in its first 15 lines. Bypass (rare, logged): `# airuleset:script-ok <reason>` anywhere in the written content.

- **A label-based cross-project protocol convention (e.g. `prio:bounce`) needs an explicit REPO ALLOWLIST, not just a "who does this exclude" scoping.** Job 8's `_bounce_quals` scoped WHO a query excludes (sub-dev stream labels, to avoid double-pinging) but never WHICH REPOS the label can mean anything in at all — so a bare `prio:bounce` used as a generic priority marker on an unrelated repo (restreamer #337, 2026-07-26) matched and fired a confusing cross-project nudge. The fix is `_repo_in_cross_stream_flow()`, an opt-in `_CROSS_STREAM_REPOS` registry checked BEFORE the query is even issued — never try to discriminate a genuine protocol artifact from a misused label per-TICKET (the false ticket had a real, unrelated comment too, so "has a comment" doesn't discriminate); the repo itself is the only reliable signal.
- **The #48 context-size gate answers "is compacting worth it", not "did real work happen" — a marker-only compaction trigger needs a SEPARATE substantiality signal, and "commits since an anchor" is a clean one.** #99: job 14 / the synchronous `deliver_compact_now` path fired `/compact` on every `✅ DONE`-shaped turn once a session's context passed 200K, including a bare one-line answer or a single filed ticket with zero code change — because #48's gate only ever asked "is the context big enough", never "did anything durable land". Fix: `compact_boundary_substantial(cwd, sid)` counts commits in the session's OWN `cwd` git repo since an ANCHOR (a persisted per-repo `compact-substantiality.json` timestamp, updated by `mark_compact_boundary` on every real send; falls back to the session's own transcript start time on the very first boundary ever seen for that repo) — a positively-confirmed ZERO drops the request outright, an UNMEASURABLE result (not a git repo, git unavailable, no anchor) falls through to the pre-#99 behavior unchanged, mirroring the #48 gate's own "never block on 'don't know'" philosophy exactly. Corpus-replayed against this repo's own 268 real `✅ DONE`-boundary turns + its own real git history: old behavior fires all 268, new fires 187, drops 81 (30%) — and the 187 remaining prove the fix narrows false triggers without silencing genuine ones. Reuse this exact shape (git-commit-count-since-a-persisted-anchor, never-block-on-unmeasurable) for any future "did real work actually happen" signal.
- **Testing a "did work happen since X" signal: build REAL git repos in a temp dir (`git init` + `git -C <repo> commit` with `GIT_AUTHOR_DATE`/`GIT_COMMITTER_DATE` env vars pinned to an exact epoch), never a hand-typed `git log` string.** Placing commits deterministically before/after a fixed anchor timestamp via those two env vars (not wall-clock `now`) makes the test reproducible and lets a SINGLE helper (`_commit_at(repo, epoch_ts)`) build every before/after case the substantiality gate (#99) needed. The corpus-replay itself (`git rev-list --count --since=<iso> --until=<iso> HEAD`) is the same primitive scaled up to real history — write the primitive once, reuse it for both the unit test and the replay.
- **Playwright MCP's `browser_file_upload` REJECTS any path outside its own allowed roots (the repo root + `<repo>/.playwright-mcp/`) — a file staged under the session's scratchpad (`/tmp/claude-.../scratchpad/...`) is refused with "File access denied ... outside allowed roots".** Stage upload-test fixture files under `<repo>/.playwright-mcp/<subdir>/` instead (create the dir, `head -c N /dev/urandom > file`), run the upload, then delete the whole subdir afterward so nothing lingers in the working tree (`.playwright-mcp/` isn't meant to be committed). Hit live verifying #27's multi-file drag-drop through a REAL browser session.
- **Proving "does watchdog job X's fix actually hold" needs a LIVE CORPUS SCAN across EVERY project's transcript + the job's own sync log, not just the ticket's originating project.** #78's own acceptance demanded proof from a project OTHER than airuleset. The recipe: for every dir under `~/.claude/projects/` (excluding the repo being worked), grep each `*.jsonl` for the relevant marker pairs (here: a top-level `user` entry whose content is exactly the slash command, and a `system`/`subtype` boundary entry), THEN cross-reference against the mechanism's own log (`~/.claude/compact-sync.log` for the synchronous `/compact` path, `journalctl --user -u api-watchdog.service` for the periodic jobs) to determine WHICH sender fired each event — an event with no matching log line in EITHER source is very likely a HUMAN typing the same command manually, not a regression; don't count it as a bug. The STRONGEST proof isn't a clean single pair — it's catching the guard ACTIVELY firing (a `SKIP claim-queued` 30s after a `SEND`, for the exact same session) mid-incident, which is direct evidence of prevention rather than just absence of a problem.
- **Settling "can a LOCAL slash command (e.g. `/compact`) ever trigger hook mechanism X" (here: the goal Stop hook) — trace the ACTUAL call graph of the hook's real implementation function in the installed CC binary, don't stop at string presence.** #87: `strings`-searching for "Stop hook" text only finds string literals and an export-symbol table (a minified module's `tt(Module,{name:()=>impl,...})` map) — neither proves WHO calls the implementation. The decisive technique: (1) find the hook-event REGISTRY object (`{Stop:VEe,SubagentStop:VEe,...}` — one implementation symbol reused across event names) to get the canonical implementation's minified name; (2) `re.finditer(rb"\bVEe\b", data)` for EVERY raw-byte occurrence of that exact symbol in the whole binary (not just near the string you started from) — this finds both the export map AND every real call site, typically a handful; (3) read a few KB of raw bytes around each call site (`data[idx-N:idx+N].decode("utf-8",errors="ignore")`) to see the actual minified JS and its enclosing function; (4) for each call site, trace ONE level further up to its own caller and check what triggers THAT (e.g. `Ycd`'s only caller processes the RESULT of a real, already-executed model query — never reachable when the local command's own handler already returned `shouldQuery:false`). Two binary-format gotchas: strings you find via a plain `strings`/`data.find()` near a symbol may sit inside a COMPILED V8 bytecode/snapshot region (interspersed with `\x00`/length-prefixed bytes, not readable JS at all — the goal marker strings `"Goal set: "`/`"Goal cleared: "` are stored this way), while genuinely readable minified JS source lives in a SEPARATE region of the same binary; a byte offset that decodes to garbage is not proof the feature doesn't exist, just that you're looking in the wrong region — search for the SAME symbol elsewhere in the file (multiple hits are common: registry, export map, AND real call sites) before concluding.
- **CC renders the separator after a held-draft `❯` as a NON-BREAKING SPACE (`\xa0`), never a plain ASCII space — a bare box has no separator at all (`'❯'` alone), so only the DRAFT case differs.** #100/#101: `_has_free_prompt(bare_only=False)` — the precondition `deliver_with_stash` checks before EVERY real delivery — was anchored on a literal `"❯ "` and so NEVER recognized a real held draft as free, always returning `"stash-abort: not idle-with-draft"` regardless of how idle the pane actually was. This had been silently wrong since the stash mechanism shipped (#35): every existing unit-test fixture across the whole file modeled the assumed (wrong) character, so "successful delivery" tests were passing against a fixture that never matched reality. Fixed by accepting either character in both `_has_free_prompt` and `_MENU_POINTER_RX`'s dialog-open exclusion. Found ONLY by live-testing against a real CC v2.1.220 pane (`_find_boundary_line(cap)` on a real capture, print the repr, look at the actual bytes) — no amount of unit testing against hand-written fixtures could have caught it, because the fixtures themselves encoded the wrong assumption.
- **Before assuming a ticket's own "job N does X" claim identifies the right mechanism, trace which watchdog job's PRECONDITIONS actually match the described scenario — a live incident narrative can misattribute a symptom to the wrong job.** #100's own ticket said "job 20 (goal_rearm) arms goals programmatically", citing a gatekeeper timestamp pair as proof — but job 20's revival path requires a PRE-EXISTING `Goal set:` transcript marker (`rec.get("mark") == "set"`), so it is structurally incapable of arming a goal that was never armed before. Reading each job's actual GATE conditions (not the ticket's prose) is what correctly redirected the fix.
- **A "scratch, isolated" `CLAUDE_CONFIG_DIR` Claude Code session is isolated for CONFIG/PROJECTS/CREDENTIALS — it is NOT isolated from the REAL CWD, and typing a literal `/goal ...`-shaped line as plain chat text (even split across several `send-keys -l` + `Enter` calls meant to just make CC PRINT that text) gets interpreted as a REAL slash command and REALLY arms a goal, which then autonomously starts working (real `gh` calls against the real repo) — burning real tokens on unintended work.** Live-verifying #100/#101's stash delivery: a multi-line "print this text verbatim" prompt caused the scratch session to itself synthesize and ARM a full `/autopilot`-shaped goal for the real `zbynekdrlik/airuleset` repo, which then ran `gh issue view` against real issue numbers before being caught and `/goal clear`ed. Never send anything starting with `/goal ` as literal keystrokes to a scratch/test pane unless arming a REAL goal there is the intended, contained test — and always end a scratch-session live-proof with `/goal clear` + capture-pane confirmation BEFORE `tmux kill-session`, not just the kill.
- **Corpus-replaying "was the /compact SEND's PRECEDING status marker ❓" needs two things #78's own recipe (above) doesn't spell out: (1) job 14/15/17's OWN "OK (compact-...)" journalctl lines log the PANE LOCATION (`zbynek-0:6.0`), never the session id — only the synchronous path's `compact-sync.log` is sid-keyed — so attributing a periodic job's send to a specific transcript needs a PROXIMITY match (the nearest real `compact_boundary` system entry across the WHOLE corpus within a few minutes after the send timestamp), not a text-substring sid search (which silently finds ZERO matches and looks like "no evidence" when the evidence is just filed under a different key). (2) The marker at SEND TIME is NOT `transcript_last_marker(path)` — that function reads to EOF, i.e. the session's marker as of TODAY, not as of the historical send; replaying a past decision needs a small variant that walks entries backward with a `timestamp <= cutoff` filter first.** #102: this exact recipe replayed job 14 (14 real historical sends, 0 preceded by ❓), the synchronous path (7 real sends via `compact-sync.log`, 0 preceded by ❓), and job 17 (8 real sends, 0 preceded by ❓ but 4 preceded by ⏳/blank — proof it WAS firing off non-ticket-boundary turns, the exact unauthorized behavior the ticket's correction forbids, even though it never happened to catch a ❓ specifically in this box's log window) — and found the two ❓-preceded `compact_boundary` events in the post-#39 corpus had ZERO matching watchdog log lines nearby (one had a "question answered in-session" line ~1 minute later — a human at the terminal, not automation). Absence of a nearby log line is evidence of a MANUAL `/compact`, not proof the fix is unnecessary — the user's corrected agreement (#102) stands on its own regardless of whether the one reported incident can be forensically pinned on a specific sender.
- **Retiring a numbered watchdog job: NEVER renumber the survivors.** #102 removed jobs 15 and 17 entirely (constants, state, tests) but left their NUMBERS as gaps in `run_once`'s docstring (`(15) ... — REMOVED (#102, ...)`) and in the job-count bullet above, rather than shifting 16→15/18→16/etc. Dozens of historical comments, `docs/autopilot-log.md` entries, and this very playbook file address incidents by job number ("job 17's own `compact_ceiling`") — renumbering would silently break every one of those references for a purely cosmetic gain. A short REMOVED note at the old number (what it did, why it's gone, pointer to the removing ticket) is enough for a future reader to orient.

- **A dispatched subagent's copy of the global `CLAUDE.md` is a SNAPSHOT taken at the PARENT SESSION's start — an `@import`ed module edited mid-session does NOT reach subagents dispatched later in that same session (#49/#50, 2026-07-27).** This qualifies #104's "a module body reaches a dispatched subagent = YES": true, but of the text as of session start, not as of disk. Proof shape (falsifiable in both directions, one cheap `haiku` `general-purpose` probe, no tools): ask for TWO quotes from the SAME module file — a control sentence that predates the session and the clause just added. The probe quoted the control (`NEVER invent a plugin-prefixed name`) verbatim and reported the new least-tool-authority and fork-inheritance clauses ABSENT, minutes after `airuleset.py push` had installed them and with the module file on disk containing both. So `install`'s own "Restart Claude Code for changes to take effect" applies to SUBAGENTS too, and a live-verification of a freshly pushed rule via a dispatched probe will report a FALSE NEGATIVE unless the session is restarted first. The surface that IS process-fresh is the `inject-situational-rule.sh` PreToolUse injection — a new process per tool call, reading the skill body off disk — so a rule that must take effect in an already-running session belongs there, and the honest same-session proof is running that hook against a real payload rather than dispatching a probe. Corollary for probe design: a one-sided "the agent did not know X" proves nothing on its own; only the control quote from the same file turns it into evidence about WHEN the file was read.
- **`Explore` subagents report a much thinner context than `general-purpose` — do not use `Explore` for an introspection probe.** The same probe (2026-07-27) run as `Explore` returned ABSENT for every question INCLUDING the control, and described its skill list as bare names with no descriptions; the `general-purpose` run answered the control verbatim. - **Deciding "does the current model do this natively?" — run a BARE-model probe, and PAIR a leading scenario with a non-leading one.** #110 settled six sections of `ci-monitoring.md` this way. The harness: a throwaway `HOME` containing only `.claude/.credentials.json` (copied) and `{"hasCompletedOnboarding":true}` in `.claude.json`, prompt on stdin, `env -i HOME=<tmp> PATH=$PATH claude -p --model sonnet`, fanned with `xargs -P 8` (5 sonnet + 3 opus replicates per scenario; 64 probes ran in ~4 min). **Always run the contamination control FIRST** — ask the probe whether its instructions contain the rule: bare answered "NO", the real `HOME` quoted the module verbatim. Without that check a "the model already knows it" result proves nothing, because our own always-on prefix would have told it. **The pairing is what makes the verdict trustworthy**: shown the pending deploy job explicitly, 8/8 waited for it (looks native); shown only "lint passed, test passed" with the run still in progress, 8/8 declared "CI is green" and 5/8 added "no further action needed" (decisively NOT native). A single leading scenario would have deleted the module's load-bearing line. The probe must be able to return NO — in the same run it did, on the mechanism axis (0/8 produced our poll-loop shape).
- **Before keeping OR dropping a rule that BANS a tool, MEASURE the tool.** `ci-monitoring.md` banned `gh run watch` on an unmeasured "polls every 3 seconds and causes rate limiting", while 8/8 bare models reach for it — the tempting conclusion was that the rule fights the model for nothing. Measured against a live public in-progress run (`gh api rate_limit` delta around `timeout 62 gh run watch`): **71 API calls + 9.7 KB of output per minute** at the default interval (~4100/h against a 5000/h limit), and `--interval 30` still cost 38 calls/min (~2200/h) — the interval does NOT scale the cost down linearly because `gh` re-polls every JOB in the run. `gh run view --json status,conclusion` is 1 call and one line per poll. The ban was right; the hypothesis that "the native tool has caught up" was wrong, and only a two-minute measurement separated them.
- **`nohup <cmd> &` INSIDE a `run_in_background: true` Bash call defeats the whole point.** The trailing `&` returns immediately, so the harness's task exits at once and fires its single completion notification straight away — the "one notification for the whole wait" design silently becomes "one notification one second in". A background waiter must BLOCK in the foreground of its own call (`timeout <budget> bash -c 'while :; ... done'`); the harness does the backgrounding.
- **A module's code block can be EXECUTED by a test — check before reordering or replacing one.** `tests/test_airuleset.py::TestCiMonitoringPollSnippetSelfBounds` extracts the **first** ` ```bash ` fenced block in `ci-monitoring.md` with `re.search(r"```bash\n(.*?)\n\s*```", ..., re.S)`, substitutes `<id>` and `sleep 30`, and RUNS it against a fake `gh`, asserting the exact strings `TERMINAL: completed success` and `POLL BUDGET REACHED`. So the snippet's position in the file, its placeholder spellings, and its echoed strings are all load-bearing. A second code block is safe to rewrite only because it is fenced with a bare ``` (untagged) and the regex is non-greedy on ` ```bash `.
- **Pre-normalize the corpus in the n-gram test-lock sweep or it times out.** The obvious first draft calls `re.sub(r"\s+", " ", txt)` on each test file inside the innermost loop — that is O(lines x windows x files) regex work and blew a 2-minute Bash timeout on a 73-line module. ## #414 — SOTA architecture: design-gate extension (Architektúra:/Triage: sections)

- **A block-reason assertion on a fixture that trips TWO branches of the same gate is a mutation-teeth tautology: pin the asserted reason to the branch under test, and keep one fixture where the other branch structurally CANNOT fire.** #446 adversarial review F1: bare `n/a` on a 🌐-carrying fixture blocked via EITHER the value-free branch or the n/a×🌐 contradiction — a mutant deleting the n/a-reason requirement survived because the contradiction still blocked the same fixture (same observable, different reason). The surface-less (no 🌐/📱) sibling fixture is what killed it.
- **`block-commit-without-design.sh` scans the WHOLE commit-message text for `#N` refs and requires a design marker for EVERY OPEN, unmarked one — so a bare `#N` CONTEXT citation that is NOT the commit's own ticket false-BLOCKS the commit.** #386 (worker): a `[green]` commit for #386 cited the user-directive ticket `#486` (and related-lane `#433`) in its body prose; #486 was OPEN with no design marker, so the gate blocked with `#486: missing: root cause, chosen approach, rejected alternative`. The hook already drops CLOSED refs (#206) but has no way to tell "this commit's ticket" from "a context ref" among OPEN ones — the repo's own `(#N)` convention is syntactically identical. Fix at authoring time: name a context/related ticket in WORDS without the bare `#N` (e.g. "the user's reuse-existing-structure direction" instead of "#486"), keeping only the commit's actual ticket as `#N`; last resort `[no-design: <reason>]`. Note the atomic-block trap (#310): a `git add … && git commit -F msg` compound is denied WHOLE, so the `git add` never ran — re-stage before the reworded retry.
## Managed-plugin tiers + per-project Playwright opt-in (#415, 2026-08-13)

There are now THREE plugin tiers in `airuleset.py`, distinguished by what
`reconcile_managed_plugins()` writes into user-scope `~/.claude/settings.json`:

- **A `gh issue create -F "$VAR"` (or any hook-gated command with a `$VAR` argument) is read by the PreToolUse hook as the LITERAL unexpanded text `$VAR` — hooks see argv BEFORE shell expansion — so a hook that reads the `-F` body file gets an empty/unreadable body and false-blocks on "no Scope-gate / no Dedup-checked line" even when the file has both.** #415: `block-ungated-issue-filing.sh` logged `criterion=none dedup="none"` for a body file that demonstrably had both lines, purely because the path was passed as `$SP/followup_body.md`. Always pass the FULL LITERAL absolute path to a `-F`/`--body-file` argument of any hook-gated `gh`/`git` command. Companion (#159, re-hit): a `printf ... >> body.md && gh issue create ... -F body.md` chained on ONE line never appends when the `gh` half is blocked — a PreToolUse block kills the WHOLE compound command atomically, so the `printf` never runs. Compose the body (and any last-line append) in its OWN Bash call, then file in a SECOND call.
- **A hook that reads a `-F <file>` (or any relative file-path argument) must resolve a RELATIVE path against the command's EFFECTIVE cwd after a leading `cd <dir> &&`/`;`, NOT the hook process's own cwd — otherwise `cd /dir && gh issue create ... -F body.md` opens `<hookcwd>/body.md`, fails, treats the body as unresolved, and false-blocks a fully-compliant filing with the opaque per-item reason `-> none`.** #483 (live incident gk@odoo-erp filing odoo-erp#4102; the IDENTICAL body PASSED with an absolute path — the giveaway that the path, not the body, was the problem). Distinct from #415 above (that one is `-F "$VAR"` read as the LITERAL unexpanded string; this one is a real relative path resolved against the wrong dir). Fix pattern in `block-ungated-issue-filing.sh`: walk the top-level segments tracking `effective_cwd` (starts as the hook cwd == the shell's own starting cwd, so a no-`cd` command is unchanged) and fold every `cd <dir>` segment into it (`_apply_cd`: absolute target replaces it, relative one is `os.path.normpath(os.path.join(base, target))`); resolve a relative `-F` against `effective_cwd`. TWO safety rails make option-1 non-fragile: (a) an unexpandable `cd` target (`$VAR`/`~`/glob/`` ` `` → `_cd_target` returns None → effective cwd becomes None), and (b) any `-F` disk path that still can't be read, BOTH degrade to an explicit actionable reason (`_unreadable_body_err`: names the file + cwd + "use an absolute -F path") that the missing-criterion BLOCK prints instead of `-> none` — never a WRONG resolution, never a fail-open PASS (which would wave a genuinely ungated filing through, breaking the hook's documented conservative bias). Companion: `block-commit-without-design.sh` already solved the SAME class for `cd <path> && git commit` via `notify.resolve_work_cwd` (#187) — reach for a cwd-aware resolution whenever a hook reads a path from a compound command that may `cd` first.
- **Extending a REMOTE_HOSTS-based delivery (the meeting-analysis Soniox key) to a managed NON-subdev target uses a declarative per-host FLAG, and is EXEMPT from the #143/#300 onboarding-registry checklist (#451).** `provision_subdev_soniox_key`'s target filter keyed on `AUTHORITY_BY_USER` MEMBERSHIP, which is about MERGE rights, NOT per-service usage — so a full-authority box like `newlevel@dev2` (not a sub-dev stream) was silently excluded from soniox delivery and meeting-analysis Phase 2 died there with `SONIOX_API_KEY not set` (the skill greps `~/.soniox.env` first, SKILL.md:123). Fix pattern: add `"soniox": True` to that host's REMOTE_HOSTS entry and widen the filter to `h.get("user") in AUTHORITY_BY_USER or h.get("soniox")` — the host then rides the SAME existing delivery loop (line-scoped `_soniox_key_line` source read, value via `input=` never argv, `umask 077`+`chmod 600`, per-host retry, loud missing-source failure), no parallel mechanism, no `cmd_push` change (the deploy loop already calls the function over full REMOTE_HOSTS). CRITICAL distinction: registering a NEW sub-dev STREAM account triggers the five-place checklist (`REMOTE_HOSTS` + `AUTHORITY_BY_USER` + `block-subdev-ssh-misuse.sh` allow-list + watchdog `_REDUCED_STREAM_USERS` + notify `STREAM_NOTIFY_OWNER`, per #251/#300/#326/#347); a delivery FLAG on an EXISTING full-authority target needs NONE of those — it creates no new user/stream/authority, only opts an already-registered box into one more per-service delivery. Don't over-do the registries for a flag; don't under-do them for a real stream. (Companion design-gate note: a STEP-0 validation comment must NOT also satisfy `classify_design_comment` — the recorder grants at most the first still-missing kind and, if a design-shaped comment lacks the Triage/Architektúra shape, `break`s granting NOTHING; keep the validation comment missing at least one of root-cause/approach/alternative so it lands as `validated`, not a failed `design` attempt.)
- **The native private plugin MARKETPLACE (`claude plugin marketplace add` + `plugin install` + auto-update) CANNOT absorb airuleset's skills/hooks/rules payload: it is DEFERRED-KEEP and the bespoke `airuleset.py install/push` deployer is KEPT for the WHOLE payload (#419, 2026-08-14; audit #416 candidate verdict was "marketplace absorbs the payload" — this evaluation refutes it with the CC capability model).** The payload push deploys is (1) 59 always-on modules → generated `~/.claude/CLAUDE.md` via `@import`, (2) ~23 skills symlinked with a PER-BOX subset (`skill_names_for_user`), (3) 2 agents, (4) 5 path-scoped rules → `~/.claude/rules/`, (5) 49 hooks merged into `settings.json` + managed settings DEFAULTS (`model`=fable / `effortLevel`=xhigh / `disableAgentView` / `env` / …). Four capability facts (CC docs 2026-08-14) make the native plugin framework un-adoptable for THIS payload, not merely weaker: (1) NO declarative always-on-rules component exists — the 59 always-on modules could only move as a hand-authored `SessionStart` hook emitting them, a strict downgrade from declarative `@import`; (2) NO native plugin-sourced path-scoped `.claude/rules/` component; (3) a plugin's own `settings.json` honors ONLY `agent`+`subagentStatusLine`, so the managed fleet-policy settings defaults (`model` / `effortLevel` / `ultracode` / `disableAgentView` / `env`) CANNOT be set by a plugin at all; (4) NO per-box subset within one plugin (`enabledPlugins` is whole-plugin, `skillOverrides` excludes plugin skills) — subsetting forces 2-3 separate marketplace plugin ENTRIES. Structural clincher: the repo is git-cloned on every box by push REGARDLESS (CLAUDE.md `@import` and the 49 hooks reference on-disk `~/devel/airuleset/…` paths), so a plugin channel is ADDITIVE, not a replacement — push never retires, no maintenance is saved, only added, and the payload loses its version-COHERENCE (one commit deploys the modules + the skills they name + hooks in lockstep, vs a separately-pinned plugin skewing stub modules against the skills they defer to). Measurement (the ticket asked "lines of push that die"): only ~90 lines of skill/agent symlink loops are cleanly-mappable, offset by NEW marketplace-split + offline-seed-dir + auto-update-toggle machinery that is MORE code than it removes — so DEFER-KEEP loses no lines worth losing and adds no version-pin/offline/application-order fragility under the supervision-machinery FREEZE. Re-audit trigger (per #423's permanent native-now process): a future CC release adding a declarative always-on-rules plugin component OR a native plugin-sourced path-scoped `.claude/rules/` component AND a per-installer skill-subset mechanism flips this KEEP into a real migration evaluation.
