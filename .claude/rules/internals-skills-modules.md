### airuleset internals — skills / modules / agents / profiles / rules

Hlbší archív airuleset-internals je v `.claude/rules-reference/internals-archive.md` (on-demand). NOVÉ skills / modules / agents / profiles / rules lekcie pridávaj SEM.

- Every module must be standalone, actionable, and 5-20 lines
- Rules must have YAML `paths:` frontmatter
- Skills use the SKILL.md format with YAML frontmatter
- **Skills deploy per box (`skill_names_for_user()`): when scoping a skill away from a box, check whether that box's WORKFLOW actually uses it** — `SKILLS_EXTRA_BY_USER` re-grants a scoped-away skill per user (montalu ← meeting-analysis, 2026-07-14). And a skill deployed to isolated sub-dev users must be user-agnostic: `$HOME` paths, never `/home/newlevel/...`; per-user secrets read from `~/.claude/secrets/*.env` (provisioned via ssh-stdin, NEVER git).
### Which surface actually LOADS — measure before converting a module (#104, 2026-07-27)

Every `module → skill` or `module → path-scoped rule` conversion in this repo is
a bet that the target surface is loaded on the path that needs it. `e9d1022` lost
that bet once already, and the loss was invisible for 18 days. Before converting
anything, know these EMPIRICAL facts (three introspection probes, 2026-07-27 —
each subagent was asked only to report its own context):

| Surface | Reaches a dispatched subagent? |
|---|---|
| Global `~/.claude/CLAUDE.md` with `@import`ed module BODIES expanded | **YES** — probes quoted verbatim sentences from inside the modules |
| Project `CLAUDE.md` | **YES** |
| Auto-memory `MEMORY.md` | **YES** |
| An agent file (`agents/<name>.md`) | **YES** — it IS the subagent's system prompt |
| **Skill BODIES (`skills/*/SKILL.md`)** | **NO** — only the name + one-line description from the skill list |
| Path-scoped rules (`rules/*.md` → `~/.claude/rules/`) — MAIN session | **YES** — `nested_memory` attachment on Read (#105) |
| Path-scoped rules (`rules/*.md` → `~/.claude/rules/`) — dispatched SUBAGENT | **NO** — zero `nested_memory` attachments even with the correct cwd (#105) |

Consequences that keep biting:

- **Content a dispatched worker must ACT on cannot live in a skill body.** It only
  arrives if that worker itself calls the `Skill` tool, and nothing in the
  `/autopilot` dispatch chain tells it to. This is exactly how the design-first
  step vanished from the ticket path (#104): the supervisor loads
  `batch-issue-development` in ITS context; the worker is a separate dispatch
  joined to it by a one-line prompt.
- **A lock test that forbids a literal WILL match its own prose — assert the STATEMENT, never the substring.** #113: the RED lock asserted `time.sleep(0.6)` was absent from the whole source, but the module's docstrings and comments necessarily NAME the literal they exist to explain, so the test could never go green whatever the fix did — red for the wrong reason, which reads exactly like a fix that does not work. The replacement matches a comment-stripped line that IS the bare statement (and reports offending LINE NUMBERS instead of dumping the file into the assertion message). Its companion assertion then hit the same trap one level up: `src.count("subprocess.Popen(")` counted the string inside its OWN failure message, so it read 2 where the module has 1 — fixed by matching the statement form `^\s*\w+\s*=\s*subprocess\.Popen\(`, which the assertion's own escaped-regex line cannot match. Rule of thumb: whenever a test forbids a token that the test itself must mention, match a SHAPE the mention cannot take (a bare statement, an assignment) — never a bare `assertNotIn`/`count` over the file.
- **Two Python gotchas when driving repo scripts from a scratch dir.** (1) The shared scratchpad contains a stale `inspect.py` from an earlier session, which SHADOWS the stdlib module and makes `import dataclasses` explode with a `FileNotFoundError` from someone else's script — run analysis scripts from a clean `/tmp/<ticket>/` dir, never from the scratchpad, and don't delete the shadowing file (other users share this box). (2) Loading a module that defines a `@dataclass` via `importlib.util.spec_from_file_location` needs `sys.modules[name] = mod` **before** `exec_module`, or `dataclasses._is_type` hits `sys.modules.get(cls.__module__)` → `None` and raises `AttributeError: 'NoneType' object has no attribute '__dict__'`.

- **A background agent's `<output-file>` in the task dir is a SYMLINK into `projects/<session>/subagents/agent-<id>.jsonl` — poll it with `stat -L`, or a liveness check reads the LINK.** #121: `stat -c %s` returned **139** (the length of the target path) and `%Y` the link's own mtime, so a bounded wait loop reported "size=139, idle 495s" and concluded the agent had died — while it was actively writing and went on to 685 KB / 137 lines. Any poll of a launched agent's output must use `stat -Lc` (or `wc -l` on the resolved target); a stat that silently describes the link instead of the file is the `verify-launched-work-liveness` failure mode wearing a disguise.

- **A mandate that reaches an agent is not a mandate that is enforced — measure how often it is actually satisfied before trusting it.** The per-ticket card lived in `agents/autopilot-worker.md`, which genuinely IS the worker's system prompt (so this was NOT the `e9d1022` skill-body problem, #104), and workers skipped it anyway for a hundred tickets. The measurement that settled it: extract every worker FINAL MESSAGE from the corpus (`~/.claude/projects/**/subagents/agent-*.jsonl`, 5,180 files → 339 evidence blocks) and count the field — **2 of 339** mentioned `cards_fired`, because the full-authority block had no such field at all while the fork-no-merge variant did. A supervisor "re-verifying every line" of a block with no line for X cannot catch a missing X.
- **`Explore` does not carry the always-on ruleset; `general-purpose`, `ticket-validator` and `autopilot-worker` do.** Live medians: Explore floor ~19.8k against ~113k–148k for the rest, on the same box with the same skill listing and the same 116 deferred tool names. Do not reason about "what a dispatch costs" without saying which agent type — a fleet-wide mean of the floor describes no real dispatch. (This also sharpens the #104 table: the ruleset reaching a dispatched subagent is true for the custom/general types, and NOT true for `Explore` — which is a second, independent reason not to use `Explore` as an introspection instrument.)
- **A lock test that forbids a literal has a SECOND failure mode beyond matching its own prose: forbidding a token the CORRECT FIX must legitimately contain.** The playbook already warns that a `assertNotIn("time.sleep(0.6)")` matches the docstring explaining it. #156 hit the other shape: a lock asserting `not isinstance(payload, dict)` never appears — written to kill a dead conjunction — which no correct implementation could satisfy, because a top-level guard rejecting a non-object payload IS the fix and contains that exact token. Lock the BUG's shape (`not cmd and not isinstance(payload, dict)`), not a token the bug happens to use. Same remedy as before: match a shape the legitimate use cannot take, and report offending LINE NUMBERS instead of `assertNotIn` dumping a 400-line file into the failure message.
- **A NEW module writing potentially-sensitive, arbitrary content to disk (a "rescue"/diagnostic store, not just the existing vault/secrets store) needs the SAME `O_EXCL|O_NOFOLLOW` + owner-only (0700 dir / 0600 file) discipline from day one — it will not be caught by a functional test suite, only by an adversarial review looking specifically for it.** #271: `_draft_rescue_persist`'s first cut used plain `os.makedirs(dir_path, exist_ok=True)` + `Path.write_text()` — umask-default (0775 dir / 0664 files on dev1) with no symlink protection at all, for a store whose whole purpose is capturing arbitrary user-typed text (which can include a pasted credential) on boxes that host foreign uids by design. A full, green, mutation-tested unit-test suite caught none of this — permissions/symlink-safety is not something functional assertions naturally exercise. Any future "write recovered/diagnostic content to disk" feature should start from this repo's OWN established vault-store shape (`os.makedirs(mode=0o700)`, symlink-checked before AND after, `os.open(..., O_EXCL|O_NOFOLLOW, 0o600)`) rather than reaching for the simpler `Path.write_text()` and hoping a later review catches the gap.
- **A bash-level "must be preceded by a command-boundary" prefilter regex is defeated by an inline `VAR=$(...)` assignment, and enumerating assignment shapes is the wrong fix — widen to a plain word-boundary match instead.** #277/#274: `post-record-design-comment.sh`'s prefilter required `gh` to be preceded by start/`;`/`&`/`|`/`&&` (optionally `sudo `/`env `), which the documented stream-account recipe `GH_TOKEN=$(grep -oP '...' ~/.git-credentials) gh issue comment ...` never satisfies — the `$(...)` command-substitution VALUE routinely contains internal whitespace, so a `\S+`-based assignment-value character class (the ticket's own suggested fix) cannot match it at all; correctly parsing it would need a real shell-aware splitter. GNU grep's `\b` is a genuinely correct word boundary (playbook already confirms this elsewhere) and needs no assumption about what precedes the match — `\bgh[[:space:]]+issue[[:space:]]+comment\b` matches regardless of a `VAR=value` prefix (of any shape), `sudo `/`env `, a command separator, or start-of-string, while still refusing a "gh" glued onto another word. Reuse this pattern (drop the boundary-alternation enumeration, reach for `\b`) any time a cheap prefilter's "must start a command" requirement turns out to be defeated by a legitimate prefix shape too varied to enumerate.
- **`GITGH`-precedes segment-scoping (already used for `_blank_gh_text_flag_values`, #280) generalizes cleanly to ANY OTHER extraction that must be confined to "the same invocation", not just flag values.** #280 follow-up (F4): `-R`/`--repo` extraction used to scan the WHOLE `scan_cmd` for a matching string, so a value living in a segment that is NOT the `gh issue comment` invocation at all (an `echo` argument, a different `gh` subcommand's own flag/value elsewhere in the same compound command) was scavenged as belonging to the invocation being classified. Fix: bound each match to its OWN `SEP`-bounded segment (BOTH sides this time — a `-R` can appear before OR after the invocation's own start position, unlike a flag whose GITGH-precedes check only ever needs the LEFT side) before searching that segment alone. Kept deliberately independent of `lib_poll_payload` (a local `SEG_SEP` tuple, not an import) so the scoping survives even when that module fails to import — the existing flag-blanking pass already degrades to "no blanking" on that failure, and repo-scoping degrading the SAME way (rather than silently reverting to the unscoped whole-command scan) keeps both failure modes consistent.
- **Fixing a "naive quote-span regex is not backslash/shell-idiom-aware" defect (#282, the F3 residual #280 deliberately filed rather than fixed in-diff): replace the whole quote-PAIR match with a forward SCANNER that implements real bash word-tokenization, and reuse ONE implementation across every consumer rather than duplicating it.** `hooks/lib_poll_payload.py`'s `BODYFLAG`/`MSGFLAG` and `hooks/post-record-design-comment.sh`'s own `_TEXT_FLAG_VALUE_RE` all shared `(['"])(.*?)\1`, which closes the "value" at the FIRST quote character seen — escaped or not — and cannot see past the FIRST fragment of the shell's `'"'"'` single-quote-splice idiom (the standard way to embed a literal `'` inside what bash treats as ONE continuous single-quoted argument: close-single / open-double-containing-a-lone-quote / close-double / reopen-single — four fragments concatenating with zero whitespace between them). Fix: `_shell_word_end(text, start)`, given the position of the OPENING quote, scans forward — no escaping inside single quotes, `\` escapes the next char inside double quotes, and (the key insight) an immediately-following quote character with NO intervening whitespace is a CONTINUATION of the same logical word, not a new one. Both regexes were rewritten to match ONLY up to the opening quote (dropped the `.*?...\1` capture), and `post-record-design-comment.sh`'s consumer calls `lib_poll_payload._shell_word_end` directly (it already receives the module as a parameter) rather than reimplementing the scanner — closing the "needs a blast-radius audit across four dependent hooks" concern #280 raised by construction: there is only ONE implementation to ever audit.
- **Diagnosing an orphaned/dead dispatched async `Agent`: `TaskStop(task_id=<the id from the launch tool_result>)` returning `"No task found with ID: X"`, cross-checked against its `<output-file>`'s own `stat` (tiny — e.g. 139 bytes — and unchanged by `mtime` for far longer than the task should plausibly still be working) is decisive, corroborating evidence that the dispatch died — most plausibly across a session-limit reset (a coordinator message reporting "session limit sa práve resetol" mid-wait is the tell) — rather than "still working, just slow".** #354: two async dispatches (a `Skill({skill:"review"})` fork and a `general-purpose` requesting-code-review agent) both went unresponsive for 2+ hours of bounded foreground waits; `TaskStop` on both ids came back not-found, and both output files sat at 139 bytes with `mtime` 2+ hours stale — the correct recovery was to treat both as dead (never try to read the orphaned output file's content — "don't peek" still applies to a dead dispatch, not just a live one) and re-dispatch a FRESH, self-contained `general-purpose` review with the same digest, which then completed normally in ~7 minutes. Never keep bounded-waiting on a dispatch past this evidence threshold hoping it resumes on its own.

- **`/architecture-check` (`skills/architecture-check/SKILL.md`) is the existing, ALREADY-BUILT periodic deep-audit tool for this whole ticket's concerns** — a user-invoked, manual-only multi-agent fan-out review producing a tiered issue roadmap. Recommended cadence: after each new model release (a genuinely different code-generation baseline is worth a fresh structural pass) and after each major feature wave (several tickets landing close together, the exact "5 days debugging why a simple thing is broken" pattern #414 was filed to prevent). It is NOT auto-run by anything (`docs/superpowers/specs/2026-05-30-architecture-check-design.md`'s own explicit "manual only" trigger) — a project's own gatekeeper/maintainer runs it by hand; airuleset's rules reach a target repo's own code via the normal fleet push, never by this repo running the audit FOR another repo.
- **A `mock.patch.object(airuleset, "<internal>", ...)` test seam breaks SILENTLY-in-the-wrong-direction the moment the patched name's CALLER moves to a new module — the patch still applies (the facade attr exists) but the moved body resolves the bare name in its OWN globals, so the test exercises the REAL implementation.** #433 cluster K hit exactly 3 such tests (`test_autopilot_lock.py`: `_proc_parent_pid`/`_proc_comm`/`_pid_alive` patches behind `_campaign_pid`/`sweep_...` calls) — all three FAILED loudly here (the real /proc walk returned different data), but that is luck, not a property: a patch whose real fallback happens to return the expected value would pass while testing nothing. On every future cluster extraction, grep the cluster's test files for `patch.object` on any MOVED name BEFORE running the suite, and repoint the binding (`self.airuleset = <new module>`) rather than the individual patch lines — direct-call and `assertIs(SUBCOMMANDS[...], ...)` identity assertions stay facade-covered and need no change. Companion rule to the #1341 hand-enumerated-corpus entry above: that one rots on file LISTS, this one rots on patch TARGETS.
- **Splitting a path-scoped `.claude/rules/*.md` monolith that got huge and kills sessions (#482):** route by BLOCK, never by `##` section — such a file is a FLAT gotcha list under loose chronological headers, so its `##` sections are cross-area grab-bags (a marketplace bullet lived mid-"Reading a transcript"). Do it as a verbatim line-range PARTITION with a RECONSTRUCTION assert (every body line → exactly one destination; concatenating all blocks in original order must equal the original body byte-for-byte) — that assert, not careful hand-work, is what guarantees zero content loss. Small areas go fully inline into `.claude/rules/internals-<area>.md` (narrow `paths:`); big areas (watchdog/hooks were 245/219 KB) keep the newest blocks up to a ~43 KB budget inline and send the overflow + all narrative to an on-demand deep archive at `.claude/rules-reference/internals-archive.md` (**NO `paths:` frontmatter AND a DIFFERENT dir** so the rules mechanism never scans it → never auto-injects). Keep the ROUTER at the OLD filename (`airuleset-internals.md`) with the original broad `paths:` so `CLAUDE.md`/tests that name it stay valid and every session still gets a small routing table + the general conventions; the union of all new files' `paths:` must equal the original set (no behavioral expansion). **Two traps that bit:** (1) `.gitignore` here is `.claude/*` + `!.claude/rules/` — `.claude/rules-reference/` is therefore IGNORED, so the 615 KB archive silently would NOT commit (catastrophic content loss on merge) → add `!.claude/rules-reference/`; (2) the recurrence-guard ratchet must use a BYTE cap, not lines — the monolith was only 1575 lines but 973 KB (~616 B/line), so a line cap would never have caught it (`size_ratchet.py` `rule_bytes`, flat 51200-byte CAP, distinct from the .py freeze-at-current semantic because rule files are DESIGNED to accrete playbook lessons up to the cap then archive their oldest). Content-asserting consumer tests repoint to the UNION of split surfaces (no-loss checks) or the specific per-area file (auto-load checks); force load-bearing-but-old content to its area file with an explicit line-range override (pre-write-script-check → hooks, the #130 measure cycle → burn) so "must auto-load on area X" tests stay honest.
- **A dispatch that says "CREATE skill X" whose DOMAIN is already owned by an existing managed skill → STEP-0 catches it, and the correct move is EXTEND, never a parallel new skill (rule intake gate step 3).** #480: dispatched to "create the Cloudflare credential taxonomy skill", but `ls skills/` + `grep -rilE 'cloudflare|cfat' skills/ modules/ rules/` found `skills/cloudflare-api-tokens/SKILL.md` (from a DIFFERENT ticket #443, already in `SKILL_NAMES` + its own test) — two skills both matching "cloudflare token" would compete for the same load-trigger and duplicate the verify-lie/never-by-length/secrets content. Extend it instead (the ticket author had also explicitly permitted "rozšírenie existujúceho CF modulu"), and RECORD the deviation-from-literal-"create" reasoning in the design comment so the supervisor's re-verify sees why "extend" ≠ "create". No new `SKILL_NAMES` entry is needed when extending. **Mechanical consequence: growing an existing skill's TEST file past its `tests/size_ratchet.json` ceiling requires a same-commit HAND-bump of that ONE number** — `scripts/size_ratchet.py --update` never RAISES a ceiling (only shrinks tighten it), so `--check` fails until you hand-edit the JSON (the sanctioned "deliberate, reviewed growth" path, justified in the commit message).
- **A content-lock test on a skill QUERY that asserts against a WINDOW around the query has NO teeth on the query when that same window also contains the "why" PROSE naming the tokens — a partial revert of ONLY the `gh issue list --search "..."` line (leaving the explanation intact) passes green (#498).** The existing "assert the STATEMENT, never the substring" family (#113/#156, this file) covered forbidding a literal that a comment mentions; #498 is the DUAL: REQUIRING a token (`needs-gatekeeper`) whose only guaranteed occurrence in the asserted window is the paragraph explaining the query, not the query itself. A fresh-context adversarial reviewer PROVED it by mutating only the query line to rfr-only and watching all window-based assertions stay green. Fix: extract the actual query STATEMENT line and assert on IT — iterate `read(SKILL).splitlines()`, pick the line by a token NOT under test (`s.startswith("gh issue list") and "--search" in s and "label:stream" in s`, i.e. the stream scope it carries — NEVER by the `needs-gatekeeper`/`ready-for-review` token you are about to assert, or the finder begs the question), then `assertIn` both labels IN that single line. Mutation-verify it: `cp` the skill aside (uncommitted → `cp` restore, never `git checkout`, #488), `str.replace` only the query line to rfr-only with an `assert mutated != src`, run the ONE query-line test, confirm it FAILS, restore. Keep the coarse window/whole-file assertions too (they still fail a FULL revert), but the query-line test is the only one with teeth against a partial (query-only) drift back to the bug.
- **Durability-backup push of a worktree worker's branch (#503) — four reusable sub-lessons.** The worker builds work as LOCAL commits and (contract) never pushes to the integration flow; the supervisor merges from the local branch ref, so origin is unwritten until integration — the account-cap-death window. Fix = a CI-neutral BACKUP push after each commit. (1) **A push to any git ref OUTSIDE `refs/heads/*` and `refs/tags/*` (e.g. `refs/autopilot-wip/<branch>`) triggers NO GitHub Actions workflow on any GitHub repo, whatever its push-trigger config** (GitHub's `push`/`create`/`delete` events fire only for branches+tags — verified GitHub docs + community #48858). So a durable backup to a custom ref namespace burns ZERO CI with no per-repo reasoning and no branch-ignore edit — reuse this for any "durable copy on origin without burning CI" need. (2) **A `git push` hook exemption MUST anchor on the push DESTINATION refspec (`:refs/x/` or `--delete`/`-d refs/x/`), NEVER a bare `grep -q 'refs/x/'` over the whole command** — a bare substring false-exempts a real push that merely MENTIONS the ref in a commit message / echo / trailing comment, silently skipping the local gates (both #503 adversarial reviews reproduced this). (3) **When adding a `git push` gate/exemption, enumerate ALL FOUR push-gating hooks: `pre-push-lint.sh`, `pre-push-test-check.sh`, `pre-push-base-sync.sh`, `block-test-skips.sh`** — a review caught `block-test-skips.sh` missed from a 3-of-4 enumeration. (4) **Separate the DURABILITY layer from the DELIVERY push across authorities** — the exempt WIP backup is the uniform durability layer for EVERY worktree worker (full / fork-no-merge / branch-merge); each authority's real delivery branch (supervisor-merged local branch / fork-branch hand-off / integration PR) stays a CLEAN push per its normal flow, so a reduced-authority worker's real (gated, CI-triggering) branch is never pushed mid-work just for durability. Content-lock teeth caveat (extends #498/#500): a bullet that names a token TWICE (an authority name in both a coverage clause and a delivery clause) gives a partial revert NO teeth — lock a UNIQUE operative phrase ("regardless of authority"), not the recurring name.

- **Worktree-isolated worker: the command checker REFUSES heredoc-python (`python3 - <<'PY'`), any `cmd > file` redirect, and multi-clause inline python — "too complex to verify it stays inside the worktree" (#513 guard).** Every non-trivial probe/repro/measure must be a SCRATCH `.py`/`.json` file under the dispatch scratchpad, run plainly (`python3 /abs/scratch.py`); a compound command is only accepted when it is a bare pipeline of simple commands with NO file redirect (e.g. `inotifywait … ; echo rc=$? ; stat -Lc %s <path>` is fine, but appending `>out.txt` trips it). - **Extending a skill for a `hooks/situational-triggers.conf` trigger: watch the CO-FIRE injection budget, and prefer a COMPANION body file over growing the skill body (#521).** `inject-situational-rule.sh` caps total injected bodies at `MAX_TOTAL=14000` per tool call and DEFERS (marker left unset → loads on the topic's own next action) any body that would push the running sum over once a prior chunk is in.
