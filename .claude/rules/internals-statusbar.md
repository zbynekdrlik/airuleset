### airuleset internals — statusbar / footer

Hlbší archív airuleset-internals je v `.claude/rules-reference/internals-archive.md` (on-demand). NOVÉ statusbar / footer lekcie pridávaj SEM.

- **A tmux pane's STATUSLINE is frozen at its LAST RENDER — an idle Claude session keeps showing the usage/limit numbers from its last turn, never live account state.** Reading current weekly/session usage % from a pane's footer is WRONG and produced a real misdiagnosis: on 2026-07-25 three panes showed 93% / 47% / 4% weekly for what was actually ONE account plus one separate box (each pane's statusline was simply stale from whenever it last rendered). The authoritative source is the watchdog's own usage cache, `~/.claude/airuleset-usage-cache.json` (written by `watchdog.write_usage_cache`, read by `cmd_burn`/the statusline segment) — read THAT for account state, never a pane capture.
- **Attributing a fixed prefix: dispatch CONTROLLED PROBES with an identical trivial prompt, one per agent type, and difference them.** Three probes with the same 22-char prompt, one request each, same box and repo: `Explore` **10,392**, `general-purpose` **80,372**, `caveman:cavecrew-investigator` **69,993** (no skill listing, no deferred-tool list, 4 tools). The gp-minus-Explore delta of **69,980** is the always-on ruleset block — same skill listing and same deferred-tool set on both sides, so nothing else can account for it — and against the 215,358-char `@import` closure that implies 3.08 chars/token. **The honesty trap:** once the rate is calibrated from that delta, `Explore`'s residual necessarily equals `general-purpose`'s (7,787 both), so it is NOT an independent check — say so. The investigator probe is what bounds the block from below (it carries the ruleset and totals 69,993, leaving implausibly little for its own base prompt), giving **~67k–70k tokens** rather than a false point estimate. Cost of the whole calibration: three ~2-second `haiku` dispatches.
- **`gh issue list --search` ANDs space-joined qualifiers ACROSS QUALIFIER TYPES — it cannot OR two different qualifier types (e.g. `assignee:X label:Y`) — so a caller needing a UNION across DIFFERENT qualifier types (assigned ∪ authored ∪ stream-labeled) must run one gh query PER QUAL and union the results in Python, never join the quals into one `--search` string.** (M8/M-6, rounds 2-3 of #181: the comma-OR that DOES exist is a **`label:`-family** behaviour — `label:a,b` matches either label, verified live (`label:stream:montalu label:stream:simap` → 0 vs `label:stream:montalu,stream:simap` → 26) — and it does NOT generalise: `assignee:` has no comma-OR. So the claim is about combining DIFFERENT qualifier types, never a blanket "search can't OR at all", and equally never "you can always comma-OR within a qualifier".) #181: the `/goal` reduced-authority stop-proof hardcoded `--assignee @me`, which silently resolves to `0` on a shared-gh-account stream box (montalu/marek/simap — `@me` there is the maintainer, matching nothing assigned) while the footer's own `_slice_quals()` already got this right via per-qual queries + a Python `set` union. The tempting one-line fix — append `label:stream:<me>` alongside `--assignee @me` in the SAME `--search` string — was rejected precisely because it ANDs the two constraints together instead of ORing them, which would have fixed montalu while silently NARROWING david's real union into an intersection (a different false-empty bug on a different box). The general fix: expose the union as ONE small CLI subcommand (`airuleset.py slice-quals --count`/`--list`) that wraps the existing per-qual-query-and-union function and prints only the RESULT — this also SHRANK the `/goal` proof command by ~44 characters (a hand-rolled `--search` fragment plus its own `--jq 'length'` versus one short CLI invocation), which matters because the reduced-authority templates sit within ~10-40 characters of Claude Code's 4000-char `/goal` condition cap (#169).
- **A "make this guard refuse instead of guessing" fix is not finished until you enumerate EVERY caller-context that can reach the guessed branch, not just the one the ticket's own reproduction hit.** #181 round 2: the round-1 fix made `_slice_quals()` login-aware (good), but `cmd_slice_quals` — the NEW CLI wrapping it — never itself checked `resolve_authority()`, so the exact false-empty-`0` shape simply moved one call frame outward (live-reproduced on dev1: 29 real open tickets, `slice-quals --count` printed a clean `0`, exit `0`). A second, independent gap sat right next to it: a SHARED-account slice's only signal is ONE label, and gh returns `[]`/exit-0 for a label that was merely forgotten — the same "plausible-looking zero" shape the whole mechanism exists to prevent, just relocated to a different precondition. The fix pattern for any future "refuse rather than guess" guard: (1) refuse at the EARLIEST possible point (`resolve_authority()` before building any query, not after), and (2) when a zero result rests on exactly ONE piece of unverified evidence (one label, one flag, one file), validate that evidence's own EXISTENCE before trusting its absence of hits — here, confirm the label is actually a real label on the repo (`gh label list --search`) AND that an unrelated cross-check query (`involves:@me`) itself succeeds, so a broadly-broken `gh` can never masquerade as "nothing to do here".
- **Before "fixing" two counters that read differently, check whether they are answering DIFFERENT QUESTIONS ON PURPOSE — forcing them numerically equal can reintroduce the exact bug a sibling mechanism exists to prevent.** #181 round 2, I3: a review flagged that the footer's `Issues 0 · gk 5` (an ACTIVE/handed-off-to-gatekeeper PARTITION, for display) disagreed with `slice-quals --count`'s raw open-issue count (which still counts a handed-off ticket, since it is genuinely still OPEN on GitHub). Making them match by subtracting `gk` from the `/goal` proof would let the proof read `0` while a ticket the gatekeeper has NOT yet closed sits open — precisely defeating the review-watch state (`/goal` STOP CONDITIONS) that exists specifically to keep the loop alive until such a ticket is truly closed. The fix here was NO code change: document the intentional difference and lock it with a regression test (a handed-off-but-open ticket must still be counted), rather than implementing a "fix" for a correctly-designed divergence. Same session's I7 finding is the test-quality mirror of this: the existing regression lock for `cmd_slice_quals` only asserted `_slice_quals()`'s OWN (unrelated, unchanged) return value, which is byte-identical before and after the fix it was meant to guard — replaced with a test that mocks `_slice_quals()` itself (a sentinel qual) and proves the CALLER genuinely consumes it, which fails against a reimplementation that quietly stops calling the shared function.
- **A partition that answers "which population am I SHOWING" is not the partition that answers "what must I FINISH before I may stop" — reusing one as the other is a defect class, and it looks like a single-source-of-truth WIN while you do it.** #181 round 3: `_core_search_excl()` was written for the footer's display question, and reusing it as the `/goal` stop-proof's obligation partition dropped exactly the tickets a full-authority box is the ONLY one able to move (live on `zbynekdrlik/odoo-erp`: 41 core, 54 obligation, 84 whole-repo — #2396/#2377 carry `stream:montalu` AND `needs-gatekeeper`, invisible to a core-only count, actionable by nobody else). The tell that you are in this situation is a partition defined by OWNERSHIP being used to answer a question about RESPONSIBILITY: ownership excludes what someone else owns; responsibility must still include what someone else owns but only you can act on. The fix is a third set (`_obligation_quals` = the ownership partition UNIONED with the labels that mean "only this box can act"), never collapsing the two into one number — the display and obligation answers are documented as deliberately different and locked by a test, the same resolution round 2 reached for the footer-vs-`slice-quals` divergence.
- **Proving RED for a multi-file change already written: `git stash push -- <only the implementation files>`, run, `git stash pop` — then count how many failures are `AttributeError`.** A failure that is only "the new function does not exist yet" proves nothing about behaviour, and this repo has shipped that tautology once. Grep the RED run for `AttributeError` and rewrite every test that produces one so it drives an EXISTING entry point instead: assert the CLI refuses rather than that a new exception class exists; assert the command's own printed quals rather than a new constant's contents; wrap `assertRaises(NewError)` in a `try/except Exception` + `self.fail(...)` so the pre-fix path fails on the guessed VALUE rather than on the missing name. Target for a round like this: zero of N.
- **A fixture that must measure BOTH the old and the new implementation has to serve both query shapes.** The `_gh_out` fake for `core-quals` returns a count string when the argv carries `-q length` (the round-2 one-query form) and JSON rows otherwise (the per-qual union form), so the pre-fix run fails on the NUMBER (`'2' != '5'`) instead of on a JSON parse error. A fixture that only serves the new shape makes RED look behavioural when it is really a parsing artefact.
- **Verifying a repo-scoped CLI against a repo that is NOT checked out on this box: `mkdir /tmp/x && git init && git remote add origin https://github.com/<owner>/<name>.git` is enough** — `gh` resolves the repo from the git remote, so every `gh issue list` in that directory answers for the real repo with no clone, no auth change and no new `--repo` flag on the command under test. Used to measure `core-quals --count` against `zbynekdrlik/odoo-erp` from dev1. Note the trap on cleanup: `rm -rf` the directory you are standing in and the next command dies with `getcwd: cannot access parent directories` — `cd` out first.
- **A guard written as "extra validation for THIS caller's zero" instead of "a precondition on trusting the RESULT" will be re-broken every round, and the tell is that the guard sits behind a branch describing its CALLER rather than its SUBJECT.** Four rounds of the #181/#164 false-stop class ran on exactly this: round 1 fixed `_slice_quals`, round 2 the same bug one frame out in `cmd_slice_quals`, round 3 built the correct probe (`_search_index_healthy`) and wired it into ONE of the two stop-proof commands — and even there nested it inside `if not seen and len(quals) == 1 and quals[0].startswith("label:")`, the SHARED-account qual shape, so the OWN-account 3-qual shape in that same command skipped it too. Two live reproductions in round 4, both against shipped code: `core-quals --count` printed `0` with 110 open issues, and `cmd_slice_quals` printed `0` for david's 3-qual slice. The fix that finally holds is a helper whose NAME is the property (`_refuse_unless_empty_is_trustworthy`), called by every command at the same point, with the branch conditions moved INSIDE it. When reviewing any "we added a guard" change here, read the guard's enclosing `if` out loud: if it names a caller, an identity, or a qual shape rather than the thing being trusted, it is the next round's CRITICAL.
- **Adding a refusal to a command that ALSO serves filtered queries: ask what the filter changes about the meaning of "empty" — a guard that is right for the unfiltered question is a FALSE REFUSAL for the filtered one, and a false refusal spins an autonomous loop forever, which is not a safer version of stopping it wrongly.** Self-found in round 4 after the fix was already committed: the new hand-off-labeller gate fired on ANY empty result, so `core-quals --list --extra "label:prio:bounce"` — the bounce-lane SEED, whose honest answer is routinely "none" — refused (rc 1) on the one repo enrolled in the cross-stream flow whenever its labeller was unhealthy, breaking Step 3.1. Confirmed live before writing the lock. The scoping rule: a guard validating the EVIDENCE a stop-proof rests on belongs on the UNFILTERED query only (`if not seen and not extra:`); a guard validating the MECHANISM that produced the rows (here the search index) stays unconditional, because a dead index makes a filtered answer just as meaningless. Ship the narrowing with a companion control test asserting the unfiltered path is still gated, or the narrowing silently becomes a deletion.
- **Rendering an OLD version of `CAVEMAN_SHIM_CONTENT` for a genuine before/after comparison: extract the r-string via regex from `git show <sha>:airuleset.py`'s TEXT, never `exec()` the whole historical module.** `exec(compile(old_source, ...), ns)` dies with `NameError: name '__file__' is not defined` the instant the old module hits its own `REPO_DIR = Path(__file__).resolve().parent` — module-level `__file__` genuinely does not exist for a string compiled and exec'd this way, and there is no clean workaround short of faking a whole loader. `re.search(r'CAVEMAN_SHIM_CONTENT = r"""(.*?)"""', src, re.S)` sidesteps this entirely: it needs no execution context at all, just the raw text `git show` already returned. Used live for #223's before/after evidence — the OLD bash-level shim rendered against the CURRENT `statusbar.py` (imported fresh via `sys.path.insert` at runtime) is a legitimate, honest before/after for a change scoped to the bash wrapper specifically, since the Python segment functions it calls into are shared and were already deployed either way.
- **A NEW statusline segment sitting FIRST in `CAVEMAN_SHIM_CONTENT`'s shared `try:`/`except Exception: pass` block turns any crash in THAT segment into a crash of every segment composed AFTER it — position inside the block decides blast radius, and the block itself has zero per-segment isolation.** #133's adversarial review: a hostile-but-realistic non-string `model.id` (int/float/list/dict/bool — all valid JSON scalars a statusline stdin payload can legally carry) reached `burn.tier()`'s `.lower()` uncaught; because the new `model_segment()` call was inserted FIRST (right after `import statusbar`), the crash silently deleted `sub`/tickets/questions/ctx/account-email too — a 6-segment fleet-wide outage from one malformed payload, triggered live through the real rendered shim. `context_cost_segment` has the identical latent `.lower()`-on-non-string flaw (its own `model_id = ((payload.get("model") or {}).get("id")) or ""` has no `str()` coercion either) but sits LAST, so its own blast radius is one segment — the repo's own FREEZE policy ("fix only what has actually failed") means that pre-existing sibling gap was reported, not touched. Lesson for any FUTURE segment addition to this shared block: coerce every payload-derived value to its expected type (`str()`, `int()`, `isinstance` guard) at the point it enters the segment function, and place a genuinely new/unproven segment LAST in the block (or give it its own `try/except`) rather than first — a proven segment crashing takes out only what comes after it in source order.
- **A per-stream ORIGIN marker for a SHARED gh identity must live in a namespace DISTINCT from the OWNERSHIP label, even when both are conceptually "which stream does this belong to" — reusing the ownership label breaks every consumer that keys on it for a different question.** #191: the sub-dev footer's `gk` bucket couldn't see a stream's own handed-off tickets once relabelled away from `stream:<user>` (the ownership label, which a SHARED-gh-identity stream's slice is `label:stream:<user>` ALONE — `_slice_quals`). The first fix had `cmd_gk_request` best-effort apply `stream:<user>` as the origin/provenance marker too, on the reasoning "it's the same information". An adversarial review caught the CRITICAL consequence: `stream:<user>` is read by THREE independent ownership consumers (`_slice_quals`'s own slice query, `_core_search_excl`'s full-authority exclusion, `_row_action`'s implement/action-only classifier) — tagging a `needs-gatekeeper` ticket (by definition "an action the stream cannot perform itself") with it made that ticket PERMANENTLY part of the stream's own `/goal` stop-proof slice, so `slice-quals --count` could never reach 0 while one stayed open (#181's never-stops class at a NEW address) and the autopilot worker would be told to `implement` a request it structurally cannot. Fixed with a genuinely distinct namespace (`handed-by:<user>`, per the issue's own suggested candidate #2) that the three ownership consumers are structurally blind to — recoverable in the footer, invisible to the stop-proof and the core count. General check for any future "mark WHO this belongs to, for a DIFFERENT reason than the existing ownership label" feature: enumerate every consumer of the label you're tempted to reuse and ask whether ANY of them treats presence as "must be finished/owned/implemented by this stream" — if so, a same-named marker for a "can't be implemented" fact is a landmine.
- **A grep-verified, PRE-EXISTING gap a sibling stream already has (found while registering a NEW one) is documented with an honest comment, never silently widened, under this repo's own FREEZE** ("the same defect exists in N more places" is not fixed pre-emptively — confirm with `git log --oneline --all --grep="#<sibling-ticket>" -- <the file in question>`: if it never touched that file, the omission was never a documented decision, just an unrevisited gap). #300: `watchdog/__init__.py`'s `_REDUCED_STREAM_USERS` tuple never gained `simap` when #143 landed (confirmed — no #143 commit touches `watchdog/__init__.py` at all), so both `simap` and the new `miva1` are silently treated as FULL-authority by `_gkreq_supervisor_root`/`_bounce_quals`, scoped to `_CROSS_STREAM_REPOS`. Neither has ever produced a real incident from it; widening the tuple now (for a stream this ticket didn't ask about) would be exactly the pre-emptive fix FREEZE forbids — a one-line honest comment at the tuple's definition is the correct, cheap, zero-behavior-change alternative.
- **A cross-stream `prio:bounce` lifecycle needs TWO gatekeeper-side mechanisms with DIFFERENT scopes, not one blanket "the gatekeeper's loop holds while any bounce is open" rule — conflating them either inflates a stop-proof or leaves a real liveness gap.** #307 (2026-08-08): the full-authority `/autopilot` loop's `core-quals` stop-proof (`MAINTAINER_ACTION_LABELS`) counts ONLY `needs-gatekeeper`/`ready-for-review` — a BARE open `prio:bounce` (sub-dev still fixing, no hand-off yet) is the sub-dev's own work and correctly does NOT hold this loop; it used to also carry `prio:bounce`, which inflated a real `core-quals --count` 63 -> 77 (all 14 extra `stream:david`'s own bounce tickets) and could let a full-authority `/goal` SELECT a ticket it must never implement. `/process-subdev`'s SEPARATE per-stream `/goal` (its own DONE line: "Also not-done while any open `prio:bounce` ticket of this stream awaits a sub-dev fix or a re-handoff awaits my re-review") is UNCHANGED and is the mechanism that actually holds through a bounce's WHOLE lifecycle and picks up the re-hand-off — a fresh-context adversarial review caught the first-pass fix's own rule-4 rewrite ("resuming once ready-for-review reappears") naming NO real mechanism, which would have been a genuine liveness gap had `/process-subdev` not already covered it. - **The #300 `_REDUCED_STREAM_USERS` "leave it out, honest comment, per FREEZE" precedent (see the #300 bullet above) does NOT transfer to a new stream whose OWN onboarding ticket states it works on a `_CROSS_STREAM_REPOS` member — that carve-out is specifically for UNCONFIRMED involvement (simap/miva1: no ticket text ever said they touch odoo-erp), not for a stream the ticket explicitly describes as a clone of one already in the tuple.** #326-review MAJOR (fresh-context adversarial review, fable): the first onboarding pass for david2/david3/david4 copied the #300 comment's REASONING onto a case that doesn't match its premise — #326's own ticket body says the three accounts are provisioned "for the odoo-erp repo" as clones of `david` (already in `_REDUCED_STREAM_USERS`), a known, ticket-scoped fact confirmable by reading `gh issue view <N> --json body`, not a speculative guess FREEZE is meant to block. - **Two code paths computing "the name of the same target" independently (a live-pane path using `os.path.basename(cwd)`, a no-pane-fallback path using the tickets-status cache's own origin-derived repo name) can silently diverge for the SAME real repo whenever the checkout directory name differs from the repo's origin-derived name — making a dedup/reset mechanism keyed on "did the name change" structurally DEAD for that repo forever, since the two paths never even compute the same key.** #353 (job 11's gk-request backstop, MAJOR-3): live on dev1 for 3 real repos including `odoo-slovnormal` (checkout dir name) vs `odoo-erp` (origin-derived name), confirmed against the box's own real cache. Fixed by preferring the ALREADY-COMPUTED cache name for a pane target's root too (no new subprocess, no new read) rather than keeping two independent name-derivation paths alive side by side. Reusable check for any future job that resolves "the name of a target" from two different code paths (a live-pane branch and a no-pane-fallback branch): verify both branches produce the SAME string for the SAME real target before trusting a name-keyed dedup across both.
- **A round-dispatched WORKTREE worker's own branch can be MERGED into `main` by the supervisor WHILE the worker is still mid-session — not just the already-documented shared-non-worktree-tree variant of this phenomenon.** #378: mid-ticket, `git fetch origin && git log --oneline HEAD..origin/main` showed a merge commit whose SECOND PARENT was the worker's own local commit hash verbatim (`git merge-base --is-ancestor <own-HEAD> origin/main` returned true) — proof the supervisor had already pulled the worktree branch straight from the shared `.git` (exactly as `two-branch-workflow.md`'s worktree-mode doc says it will, "does not need your worktree to still be present") and merged it, THEN layered a follow-up commit resolving a decision (Discord routing) that had been explicitly out of THIS worker's scope at dispatch time but got answered by the user mid-session. Consequence: a pre-existing, unrelated regression test (`TestStreamAuthorityHasNotifyRouting`) that legitimately needs BOTH halves together failed on the worker's OWN (older) branch tip — not a real bug, just evidence the branch was stale relative to `main`. Recovery, safe because it is READ-ONLY plus a fast-forward of the WORKER's OWN local ref (never a push, never a merge INTO main): `git fetch origin` again, confirm `git merge-base HEAD origin/main` equals the worker's own HEAD (i.e. the worker's branch is a strict ancestor — a genuine ff-only case, not a divergence), then `git merge --ff-only origin/main` to catch the local worktree up for accurate final verification. This generalizes the existing "shared batch-dispatch tree can show concurrent supervisor activity" lesson to the WORKTREE-isolation case: before concluding a full-suite failure is a real regression, `git log --oneline HEAD..origin/main` to check whether `main` has simply moved past the worker's own branch tip since dispatch — a plausible-looking "one pre-existing test broke" is often just staleness, and the diagnostic is one command, not a debugging session.
- **A synthetic "goal-armed" pane-capture fixture needs the `◎ /goal` indicator glued onto the SAME line as the rest of the managed statusline (e.g. `"  ctx ███░  caveman:lite  ◎ /goal active\n"`), never on its OWN standalone line — a standalone indicator row (`"❯ \n  ◎ /goal active\n  ctx ...\n"`) is NOT `_is_bottom_chrome`-recognized on its own (it matches none of the chrome shapes: not agent-strip, not a statusline segment by itself, not a border), so it breaks the bottom-up chrome peel that `_classify_boundary`/`_find_input_box_from` use to LOCATE the input box in the first place — the whole capture reads `kind="busy"` instead of `kind="input"`, for a completely unrelated reason than the one being tested.** #403's own first-draft `GOAL_ARMED_CAP` fixture hit this; the real render CC produces (per `pane_goal_armed`'s own docstring) puts the glyph on the `ctx …` statusline row itself, which `_is_bottom_chrome` already recognizes via its legacy `startswith("ctx ")` branch regardless of what else is appended to that row. - **The fleet shares ONE GitHub account = ONE 5000/h GraphQL bucket, and the empirical `gh`-shape → rate-limit-bucket mapping (measured with `GH_DEBUG=api`, #370, 2026-08-14) is NOT what the command names suggest — reuse it before ANY future quota/gh-cost work rather than re-deriving.** `gh issue list` is `POST /graphql` **whether or not** `--search` is passed (both hit the graphql bucket — the plain listing is NOT REST); `gh repo view --json` is also graphql; `gh api repos/{owner}/{repo}/issues?…` is REST **core** (a SEPARATE 5000/h bucket, near-empty on this fleet); `gh api search/issues?…` is REST **search** (30/min, worse than graphql); `gh api rate_limit` is **FREE** — it does not count against any bucket (verified: `graphql.remaining` unchanged across the call). So "move a heavy periodic list off graphql" means rewriting `gh issue list` → `gh api repos/…/issues` (REST core), never just dropping `--search`; and a NEGATIVE-label search (`-label:stream:X`, `-label:autopilot-skip` — the `_obligation_quals()` core partition) is NOT REST-expressible at all (`/repos/…/issues?labels=` is positive-AND only), so those queries are stuck on graphql.
