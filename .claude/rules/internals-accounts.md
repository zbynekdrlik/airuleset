### airuleset internals — project accounts (#1184 / #1186 / #1190)

- **Layout.** `cli_account_bootstrap` holds THE declaration (`SERVICE_ACCOUNTS`) and the root-script renderer. `cli_account_policy` is the sudo + reach validator leaf. `cli_account_hardening` holds the pure bash/nft/sudoers renderers. The bootstrap file sits at its size-ratchet ceiling, so new validation goes to the policy leaf, never back into the declaration file.
- **Golden locks.** `tests/fixtures/account_render_1186/` holds the fohmixer and claudy sudo+reach sections (`# 3a.` … `# 3c.`), byte-captured from main. Any change to the hardening renderers must keep them byte-identical, or re-capture them in the same commit with a stated reason. Put a new rule behind its feature (`lan_rules` non-empty), so accounts without that feature render unchanged.
- **Test root-only bash without root.** `nft -c` needs CAP_NET_ADMIN and `unshare -rn` is blocked on the controller. `visudo -cf <file>` works unprivileged, so use it for sudoers syntax. For the path/ancestor checks, stub `stat` and `runuser` as bash functions keyed on `${@: -1}`, then run the rendered snippet under `set -euo pipefail`. That covers the ancestor walk and the writable branch, which a real non-root run can never reach, because `runuser` refuses there and the check fails closed.
- **Reach entries are single hosts.** A LAN entry is ONE canonical private `/32`. The venue LAN also carries the password-shared dev boxes, which the fleet table knows only by tailscale IP. The uid reject covers tcp/22 only, so other ports are declared, not restricted. A declared LAN login is a possible `ssh -J` hop to the host's own `newlevel`. That makes it a go-live gate of the live migration, never something the render can close.
- **RED proof for review-fix tests.** After the fix is already in the working tree, run `git archive HEAD | tar -x -C <scratch>`, overlay the new test file, and run pytest there. That proves RED against the last commit without stashing or checking out. Mutation-verify the same way, by editing the export and never the worktree.
- **Migration step: carry the Claude session (#1190).** The checkout, services and secrets moving to the project account do not move the conversation. At cutover, once no claude runs in the old checkout, run `airuleset.py accounts transfer-session <acct> --from-dir <old checkout>` on the host. It is a dry run by default and lists the sessions, `memory/`, the excluded worktree-lane keys and the target. Then run it again with `--render | sudo bash` (or `sudo … --apply`). It copies `<uuid>.jsonl`, `<uuid>/` and `memory/` into `/home/<acct>/.claude/projects/<new key>`, with modes 0600/0700 and the file mtimes kept. Root never reads file content from, or writes into, a path an account controls. `runuser -u <old owner> -- tar -c`, with the owner fixed at render time and root refused, pipes into `runuser -u <acct> -- tar -x`. That lands in a private temp dir inside the target, and each item is then placed with `mv -n -T`. The script `cd /`s first: a `sudo bash` run from the 0700 old home would otherwise break `find`. Stdout carries ONLY a rendered script, and the dry run and every refusal go to stderr, so nothing else can ever reach `sudo bash`. It refuses a live claude under the old dir and any session or memory file the target already has. The owner then resumes with the printed `claude --resume <uuid>` and pastes the path-move note as the first prompt.
- **The jsonl `cwd` field needs no rewrite.** Measured on 2.1.284 under a scratch HOME: both `--resume <uuid>` and the picker find a session by its projects DIRECTORY, even when every line still names the old, unreadable path. The key encodes EVERY non-alphanumeric char as `-`; `cli_account_session.project_key` is the encoder, and a bare `/`→`-` replace is wrong for `.` and `_`. Re-measure it (a throwaway `claude -p --session-id` run under `HOME=<scratch>` plus a private `tmux -L` for the picker) before trusting it on a new major version.
- **Root-script patterns that crossed accounts (#1190, 3 review rounds).** (1) `runuser` keeps root's cwd, and a `sudo bash` started in a 0700 home makes `find -exec … +` abort on "Failed to restore initial working directory", so `cd /` first. (2) An EXIT trap sees `$?` = 0 after a signal unless `trap 'exit 143' TERM` (and INT/HUP) are set. Derive "what was placed" from the tree, never from a counter bumped after the `mv`. (3) `mv -n -T` returns 1 on a skip on coreutils 9.4; `|| true` plus a check that the source is gone is the sound no-clobber. (4) Test the bash mirror of a Python guard fixture-by-fixture through the rendered script, using a PATH `runuser` stub that logs argv and execs the rest. (5) A refused `--render` must write nothing to stdout, because stdout is piped into `sudo bash`.
- **A project account's GitHub API credential (#1190 part 2).** The account gets a 1-hour installation token of the `newlevel-project-accounts` App, scoped to its ONE declared repo. `cli_project_gh_token` mints it on the controller (the App key never leaves it) and delivers it in the issue 888 token-file contract. Declare `github_app: True` next to `repo`. The controller timer `project-gh-token.timer` re-mints every 30 min; `accounts status` shows the expiry or the last failure. Two gotchas. (1) The account's token shim goes to `~/.local/bin/gh-app-shim`, NEVER `gh-upstream`. The rate-guard wrapper execs the upstream BAKED into it, not `gh-upstream`, and `ensure_gh_rate_wrapper` Case 1 un-wraps a `#!` script at `gh-upstream` as #1051 loop residue, deleting the wrapper. `gh-app-shim` is the #1087 chain slot. The installer now also chains in Cases 2 and 4 (fresh / wrap-in-place), so a fresh account never gets a wrapper baked to a token-less gh, but ONLY over this shim (`is_project_shim`, its marker). An odoo-style shim re-resolves `gh` on PATH, and chained under a wrap-in-place wrapper it ends at exit 127 (review round 1 repro). The shim must exec a real BINARY (skip every `#!` file), or it re-enters the wrapper. The wrapper's depth-2 resolver (`_resolve_real_gh`) walks PATH first and falls back to `gh-upstream` only when no real gh is on PATH, and only as a regular, non-empty, non-`#!` executable. Preferring it would switch every chained fleet box to a possibly stale binary (review round 3). Test such chains with a PATH of only the needed tools (`bash`, `dirname`, `grep`, `head`), because a CI runner has `/usr/bin/gh`. Go-live check: `project-gh-token verify <acct>`: as the account, in a login shell, `gh` must be `~/.local/bin/gh`, and `gh api installation/repositories` must list exactly the repo (only a repo-scoped installation token does). (2) Test the delivery by running the rendered remote command locally: a fake `run` that execs `argv[-1]` under a temp HOME with the token on stdin. Build fake tokens as `"ghs" + "_" + …`, because a literal `ghs_…` in a staged test trips `block-sensitive-staging.sh`. A lane's worktree guard refuses a Bash command that assigns HOME, or a compound it cannot prove stays in the worktree; run such smoke checks from a scratch python script.
