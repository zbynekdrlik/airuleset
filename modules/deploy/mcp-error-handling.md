### Windows MCP Error Handling → skill `windows-remote-gui`

**Two contexts, not one absolute rule (#249 — an absolute "NEVER ssh" the codebase must itself violate for headless CI/watchdog paths just teaches workers to ignore it).** An AGENT SESSION with `mcp__win-*` servers configured uses ONLY the MCP tools for anything desktop-dependent (a GUI window, a screenshot, a launch) — if any `mcp__win-*` call fails with connection/timeout/unavailable, STOP all work immediately and alert the user (no retries, no ssh workarounds). A HEADLESS context (CI, a systemd watchdog — no MCP tools reachable at all) may ssh, but ONLY for SESSION-AGNOSTIC operations (file copy, a CLI exe, a process/port/registry query) — NEVER for anything desktop-dependent: session 0 (an ssh shell on Windows) structurally cannot see a session-1 desktop window (`EnumWindows` never returns one), so a `MainWindowTitle`/screenshot/GUI-launch probe over ssh reads EMPTY or fails on a perfectly HEALTHY box, not a broken one — this is the exact physics behind camera-box PR #989's rig-health gate failing 3x live. Full protocol (the litmus test, the sanctioned `schtasks .../it` interactive bridge) moved VERBATIM into the `windows-remote-gui` skill — load it before any Windows-remote work. `hooks/block-destructive-remote.sh` mechanically hard-blocks the GUI-atom-over-ssh shape (and warns on other ssh use) in any project that declares a `win-*` MCP server, so this survives even a reduced-context dispatch.
