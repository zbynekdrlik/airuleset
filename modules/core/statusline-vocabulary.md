### Statusline Vocabulary — "issues N" = the Footer Segment

**When the user says "issues N", "gk N", or "skipped N", they usually mean the airuleset statusline segment at the BOTTOM of Claude Code** (the footer next to the ctx meter) — not a GitHub query for you to invent (user directive, 2026-07-19). The segment's forms:

#367 (2026-08-11) is the THIRD footer simplification round: the user wants exactly ONE live, decreasing number — how many tickets this box still has left before everything is done. DROPPED entirely: the active-run progress ratio (fed by a SEPARATE `autopilot-progress` cache the footer no longer reads at all — that cache still exists for job 20), the `core` suffix, the needs-gatekeeper repo-wide badge (already folded into the obligation set `I N` counts below, so it was pure duplicate decoration), and the excluded-from-core badge. Full pre-#367 history + rationale for every dropped form: `.claude/rules/airuleset-internals.md`.

#512 (2026-08-16) is the parked-segment CONSOLIDATION (owner decision, comment 5308903157): the footer is exactly **5 segments — `I · U · W · gk · skip`** — plus the account-identity block. The EN letter legend the owner asked for: **`I`=Issues** (this box's own WORKABLE work), **`U`=User/you** (everything on the OWNER's court), **`W`=Wait/third-party** (an external event/evidence), **`gk`=gatekeeper** (handed off), **`skip`=skipped** (`autopilot-skip`). The two dispositions that used to be their OWN letters ZANIKLI as segments: the standalone `Q N` ❓-pings badge folds into `U N` (a ticketless ping IS a thing "waiting on the owner"), and the once-planned `A N` (needs-acceptance) was never shipped — `needs-acceptance` folds into `U N` too. Only the RENDER/COUNT changed; the question map (`~/.claude/discord-questions.json`) + the watchdog daily re-ask jobs are UNTOUCHED.

- `I N` (was `Issues N`) — the LIVE **workable** obligation-ticket count for this box (what THIS box must ACTION), always excluding `autopilot-skip` and `ops-channel` (#362, deliberately with NO bucket of its own — `.claude/rules/airuleset-internals.md` has the full rationale) AND the tickets PARKED on the OWNER (`needs-answer`/`needs-decision` since #468, `needs-acceptance` since #512), which move to the `U N` bucket below — plus, since #510, `ops-wait` tickets parked on an external event/evidence, which move to the `W N` bucket — `I` counts Claude's responsibility, `U` counts the owner's: a full-authority (core/gatekeeper) box counts `core-quals` (the CORE partition unioned with every open `needs-gatekeeper`/`ready-for-review` ticket regardless of which stream owns it, since only this box can act on those — the exact set the `/goal` stop-proof already counts, never a parallel derivation, and here a handed-off ticket STAYS counted until actually closed — this box is the one that acts on it); a reduced-authority sub-dev box counts its own UNHANDLED work — `slice-quals`'s own slice (assigned ∪ authored ∪ stream-labeled tickets — or the stream label alone on a shared-gh-identity box) MINUS whatever is already parked with the gatekeeper (`len(mine) - gk`, #391, reversing the prior #367 "full slice, handed-off included" choice: once a sub-dev box has handed a ticket off, it is no longer THIS box's obligation, so the loop and the footer both stop counting it). A `gh` error renders nothing, never a wrong number.
- `· U N` (#468, consolidated by #512) — everything PARKED on the OWNER: open tickets in this box's scope carrying `needs-answer` (ask-and-continue's pinged marker), `needs-decision` (the sleep-window deferral), or `needs-acceptance` (a hand-off the gatekeeper already processed — DONE, OPEN pending the owner's/client's acceptance, "done = client saw it") PLUS the unanswered session ❓ pings that carry NO ticket reference (the merged-in `Q`; a ping whose text references a `#N` ticket is already counted via that ticket's label, so it is NOT double-counted). They LEAVE `I N` (the owner's court to answer/decide/accept, not Claude's to solve — the 2026-08-14 directive "v I by nemali byť tie čo sú Q — nech je jasné kto za čo zodpoveda") and render orange-adjacent, hidden at 0, on BOTH scopes. ONE derivation feeds `I`, `U` and `W`: `cmd_tickets_status` partitions the SAME fetched obligation/slice rows by label (`_partition_workable`, a 3-way split), never a second query, so `I N`, `U N`, `W N` and the `/goal` stop-proof (`core-quals`/`slice-quals --count`, which count WORKABLE only; `--waiting` lists the `U` remainder — each member tagged answer/decision/acceptance/ping —, `--ops-wait` the `W` remainder) cannot drift (#367 lesson); the ticketless ❓ pings are read LIVE at render time (as the old `Q` badge was) and folded onto the label-based count. **#507 precedence preserved:** a `needs-acceptance` ticket that is ALSO a re-hand-off (`ready-for-review`/`needs-gatekeeper`) or a returned bounce (`prio:bounce`) does NOT go to `U` — it stays `gk`/workable respectively (`NEEDS_ACCEPTANCE_GK_OVERRIDE_LABELS`). The loop PARKS on a `U` ticket — never claims "backlog empty" past it, never blocks 🏁 (the same surface-only treatment as `gk N`).
- `· W N` (#510) — tickets PARKED on an external event / evidence: open tickets in this box's scope carrying the `ops-wait` label — an ADVISORY state the SUPERVISOR sets and clears itself with evidence (no auto-labelling), for a ticket that is open + technically "workable" but really blocked on an external event / evidence (multi-day evidence collection, a foreign-session relaunch, an operational confirmation) with NO dispatchable code lane. They LEAVE `I N` exactly like `U N`, but for a DIFFERENT parking reason (an external event, not the user's answer); rendered grey (245, the exclusion-badge family — not this box's urgent workable), hidden at 0, on BOTH scopes. SAME single `_partition_workable` derivation as `U N` (three-way `I`/`U`/`W` over the SAME fetched rows). Surface-only treatment mirroring `U N`/`gk N` EXACTLY: the loop PARKS on a `W` ticket — surfaced (footer `W N` + `core-quals --ops-wait`), never claimed "backlog empty" past, never blocks 🏁. Re-entry (unlike `U N`, whose trigger is the user's routed answer): `ops-wait` has NO automatic re-entry — the supervisor CLEARING the label when the event/evidence lands re-enters the ticket into the workable count, a human action exactly parallel to the user answering a `U` ticket; the ticket is never lost (open + surfaced). **Owner-confirmed W workflow (2026-08-16):** the canonical use is "zisti X od človeka Y cez Odoo discussion" — the working session posts the question into the Odoo Discuss thread, labels the ticket `ops-wait` (it LEAVES `I N` into `W N`), keeps checking that thread as it works other tickets, and when the third party replies it CLEARS the `ops-wait` label and the ticket re-enters `I N`. So `W` = "asked a THIRD PARTY, waiting on THEM", distinct from `U` = "waiting on the OWNER".
- `· gk N` — sub-dev boxes only: own tickets already handed off to the gatekeeper — shown SEPARATELY, no longer a subset of `I N` (#391: `I N` now EXCLUDES a handed-off ticket rather than including it, so `gk N` is the parked count next to it, not a slice carved out of it). Hidden at 0. The signal is the `ready-for-review`/`needs-gatekeeper` LABEL when present (overridden back to unhandled by a `prio:bounce` label — a returned bounce re-enters `I N` immediately), falling back to a direct per-ticket check for a `READY-FOR-REVIEW:` comment when it is not (a fork-no-merge collaborator's own label-add routinely 403s, and the repo's own auto-labelling workflow can independently be broken — the comment is the hand-off's real primary signal either way).
- `· skip K` (was `· skipped K`) — tickets labeled `autopilot-skip` (excluded from `I N`); hidden at 0.
- **`Q N` and `A N` no longer exist as segments (#512).** The unanswered-❓ pings the old `Q N` counted now fold into `· U N` above (deduped by ticket reference); the once-planned `A N` (needs-acceptance) folds into `· U N` too. The question map + the watchdog's daily re-ask jobs are UNTOUCHED — only the footer render changed. A user quoting "Q N" / "A N" means the pre-#512 footer or the folded-in part of `U N`.
- `<email> sub <D.M.>(<Nd>)` — the account identity block, at the very end of the line, ONE unit (both properties of the same `~/.claude.json` → `oauthAccount`, so they belong together). `<email>` is `oauthAccount.emailAddress`, rendered in a readable colour. `sub <D.M.>(<Nd>)` is the monthly subscription-renewal anchor (`oauthAccount.subscriptionCreatedAt`, the next occurrence of that day-of-month), coloured by proximity (green far, yellow near, red on the last day).

**Width budget:** the whole line is fit inside the live tmux pane's width MINUS a reserve for Claude Code's own right-edge indicators (the armed-`◎ /goal` glyph is the live-evidence one — a fully-consumed pane once truncated the statusline clean off the end of the row, misread as "the goal died"). When it would overflow, the LEAST important segments are dropped dynamically, in this order: the account-identity block (email + sub) first, then the caveman tag, then — last resort — just the `ctx` segment's own `~$<cost>` suffix (keeping `ctx <size>` alone). An unmeasurable pane width (no live tmux pane, e.g. outside tmux entirely) never trims anything — the line always renders in full in that case.

The segment renders from a machine-local cache — read it when the user asks about it (never guess, never re-derive differently): `~/.claude/tickets-status/<cwd-key>.json` (refresh: `python3 ~/devel/airuleset/airuleset.py tickets-status --refresh --cwd <dir>`). A number the user quotes that mismatches your own `gh` count usually means a stale cache (TTL 120 s) or the per-stream scoping above — explain, don't dismiss. Applies to all rewordings ("v pätičke", "dole v claude", "ten counter").
