### Statusline Vocabulary — "issues N" = the Footer Segment

**When the user says "issues N", "gk N", or "skipped N", they usually mean the airuleset statusline segment at the BOTTOM of Claude Code** (the footer next to the ctx meter) — not a GitHub query for you to invent (user directive, 2026-07-19). The segment's forms:

#367 (2026-08-11) is the THIRD footer simplification round: the user wants exactly ONE live, decreasing number — how many tickets this box still has left before everything is done. DROPPED entirely: the active-run progress ratio (fed by a SEPARATE `autopilot-progress` cache the footer no longer reads at all — that cache still exists for job 20), the `core` suffix, the needs-gatekeeper repo-wide badge (already folded into the obligation set `I N` counts below, so it was pure duplicate decoration), and the excluded-from-core badge. Full pre-#367 history + rationale for every dropped form: `.claude/rules/airuleset-internals.md`.

#512 (2026-08-16) is the parked-segment CONSOLIDATION (owner decision, comment 5308903157): the footer is exactly **5 segments — `I · U · W · gk · skip`** — plus the account-identity block. The EN letter legend the owner asked for: **`I`=Issues** (this box's own WORKABLE work), **`U`=User/you** (everything on the OWNER's court), **`W`=Wait/third-party** (an external event/evidence), **`gk`=gatekeeper** (handed off), **`skip`=skipped** (`autopilot-skip`). The two dispositions that used to be their OWN letters ZANIKLI as segments: the standalone `Q N` ❓-pings badge folds into `U N` (a ticketless ping IS a thing "waiting on the owner"), and the once-planned `A N` (needs-acceptance) was never shipped — `needs-acceptance` folds into `U N` too. Only the RENDER/COUNT changed; the question map (`~/.claude/discord-questions.json`) + the watchdog daily re-ask jobs are UNTOUCHED.

#526 (2026-08-17) REFINES the `needs-acceptance` placement into a STATE MACHINE (owner ROZHODNUTÉ v3, reversing part of #512's flat "acceptance → U" fold): `U` must be ONLY what Claude asks the owner / what the owner must approve, so acceptance is split by whether the client thread was sent. **(1)** `needs-acceptance`, client acceptance thread NOT yet written+approved-by-owner+sent → **`U`** (a real question on the owner: approve the thread text). **(2)** thread approved + sent → the stream adds `ops-wait` → **`W`** (waiting on the client / third party to confirm). **(3)** client confirms → close with citation. The code fix is an acceptance-scoped precedence override in `_partition_workable`: a `needs-acceptance`+`ops-wait` row routes to `W`, while `needs-answer`/`needs-decision`+`ops-wait` STAY in `U` (a pending owner answer beats a sent thread). #507 precedence (a `needs-acceptance` ticket that is ALSO `ready-for-review`/`needs-gatekeeper` → `gk`, or `prio:bounce` → workable) is unchanged.

- `I N` (was `Issues N`) — the LIVE **workable** obligation-ticket count for this box (what THIS box must ACTION), always excluding `autopilot-skip` and `ops-channel` (#362, deliberately with NO bucket of its own — `.claude/rules/airuleset-internals.md` has the full rationale) AND the tickets PARKED on the OWNER (`needs-answer`/`needs-decision` since #468, and `needs-acceptance` since #512 — split by #526: a not-yet-sent acceptance goes to `U N`, a sent one carrying `ops-wait` to `W N`), which move to the `U N` bucket below — plus, since #510, `ops-wait` tickets parked on an external event/evidence, which move to the `W N` bucket — `I` counts Claude's responsibility, `U` counts the owner's (approve/answer), `W` counts a third party's: a full-authority (core/gatekeeper) box counts `core-quals` (the CORE partition unioned with every open `needs-gatekeeper`/`ready-for-review` ticket regardless of which stream owns it, since only this box can act on those — the exact set the `/goal` stop-proof already counts, never a parallel derivation, and here a handed-off ticket STAYS counted until actually closed — this box is the one that acts on it); a reduced-authority sub-dev box counts its own UNHANDLED work — `slice-quals`'s own slice (assigned ∪ authored ∪ stream-labeled tickets — or the stream label alone on a shared-gh-identity box) MINUS whatever is already parked with the gatekeeper (`len(mine) - gk`, #391, reversing the prior #367 "full slice, handed-off included" choice: once a sub-dev box has handed a ticket off, it is no longer THIS box's obligation, so the loop and the footer both stop counting it). A `gh` error renders nothing, never a wrong number.
- `· U N` (#468, consolidated by #512, refined by #526) — **`U` = only what Claude ASKS the OWNER / what the OWNER must APPROVE** ("čo sa ťa Claude pýta / čo máš schváliť"): open tickets in this box's scope carrying `needs-answer` (ask-and-continue's pinged marker), `needs-decision` (the sleep-window deferral), or `needs-acceptance` **whose client acceptance thread has NOT yet been written+sent** (Claude must still get the owner to approve + send it — a genuine question on the owner; once the stream SENDS the thread and adds `ops-wait` it leaves `U` for `W`, #526) PLUS the unanswered session ❓ pings that carry NO ticket reference (the merged-in `Q`; a ping whose text references a `#N` ticket is already counted via that ticket's label, so it is NOT double-counted). They LEAVE `I N` (the owner's court to answer/decide/approve, not Claude's to solve — the 2026-08-14 directive "v I by nemali byť tie čo sú Q — nech je jasné kto za čo zodpoveda") and render orange-adjacent, hidden at 0, on BOTH scopes. ONE derivation feeds `I`, `U` and `W`: `cmd_tickets_status` partitions the SAME fetched obligation/slice rows by label (`_partition_workable`, a 3-way split; a `needs-acceptance`+`ops-wait` row routes to `W`, a bare `needs-acceptance` to `U`, #526), never a second query, so `I N`, `U N`, `W N` and the `/goal` stop-proof (`core-quals`/`slice-quals --count`, which count WORKABLE only; `--waiting` lists the `U` remainder — each member tagged answer/decision/acceptance/ping —, `--ops-wait` the `W` remainder — each member tagged acceptance/ops-wait) cannot drift (#367 lesson); the ticketless ❓ pings are read LIVE at render time (as the old `Q` badge was) and folded onto the label-based count. **#507 precedence preserved:** a `needs-acceptance` ticket that is ALSO a re-hand-off (`ready-for-review`/`needs-gatekeeper`) or a returned bounce (`prio:bounce`) does NOT go to `U` — it stays `gk`/workable respectively (`NEEDS_ACCEPTANCE_GK_OVERRIDE_LABELS`). The loop PARKS on a `U` ticket — never claims "backlog empty" past it, never blocks 🏁 (the same surface-only treatment as `gk N`).
- `· W N` (#510, extended by #526) — **`W` = SENT, waiting on a THIRD PARTY** ("odoslané, čaká tretia strana"): open tickets in this box's scope carrying the `ops-wait` label — an ADVISORY state the SUPERVISOR sets and clears itself with evidence (no auto-labelling), for a ticket that is open + technically "workable" but really blocked on an external event / evidence (multi-day evidence collection, a foreign-session relaunch, an operational confirmation) with NO dispatchable code lane — PLUS (since #526) a `needs-acceptance` ticket whose client acceptance thread has already been SENT: the stream adds `ops-wait` on send, and `_partition_workable`'s acceptance-scoped override routes a `needs-acceptance`+`ops-wait` row to `W` (tagged `acceptance` in `--ops-wait`, vs `ops-wait` for a pure ops-wait member) — it is now waiting on the CLIENT to confirm, not on the owner to approve+send. They LEAVE `I N` exactly like `U N`, but for a DIFFERENT parking reason (a third party, not the owner's answer); rendered grey (245, the exclusion-badge family — not this box's urgent workable), hidden at 0, on BOTH scopes. SAME single `_partition_workable` derivation as `U N` (three-way `I`/`U`/`W` over the SAME fetched rows). Surface-only treatment mirroring `U N`/`gk N` EXACTLY: the loop PARKS on a `W` ticket — surfaced (footer `W N` + `core-quals --ops-wait`), never claimed "backlog empty" past, never blocks 🏁. Re-entry (unlike `U N`, whose trigger is the user's routed answer): `ops-wait` has NO automatic re-entry — the supervisor CLEARING the label when the event/evidence (or the client's acceptance) lands re-enters the ticket into the workable count, a human action exactly parallel to the user answering a `U` ticket; the ticket is never lost (open + surfaced). **Owner-confirmed W workflow (2026-08-16):** the canonical use is "zisti X od človeka Y cez Odoo discussion" — the working session posts the question into the Odoo Discuss thread, labels the ticket `ops-wait` (it LEAVES `I N` into `W N`), keeps checking that thread as it works other tickets, and when the third party replies it CLEARS the `ops-wait` label and the ticket re-enters `I N`. So `W` = "asked/sent to a THIRD PARTY, waiting on THEM", distinct from `U` = "waiting on the OWNER to answer/approve". **Acceptance SIDE-BRANCHES (#539, 2026-08-18):** besides the main #526 "compose thread → owner approve → send → W" path, a `needs-acceptance` ticket belongs in `W` (via a supervisor-set `ops-wait`) in TWO more shapes that skip the thread entirely — (1) **fix-class**: an owner-ruled NO-THREAD close waiting on an EXTERNAL event (e.g. a foreign-repo fix) — the supervisor adds `ops-wait` WITH evidence and it is `W` at once, no thread ever; (2) **deferred-thread**: the acceptance thread is deliberately DEFERRED to a future event (go-live), parked in `W` with `ops-wait` naming that event. Both are tagged `acceptance` in `--ops-wait` (`_ops_wait_reason`). The third — a `needs-acceptance` waiting on a THIRD PARTY (a client / named person) — is already this bullet's canonical `W` workflow. In every branch the supervisor SETS and CLEARS `ops-wait` with evidence, never auto-labelled — so a bare `needs-acceptance` parked on any external event moves to `W`, never rotting in `U` (the montalu3 `U 15`-with-zero-questions incident). **THIRD branch — CHAINED-I (#539, montalu5):** a bare `needs-acceptance` whose acceptance draft cannot be composed yet because it waits on the STREAM'S OWN sequenced work (a sibling ticket a stream worker is still finishing) is NEITHER `U` (no live owner question) NOR `W` (no third party) — it is Claude's OWN chained responsibility → it stays in `I` (workable). MECHANIZED: `_partition_workable` routes a bare `needs-acceptance` to `U` ONLY once a DRAFT was presented for approval (a ❓ ping fired — the question map references `#N`); until then it stays in `I`. So `U` only ever holds a bare `needs-acceptance` that carries a real owner-approval question. **#527 delivered-question invariant is MECHANIZED (#539):** `core-quals`/`slice-quals --waiting` tags any `U` member carrying no delivered question (no question-map `#N` reference AND no ask-flow-marked comment) `no-question!` in its reason column; an unreadable question map or a `gh` error tags nothing (never a false accusation). **Owner-UX invariant: "otázky na mňa?" must NEVER truthfully answer NIE while `U > 0`** — a positive `U` is only real, already-delivered questions. **W re-entry is MECHANICAL (#547):** `ops-wait` re-entry is no longer prose-only — watchdog job 20 reads each armed `/goal` loop's `--ops-wait` members and on a ~daily cadence types a `stuck-check:` re-check nudge into that session (re-check the external event/reply/release, then clear `ops-wait` WITH evidence or confirm still waiting), so a parked W ticket whose event already landed is re-surfaced instead of leaving the loop blind (montalu5); the SUPERVISOR still stays the ONLY one that clears `ops-wait` with evidence — the nudge only surfaces, never auto-unlabels. **I→W/U freshness audit is MECHANICAL (#552):** the SAME job 20 partition-audit nudge also covers the OPPOSITE direction — on the ~daily cadence it reminds an armed `/goal` loop to re-audit each `I` member against the #526/#539 shapes (a ticket already meeting a fix-class / sent-thread / deferred-thread shape → `ops-wait`=W, or carrying a delivered owner-question → U) so it is re-labelled instead of rotting in `I` until the owner asks (the montalu3 inflated-`I` incident); the JUDGMENT stays in the session (the watchdog cannot judge a #526/#539 shape), only the scheduler is mechanical — the supervisor still sets/clears every label with evidence. **W = tlač dopredu KAŽDÝ deň — stale! freshness tag is MECHANICAL (#570):** `W` is NEVER passive waiting — if `W N`, that is N things you must PUSH FORWARD every day so they move: at minimum a 1×/day reminder to the third party AND a re-verification that the blocker STILL holds by RE-READING the referenced (cross-repo) ticket — never citing it from memory — each recorded as a COMMENT on the ticket (that comment IS the freshness evidence). Owner (2026-08-19, verbatim): "Ak je W 15 tak je 15 veci ktore mas pushovat dopredu aby sa to pohlo. Nie ze ... cakas x dni na nejake info v discussion odoo a vobec si tych ludi aspon raz denne nepovzbudil." Mechanized: `core-quals`/`slice-quals --ops-wait` tags `stale!` any W member with NO fresh (≤24h) evidence of a stream-authored push comment (never a false accusation — a gh error / zero comments / an unresolvable identity leaves it UNTAGGED, the #539 no-question! bias), and the ~daily nudge NAMES the stale members with the required action (re-verify the blocker + remind the third party TODAY, with a ticket comment). The supervisor still stays the only one that clears `ops-wait` with evidence. **A daily reminder must be a SUBSTANTIVE, CONCRETE ask that MOVES the ticket, never a content-free ack (#568):** the mandated 1×/day third-party reminder is a real push — a specific question, a named blocker, the exact thing you need from them — NEVER a hollow "still working on it" acknowledgement; the `stale!` tag resets its 24h freshness clock on ANY stream-authored comment, so a content-free ack would silence the tag while the third party stays genuinely un-nudged (the exact "never actually nudged them" failure in tag-compliant disguise). A concrete ask is a real povzbudenie, not status noise.
- `· gk N` — sub-dev boxes only: own tickets already handed off to the gatekeeper — shown SEPARATELY, no longer a subset of `I N` (#391: `I N` now EXCLUDES a handed-off ticket rather than including it, so `gk N` is the parked count next to it, not a slice carved out of it). Hidden at 0. The signal is the `ready-for-review`/`needs-gatekeeper` LABEL when present (overridden back to unhandled by a `prio:bounce` label — a returned bounce re-enters `I N` immediately), falling back to a direct per-ticket check for a `READY-FOR-REVIEW:` comment when it is not (a fork-no-merge collaborator's own label-add routinely 403s, and the repo's own auto-labelling workflow can independently be broken — the comment is the hand-off's real primary signal either way).
- `· skip K` (was `· skipped K`) — tickets labeled `autopilot-skip` (excluded from `I N`); hidden at 0.
- **`Q N` and `A N` no longer exist as segments (#512).** The unanswered-❓ pings the old `Q N` counted now fold into `· U N` above (deduped by ticket reference); the once-planned `A N` (needs-acceptance) folds into `· U N` — but only while its client acceptance thread has NOT yet been sent (#526 routes a sent one, carrying `ops-wait`, to `· W N`). The question map + the watchdog's daily re-ask jobs are UNTOUCHED — only the footer render changed. A user quoting "Q N" / "A N" means the pre-#512 footer or the folded-in part of `U N`.
- `<email> sub <D.M.>(<Nd>)` — the account identity block, at the very end of the line, ONE unit (both properties of the same `~/.claude.json` → `oauthAccount`, so they belong together). `<email>` is `oauthAccount.emailAddress`, rendered in a readable colour. `sub <D.M.>(<Nd>)` is the monthly subscription-renewal anchor (`oauthAccount.subscriptionCreatedAt`, the next occurrence of that day-of-month), coloured by proximity (green far, yellow near, red on the last day).

**Width budget:** the whole line is fit inside the live tmux pane's width MINUS a reserve for Claude Code's own right-edge indicators (the armed-`◎ /goal` glyph is the live-evidence one — a fully-consumed pane once truncated the statusline clean off the end of the row, misread as "the goal died"). When it would overflow, the LEAST important segments are dropped dynamically, in this order: the account-identity block (email + sub) first, then the caveman tag, then — last resort — just the `ctx` segment's own `~$<cost>` suffix (keeping `ctx <size>` alone). An unmeasurable pane width (no live tmux pane, e.g. outside tmux entirely) never trims anything — the line always renders in full in that case.

The segment renders from a machine-local cache — read it when the user asks about it (never guess, never re-derive differently): `~/.claude/tickets-status/<cwd-key>.json` (refresh: `python3 ~/devel/airuleset/airuleset.py tickets-status --refresh --cwd <dir>`). A number the user quotes that mismatches your own `gh` count usually means a stale cache (TTL 120 s) or the per-stream scoping above — explain, don't dismiss. Applies to all rewordings ("v pätičke", "dole v claude", "ten counter").
