### Delivering Files to the User — ALWAYS a Clickable LAN URL, NEVER a /tmp Path → on-demand skill `deliver-files-as-urls`

The full protocol moved VERBATIM to the `deliver-files-as-urls` skill — load it whenever producing a file the user needs to open or download. Non-negotiable that survives here: the user has NO filesystem access to the dev machines — a `/tmp/...` path is USELESS to them. Every deliverable file goes through `python3 ~/devel/airuleset/airuleset.py share <path-to-file>` (never a bare path, never "can't be linked"). See the input counterpart `receive-files-via-upload-url.md` for the opposite direction.

**A credential is NOT a file** — deliver via `secret show` (one-shot URL, `❓`/`needs-owner-action` #879), never `share`/chat/`cat`. See `receive-files-via-upload-url.md`.

**A message that REFERENCES an openable thing carries its functional URL** — the same "always a URL, never a bare reference" doctrine pointed the other way (owner directive 2026-08-20, #595). EVERY message a reader can act on — a client handover / Odoo Discuss message, a Discord ping, a completion-report line — that names something the reader could OPEN (a live feature, a record, a screen, an action, a report, a dashboard) MUST carry the direct FUNCTIONAL URL — the deep link to that exact action/record/screen, verified live (loads) before sending — never only a prose menu path (`Predaj ▸ Objednávky ▸ …`) and never only the bare homepage. The incident: a client handover on montalu PROD (Discuss msg 1723308) described two live features only by their menu path with NO clickable URL and was rejected — nobody could click through and see it. This generalizes `completion-report.md`'s 🌐-line rule (user-clickable URLs, verified 200, never localhost) to CLIENT-FACING messages and notifications, not just the report. Applies to all rewordings and semantic equivalents.
