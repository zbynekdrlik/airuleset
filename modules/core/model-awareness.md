### Model Awareness (2026)

**The MAIN interactive session runs whatever the user set via `/model`** (their call alone — never auto-downtier it), **and the managed launch default on every box is Fable 5** (`claude-fable-5[1m]` — `MANAGED_MODEL`, user directive 2026-08-13). **Opus 5** (`claude-opus-5` — including the bare `opus` alias, which resolves to it on the Anthropic API) **is BANNED everywhere**: never as a main model, never a subagent dispatch, never a Workflow stage, never in settings or agent frontmatter (lock-tested — `tests/test_model_tiering.py`'s grep-gate). **Fable 5** (`fable`) is dispatched, through the budget gate, for the DESIGN phase and the REVIEW phase of a non-trivial ticket — the two think-and-check PHASES — never for the implementing worker end-to-end (the PER-PHASE model below, owner directive 2026-08-26, FLEET-WIDE — the same on every target and project); **Opus 4.8** (`claude-opus-4-8`) is the implementation ESCALATION tier (for a complex implementation) and the gate-CLOSED fallback; **Sonnet 5** (`sonnet`) is the implementation DEFAULT for a settled-design ticket AND carries LIGHT / mechanical work (CI polling, log scraping, grep/locate sweeps, status collection, format-only transforms, read-only lookups) — but **Sonnet 5 is never used for anything complex** (when in doubt, Opus 4.8; a complex implementation escalates to 4.8, #721); Haiku 4.5 (`haiku`) for the most trivial reads. **The main model is the user's deliberate call — NEVER recommend switching it, in either direction** (2026-07-31 precedent: the once-per-session "recommend Opus 5" line was already RETIRED then, and the 2026-08-13 ban settles the direction outright); the user's `/model` choice stays theirs alone. Rules must work for Fable AND the Opus 4.8/Sonnet/Haiku subagents. Tier/price tables, the benchmark citations and the full policy history live in the **`fable-advisor`** skill — load it when reasoning about tiers or costs.

**The lineup:**

- **Main interactive session = the user's `/model` choice; the managed launch default is Fable 5 (`claude-fable-5[1m]`).** Never auto-downtier it; never re-recommend against it.
- **JUDGMENT-CONTENT test — now the PHASE selector (2026-08-26, fleet-wide).** The same criterion no longer decides whether a WHOLE subagent runs Fable — it decides whether a ticket is NON-TRIVIAL enough to warrant the two Fable PHASES: the DESIGN phase (before implementation) and the REVIEW phase (before integration). A ticket is non-trivial when it carries REAL judgment or design content — decisions that shape the result, not merely settled changes to type. ANY of these makes it non-trivial: (a) **Non-trivial implementation** — the ticket needs design decisions (structure, approach choice, more than one defensible way to build it; anything whose design comment is more than a TRIVIAL one-paragraph). (b) **Review of a non-trivial change** — the adversarial audit of any diff that itself carried judgment content; this includes, ALWAYS, the gatekeeper's review/verdict of a sub-dev hand-off (user directive 2026-07-24 — the tiering lives in the `process-subdev` skill). (c) **Hard debugging** — a root cause not obvious on first read, or a prior attempt failed. (d) **Plan / design / synthesis** of any feature or component. NOT non-trivial (→ no Fable phases: an Opus 4.8 one-paragraph design comment + a trivial-diff review on the implementation tier): a genuinely mechanical scoped edit with one obvious shape (typo, rename, format fix, version bump, config value), an already-fully-settled plan with zero remaining decisions. **Tie-break: when unsure whether a task carries judgment content → it DOES** — so the ticket GETS the Fable design + review phases (the 2026-08-14 "unsure → it is NOT hard" tie-break is what produced zero Fable dispatches). But **the implementing WORKER always runs the implementation tier (Opus 4.8 / Sonnet 5) — never the implementing worker end-to-end on Fable, on ANY repo.** Protocol: run the gate ONCE per qualifying Fable phase-dispatch (the design consult, the review pass) — not per subtask: OPEN → dispatch `model: "fable"` at `xhigh` (or `max` for the truly frontier); CLOSED → the SAME phase runs **Opus 4.8** and you do NOT keep re-polling the gate within the phase. Never skip the gate for an automatic Fable dispatch.
- **FLEET-WIDE — no per-repo exception (2026-08-26).** This per-phase split is the SAME on every target and every project. The 2026-08-25 "airuleset repo = Fable-MAJORITY subagent dispatch" exception is ABOLISHED — airuleset follows the identical per-phase policy as any other project, and there is **no repo where the implementing worker runs Fable**. On EVERY repo: the design phase and the review phase of a non-trivial ticket are the gated-Fable dispatches; the implementing worker runs Sonnet 5 by default for a settled-design ticket, Opus 4.8 (frontmatter-pinned) when the implementation carries complexity (#721); gate CLOSED → those design/review phases fall back to Opus 4.8 too. Genuinely mechanical/read-only dispatches (CI polls, log scrapes, lookups) stay `model: "sonnet"`/`"haiku"` everywhere, exactly as before.
- **HOW to reach Opus 4.8 (the gate-CLOSED fallback and the implementation ESCALATION tier — #721):** the per-dispatch `model` param takes only aliases (`sonnet|opus|haiku|fable`) and `opus` is banned — so Opus 4.8 is reached via (a) an agent DEFINITION whose frontmatter pins `model: claude-opus-4-8` (autopilot-worker, ticket-validator — full ids in frontmatter are documented AND live-verified: a probe agent resolved `claude-opus-4-8` in its own transcript), (b) a Workflow stage's `opts.model: 'claude-opus-4-8'` (full model names are legal there per the SDK docs), or (c) OMITTING the model override so the dispatch inherits a `claude-opus-4-8` parent (a worker's own sub-dispatches). A Fable MAIN session at gate CLOSED holds the judgment itself instead of spending a new gated dispatch — never the `opus` alias, never Sonnet for judgment.
- **DESIGN-HEAVY (HARD) taxonomy — a design-DEPTH classifier, no longer the Fable selector (the JUDGMENT-CONTENT phase selector above decides WHICH tickets get the Fable design + review phases; design-heavy decides how DEEP the design phase goes).** The autopilot skill's design-triage step reuses exactly this taxonomy to pick which tickets get the fuller 2-3-approach design treatment and a supervisor-side `Plan` synthesis within the design phase. A ticket/stage is design-heavy when ANY of these holds:
  1. **Architecture / design / synthesis of a genuinely COMPLEX or cross-cutting system or feature.** "Multi-file" alone is NOT the bar — most ordinary features touch several files; the bar is complexity/ambiguity of the design itself.
  2. **Hard debugging** — a root cause that resisted a first real attempt, or a multi-component / concurrency / heisenbug-class bug.
  3. **Adversarial final review / verify of a safety-critical or genuinely complex change** (keystroke-injection guards, auth, data-loss paths, gnarly concurrency) — including, ALWAYS, the sub-dev hand-off review above.
  4. **An autopilot ticket that is architectural / cross-cutting / ambiguous-design, or one a prior worker already failed on.**
  5. **The session is CIRCLING — ≥2 attempts at the SAME decision / plan / root cause without progress** (rework loops, try-A-fail-try-B-fail-try-A-again — the user's "točíme sa dokolečka" complaint, 2026-07-08). Do NOT run a third identical lap — ground the stuck problem into a digest and consult through the gate (advisor SHAPE below). The valve keys on **OBSERVED circling**, never on assuming the model is broken.
  Routine work is NOT design-heavy: scoped bug fixes, features with a settled design, execution of a settled plan, mechanical sweeps — those stay at the ordinary one-paragraph design-comment DEPTH, get NO Fable design phase, and their implementation runs the implementation tier (Sonnet 5 by default for the settled design, Opus 4.8 only on the complexity criteria below) like every ticket.
- **IMPLEMENTATION (the actual work) = Sonnet 5 by DEFAULT for a settled-design ticket (`model: "sonnet"`); Opus 4.8 (`claude-opus-4-8`) when the implementation itself carries complexity — NEVER Fable.** By the time the worker implements, the design is SETTLED (its CYCLE-step-2 design comment is posted / a Fable DESIGN phase ran), so the ordinary case runs on **Sonnet 5** at `high` — the TYPING is the longest, cheapest-to-downtier part of a ticket, and the gated-Fable REVIEW bookend + RED→GREEN + adversarial review hold quality exactly as they do at 4.8 (the #721 burn-phase-2 fix: after #715 moved implementation Fable→Opus 4.8, "when in doubt, Opus 4.8" made Opus ~59 % of the 7-day spend and workers died on the Opus weekly limit — the burn only SHIFTED, it did not shrink). It ESCALATES to **Opus 4.8** (`claude-opus-4-8`, `high`/`xhigh`) when the implementation carries genuine complexity — ANY of: a **multi-component change** (several interacting components/modules/services, not merely multiple files — the same "multi-file alone is NOT the bar" distinction the design-heavy taxonomy draws), **concurrency** (async/locking/race-prone paths), a **security boundary** (auth, credentials, input-trust, injection guards, data-loss paths), a **hard-debug lane** (root cause not obvious on first read, or a prior real attempt failed), or a **prior Sonnet worker already failed on this ticket** — and, per the standing fail-safe, whenever unsure → Opus 4.8. **Mechanism (fleet-wide, the only mechanically-enforceable shape):** the **autopilot-worker** frontmatter stays pinned `model: claude-opus-4-8` = the escalation tier AND the fail-safe default (the ONLY way to reach 4.8 on a dispatch — the `opus` alias resolves to the banned Opus 5 and 4.8 has no param alias); the SUPERVISOR downtiers to Sonnet 5 with an explicit `model: "sonnet"` for an ordinary settled-design ticket, and OMITS the param (frontmatter pin stands → Opus 4.8) to escalate — so the fail-safe direction is UP (forget-to-classify → Opus 4.8, never accidentally lower, and never `model: "fable"`). The `subagent-driven-development` implementer and workflow execute/transform stages follow the SAME split (`opts.model: 'sonnet'` for a settled stage, `opts.model: 'claude-opus-4-8'` for a complex one) — the **implementing worker NEVER carries a `model: "fable"` override, on ANY repo.** A mid-ticket HARD wall on the worker still dispatches a gated `model: "fable"` CONSULT (advisor shape — digest in, decision out), then implementation continues on its tier (a hard-wall ticket is by definition in the hard-debug lane → Opus 4.8); that consult is the ONE mid-implementation exception, and it is a bounded design/debug dispatch, never the worker itself flipping to Fable.
- **Purely MECHANICAL / READ-ONLY / LIGHT plumbing = Sonnet 5 (`model: "sonnet"`) or Opus 4.8 low.** This is the tier the 2026-08-14 refinement explicitly REHABILITATED ("moze byt aj sonnet 5 vyuzivany"): CI polling, log scraping, grep/locate sweeps, file enumeration, status collection, format-only transforms, "where is X" lookups — dispatch these on **`model: "sonnet"` + `low`** (Haiku for the most trivial reads). Where a surface can NAME the tier (a pinned agent definition, a Workflow stage's full-id `opts.model`), Opus 4.8 at `low`/`medium` is equally fine; on an ad-hoc alias-only dispatch (`Explore`/`general-purpose`), `model: "sonnet"` is the right EXPLICIT choice — never a model-less dispatch that would inherit the Fable main and put the MOST expensive tier on the cheapest work. Sonnet 5 is never used for anything complex — a sweep that carries any real judgment is judgment-content work and runs gated `fable` (Opus 4.8 at gate CLOSED); when in doubt between Sonnet and Opus 4.8 for a genuinely mechanical sweep, Opus 4.8.
- **HARD RULE — NEVER dispatch a subagent without an EXPLICIT model choice.** A `model`-less `Agent`/`Explore`/`general-purpose` dispatch INHERITS the caller's model — and since the managed MAIN default is Fable 5, a model-less dispatch from a Fable main silently runs the SUBAGENT on Fable, which is exactly the 2026-08-14 burn (live evidence: gk `general-purpose` CI-poll agents at 300–430k tokens EACH on inherited Fable, purely mechanical work; the 5h Fable limit gone in ~30 minutes). Every ad-hoc dispatch carries an explicit `model`: `sonnet`/`haiku` for mechanical/read-only/light, `fable` (gate OPEN) for the design + review PHASES of a non-trivial ticket, or a `claude-opus-4-8`-pinned agent definition for the implementation worker and the gate-CLOSED fallback. EXPLICIT means a `model` param on the dispatch, OR an agent definition with pinned `model:` frontmatter (autopilot-worker, ticket-validator) — never inheritance from a Fable main. **TRAP (live gk incident 2026-08-14): the explicit-model requirement for the OPUS 4.8 tier is satisfied by the pinned agent frontmatter (`model: claude-opus-4-8`) or inheritance from a `claude-opus-4-8` parent — with NO `model` param at all. Passing `model: "opus"` is NEVER correct: the `opus` alias resolves to the BANNED Opus 5 (1M context) AND overrides the frontmatter pin — a gk main, told "every dispatch must carry an explicit model", passed `model: "opus"` and launched Opus 5 live before catching + re-dispatching without the override.** The only valid explicit `model` PARAMS are `"sonnet"`, `"haiku"`, or (gate OPEN) `"fable"`; the Opus 4.8 tier is reached WITHOUT a param. This is lock-tested — `tests/test_model_tiering.py`.
- **SHAPE — a Fable CONSULT = ADVISOR: digest in, decision out.** For a consult-style call (hard-debug advice, a design-fork verdict): a cheap stage grounds the problem into a TIGHT digest — facts, constraints, attempts already failed, the ONE concrete question; ONE Fable call returns the decision; execution applies it on Opus 4.8. A Fable consult never re-reads the repo wholesale, never fans out, and never runs mechanical plumbing. Under the per-phase policy, **a DISPATCHED, fresh-context Fable worker is a sanctioned shape** — but ONLY for the DESIGN phase (a bounded design/synthesis consult that lands a design comment) and the REVIEW phase (a bounded adversarial pass over the diff), each a fresh, bounded-context `model: "fable"` dispatch; the implementing worker itself is NEVER such a dispatch. What stays BANNED is Fable as a long-lived MAIN implementation session (a Fable MAIN re-reads the full conversation context every turn — the 2026-07-01 burn; `block-main-implementation.sh` still hard-blocks implementation-size edits from a MAIN session with an ARMED `/goal` or one running unattended, #54) — the ADVISOR digest shape above stays the right form for a consult-style call.
- **Redundancy is still waste, not rigor** — ground once + pass a digest, size fan-outs to residual uncertainty, batch per-item verifies (`claude-code-tooling.md`). A Fable stage NEVER re-reads what a cheap stage already digested.
- **Self-audit before a multi-agent dispatch — the miss runs BOTH ways:** every Fable dispatch must carry a gate-OPEN check (an ungated Fable fan-out, a Fable dispatch on genuinely mechanical plumbing, or a model-LESS dispatch that silently inherits the Fable main is still the tiering MISS) — AND running the IMPLEMENTATION worker on Fable (or skipping the Fable design/review phase for a non-trivial ticket) is the OTHER miss the 2026-08-26 per-phase policy corrects: the implementation over-spends the subscription (the 89–93 % Fable-weekly burn), a missing design/review phase under-serves quality. Implementation is Sonnet 5 by default for a settled-design ticket (Opus 4.8 on the complexity criteria; Sonnet also for mechanical, #721); the DESIGN phase and the REVIEW phase of a non-trivial ticket — and nothing else — are the gated-Fable dispatches.

Applies to all rewordings and semantic equivalents — the intent: Fable 5 is the user's MAIN default at launch AND, PER-PHASE and FLEET-WIDE, the gated tier for the DESIGN phase and the REVIEW phase of a non-trivial ticket — never the implementing worker end-to-end, on any repo; Opus 4.8 is the implementation ESCALATION tier and the gate-CLOSED fallback while Sonnet 5 is the settled-design implementation default (#721), and Sonnet 5 carries light/mechanical work (never anything complex), Haiku the most trivial reads, no subagent is ever dispatched model-less from a Fable main, and the BANNED Opus 5 never runs anywhere, on any surface, under any alias.

#### Fable 5 / Opus 4.8 behavior

- **Literalism**: does exactly what rules say. Precise wording → high compliance. Vague wording → unpredictable.
- **Reasons more, calls tools less**: when a tool must be used (e.g., `gh run view` for CI monitoring, `Playwright` for E2E verification), the rule must say so explicitly.
- **Adaptive thinking** (no fixed budget): longer reasoning per turn, fewer back-and-forth rounds.
- **Effort:** the API default is `high` (per docs.anthropic.com/effort), and **the managed MAIN-session baseline is `high` with NO standing ultracode launch flag** (`MANAGED_EFFORT_LEVEL = "high"` in airuleset.py; the launcher no longer bakes `--settings '{"ultracode":true}'` into any mode — owner directive 2026-08-30, verbatim: *"Chcel by som este aby sa claude v targetoch nespustali s zapnutym ultracode ale s effort high"*, reversing the launch-flag half of #445) — the user can still raise it per session with `/effort`, and opt into ultracode by hand. Only the LAUNCH FLAGS reversed; the max-acceleration / parallel-worktree doctrine and the per-phase model tiering are UNCHANGED. DISPATCHED design + review PHASES run gated Fable at `xhigh` (`max` only for genuinely frontier work — it overthinks structured tasks); the IMPLEMENTATION worker runs Sonnet 5 by default at `high` for a settled-design ticket (Opus 4.8 at `high`/`xhigh` on complexity, #721); mechanical/read-only/light stays `low`/`medium` on Sonnet 5 or a light tier — don't blanket-`xhigh` mechanical dispatches. Changing effort mid-session discards the prompt-cache prefix (per docs) — pick a level at session start and hold it; don't hot-swap effort in a running session without a reason stronger than the cache-write cost.

#### Subagent behavior (smaller models)

- Follow rules less reliably — they need explicit "do X, not Y" instructions.
- Benefit more from hook-level enforcement (100% compliance regardless of model).
- Benefit from pattern lists (banned phrases, anti-patterns) — literalism matters less when the model already pattern-matches.

#### How to write rules for both

- **Lead with the rule in precise terms** — the top tiers will follow it exactly.
- **Follow with anti-patterns / banned phrases** — helps subagents.
- **End with "applies to all rewordings and semantic equivalents"** — prevents a smaller model from taking bullet-point lists as exhaustive.
- **Critical enforcement goes in hooks**, not rules — works for every model.

#### Example

Bad (vague, subagent may miss): "Don't skip tests."
Good (precise + pattern + semantic gate):
> "NEVER use `#[ignore]`, `test.skip()`, or `pytest.mark.skip`. Any rewording or equivalent skip mechanism also applies."
