### Autonomous Batch Issue Development → on-demand skill `batch-issue-development`

**Design the approach BEFORE writing code — every ticket, unconditionally.** Root cause (traced in the code, not the symptom restated) → the approach chosen → the alternative rejected and why, recorded on the ticket with `gh issue comment <N>` BEFORE the first code commit. The step's DEPTH scales (one honest paragraph for a scoped fix; a design consult or a user question for a genuine fork) — its EXISTENCE never does. Discovering the design through a stream of corrections is the failure this prevents (#104: the step was ambient here until `e9d1022` moved it to a skill that the ticket path never loads).

Core invariants that survive here: bundle bundle-safe issues on ONE dev branch → ONE push → ONE PR → ONE CI cycle; never prompt between issues; single feature = single PR (no progressive multi-PR rollouts). The full bundling gate (≤300 LoC/issue, ≤600 LoC + ≤4 issues per PR), per-issue cycle and banned-prompt list moved VERBATIM to the `batch-issue-development` skill — load it at the START of any /issue-planner or /autopilot run and whenever bundling/splitting issues into PRs is decided.
