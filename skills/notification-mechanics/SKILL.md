#### The three send hooks — what each script does internally

Moved VERBATIM from `milestone-notifications.md` (#92); the module keeps only the behavioural summary.

Three airuleset hooks implement this from the status marker, with no action from you:
1. `notify-discord-pending.sh` (Stop) scans the message for a question or terminal marker. On **`❓ NEEDS YOU`** (last line, blocked) OR **`❓ ASKED:`** (a body line raised while the turn continues other work and ends `⏳ WORKING`) it **SENDS the device ping IMMEDIATELY** (via the shared `notify-discord-send.sh`) — a genuine question must reach the phone even over tmux/SSH, where Claude Code's `idle_prompt` event is unreliable (depending on it is exactly why pings "stopped" arriving). **A question is NEVER suppressed** — the old "❓ + continuing language → swallow the ping" behavior was a bug (the user asked, no ping came, then got reproached hours later); it is removed. **But one ping per DISTINCT question:** a repeat with IDENTICAL content and NO user prompt in between (a `/goal`-loop re-poke of a session still blocked on the same unanswered question) is DEDUPED — the first ask always pinged and the phone already has it; re-pinging every re-poked turn was the 9× "rovnaká otázka ako predtým" spam (restreamer, 2026-07-04). A real user prompt clears the dedup (`clear-question-dedup.sh`, UserPromptSubmit), so a fresh ask pings again even with identical text. Consequence for YOU: re-poked while still blocked on the SAME question → repeat the `❓` line VERBATIM (byte-identical); a reworded repeat reads as a new question and re-pings the phone. On `✅ DONE` it records a pending line; on `⏳` with no `❓ ASKED` line / no-marker it clears any pending. **Anti-spam (2026-07-05):** a Stop attempt a blocking gate REJECTED never pings (the hook skips when a fresh `/tmp/airuleset-*-block-<sid>` exists — a draft being rewritten is not a delivered question), and a REWORD of a still-unanswered question EDITS the existing Discord message in place via `notify --edit-question` (edits don't push-ping; the phone got its push on the first ask) — a fresh POST fires only for a genuinely new ask after the user typed. This killed the 3-pings-in-3-minutes-for-one-question camera-box spam.
2. `notify-discord.sh` (Notification : idle_prompt) sends the pending `✅` line ONLY when the user is genuinely idle/away — a finished turn is less urgent than a question, and pinging every completed turn while the user watches the terminal is spam. NOTHING on `⏳`.
3. `notify-discord-send.sh` is the single send path both call (compose structured line + @mention owner + POST) — one place for the curl, no duplication.

So: a **question (`❓`) reaches the phone right away**; a **done (`✅`) reaches it when you're away**. Neither needs action from you beyond writing the honest marker.

**Owner-scoped question DELIVERY (#710, owner directive 2026-08-26).** The ❓ question ping is delivered to Discord for owner **david** (claude-david) exactly as above; for owners **zbynek** and **marek** it is owner-scoped OFF — they take questions in webterm + the footer `U N`, so the Discord ping is SUPPRESSED at BOTH question transports: the interactive `notify-discord-send.sh` hook (a per-target check via `airuleset.py notify --question-ping-off`, gated BEFORE channel resolution, on `KIND=="questions"` only) AND the Python `notify.send(kind="questions")` chokepoint (the watchdog daily re-ask / owner-decision-digest path). The single source of truth is `notify.question_ping_off(owner)` + `notify.QUESTION_PING_OWNERS_OFF = {"zbynek","marek"}` (normalised via `stream_redirect`, so a persona routing INTO claude-zbynek/claude-marek — montalu5/montalu1/simap1 — is off too, while david1-4 → david stays ON). Each suppression is a LOGGED decision (a `suppressed` delivery-log line, the #546/#704 machine-channel pattern), NEVER a silent drop. Everything else is untouched: the session ❓ marker discipline, the `discord-questions.json` map, `needs-answer` tracking, the footer `U N` partition, and watchdog job 7 (Discord reply → asking session — for zbynek/marek nothing is recorded, so job 7 has no entry to match, its normal empty path; for david it records + routes as before). Only `✅`/run-card/other deliveries to zbynek/marek are unaffected — this scopes ONLY `kind="questions"`.

#### API-error / limit / token-burn alerts are RETIRED from Discord (#546, owner directive 2026-08-18)

**These automated alert classes are owner-suppressed at `notify.send()` and no longer ping the device.** The api-error stall ping (watchdog job 1 + the now-no-op `notify-api-error.sh` Stop hook), the 5h/usage LIMIT ping (job 6 / `usage.py`), and the token-BURN / spend-budget ping (jobs 19 / 16) were "alerts for the agent" reaching a channel no agent reads. Owner directive (issue #546, verbatim): *"ty sa mas starat len aby sa pokusili agenti rozbehnut cez continue … stara sa teraz o limit a subscription iny project."*

**How it works:** `notify.send()` checks the outgoing `dedup_key` against `SUPPRESSED_ALERT_PREFIXES` (`apierr` / `sesslimit` / `usage` / `burn-alert` / `fleet-burn-budget`) FIRST; a match POSTs nothing, returns `"suppressed"`, and writes one explicit `suppressed kind=alert-class key=<key> reason=#546 …` line to `~/.claude/notify-delivery.log` (the audience split — the signal moves to the machine channel, never a silent drop, #486/#134). Every watchdog job 1/6/16/19 + `usage.py` + the CLI `--api-error` route through this ONE chokepoint, so the whole class is covered in one place. The watchdog's **`continue` auto-resume is 100% untouched** — it uses `send_verified` / `deliver_with_stash` / direct tmux keystrokes, none of which routes through `send()`, so the resume never sees the gate. Anti-total-silence for a genuinely DEAD fleet (all boxes down) is already owned by the conformance-heartbeat alarm (watchdog job 35, #543); a still-ALIVE-but-stuck episode's "gave up after N nudges" signal is now deliberately machine-channel-only (the owner directive's tradeoff — job 35 does NOT cover that case), so no new global circuit-breaker ping was added — default is SILENCE. Preserved (different key namespaces, never matched): `❓` questions (`waiting:`/`❓:`), `✅` done (`done:`), run-cards (`<repo>#<n>`), bounce/gk-req, job-4 `busypane:`, and the genuine one-shot `acctblock:` alarm (account blocked, no auto-reset, needs a human).

#### Every device message goes to the owner's OWN thread AND @mentions them (zbynek / marek)

Each project runs in a tmux session grouped `zbynek` or `marek`. EVERY Discord message (the idle `❓`/`✅` ping AND the autopilot card below) is (1) POSTED to that owner's **own thread** — `claude-zbynek` / `claude-marek` — so the two people's notifications never mix in one shared thread, AND (2) prefixed with that owner's `<@id>` so it is unambiguous WHOM it concerns (the mention also auto-joins them to their thread and fires the phone push). This is automatic — both send paths (`hooks/notify-discord-send.sh` for `❓`/`✅`, the Python `notify.send()` for the autopilot card) resolve the owner from the tmux session group, then route via `airuleset.py notify --channel-id`: `DISCORD_NOTIFICATION_CHANNEL_<OWNER>` (the per-person thread) when set, else the shared `DISCORD_NOTIFICATION_CHANNEL_ID`. The mention id is `DISCORD_MENTION_<OWNER>` in the channel `.env`. You do nothing; never strip the mention. No tmux / no mapping → no per-owner thread and no tag → it falls back to the shared thread, never pinging the wrong person.

**Questions get a SEPARATE thread (`DISCORD_NOTIFICATION_CHANNEL_<OWNER>_Q`, #296, 2026-08-07).** `hooks/notify-discord-send.sh` computes `KIND="questions"` whenever `ND_EMOJI="❓"` (else `KIND="default"`) and threads `--kind "$KIND"` onto the SAME `--channel-id` call `emit_one()` already makes for every target (primary owner AND each mirror) — so a `❓` ping resolves `DISCORD_NOTIFICATION_CHANNEL_<OWNER>_Q` first, falling through to the owner's normal thread when the `_Q` variant isn't configured yet, exactly the SAME cascade `notification_channel()` already used before this fix (never a second mechanism). `✅` and the autopilot card are UNAFFECTED — neither caller passes `kind=` at all, so they stay on the owner's normal `claude-<owner>` thread (the api-error/limit/burn alert pings that used to share it are retired, #546). The `-q` thread is created (if missing) and its id persisted into the local `.env` by `notify --provision-question-thread` (`notify.provision_question_thread()` — FINDS an existing `claude-<owner>-q` thread on Discord first, since the id is box-local config and a second box provisioning the same owner must never fork a duplicate thread). Discord-reply routing (job 7) needs NO awareness of any of this: it already fetches from whatever channel is recorded in the question map, never a channel hardcoded to the owner's "primary" thread.

**Parallel mirror recipients (`DISCORD_MIRROR_<OWNER>`).** An owner can be an automated SESSION-PERSONA rather than a person (e.g. a `david` session on dev2 running codex-bridge). Such a persona gets its OWN thread for visibility, AND a real human is pinged IN PARALLEL: `DISCORD_MIRROR_DAVID=zbynek` makes every david notification ALSO post to zbynek's thread with zbynek's `<@id>` (the actual phone push). Both send paths fan out (primary owner first, then each mirror), each target in its OWN thread with its OWN @mention; a mirror whose thread resolves to the primary's is skipped (no double-post). A normal single-owner box (zbynek / marek, no `DISCORD_MIRROR_*`) fans out to exactly one target → unchanged. This is automatic; you do nothing.

#### EXCEPTION detail — the `/autopilot` per-ticket completion card's field-by-field composition

`milestone-notifications.md` keeps the short summary of this exception inline (it exists, it's per-ticket, deduped, fired via `notify --run-card`). This is the full composition detail:

- **Fired by the `/autopilot` WORKER after merge + post-deploy verification.** The worker runs `airuleset.py notify --run-card --repo <owner/name> --issue <N> --goal "<plain goal>" --achieved "<plain what landed>" --version "<deployed version read from the DOM>"` (one per member, even in a batch). `--goal`/`--achieved` are PLAIN, simple, non-technical Slovak (the worker translates the technical issue, NOT the raw title); `notify --run-card` gathers the remaining backlog from gh, @mentions the tmux owner, and posts the card. The supervisor does NOT call `notify` by hand — it just confirms the worker carded each merged member.
- The card is **Slovak, structured markdown**: header **🎫 #N** (number only — the technical title is dropped), **🎯 Cieľ** (the worker's plain `--goal`) + **✅ Dosiahnuté** (the worker's plain `--achieved`), the **📦 deployed version** (`--version`), a **🔗 links** line — the `--url` "WHERE to SEE the change live" link(s): the web page / the specific dashboard sub-page the change is visible on, labelable (`Money Gate stav=…`); NOT a PR/diff link (the user doesn't want it) — and **📊 Autopilot** progress (`ostáva Y` open non-skip issues). Structure is composed in code, so it is consistent every time. (The "🔍 Double-review" line, the "PR #N" number / PR link, and the verbatim technical title were all removed at the user's request.)
- **Deduped on repo-name#issue** — one card per ticket; a re-dispatched fresh worker (a stopped worker is presumed dead and re-dispatched fresh from durable state) never double-posts; a failed send releases the claim so it retries.
- This is distinct from the `✅ DONE` end-of-run ping: the per-ticket cards fire DURING the loop (the loop turns still end `⏳ WORKING`), and the single `✅ DONE` fires only when the WHOLE backlog is empty.
