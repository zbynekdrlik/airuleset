### Verify Launched Work Stays Alive — Poll It; a Dead Process Sends No "Done"

**Context gate — related rules you MUST also apply:**
- `autonomous-verification.md` — you have eyes (ps, logs, the dashboard); a stalled job is YOUR work to detect, never the user's to flag
- `ci-monitoring.md` — the CI-run case of this rule (monitor a `gh run` to terminal); this generalizes it to ANY launched work
- `message-status-marker.md` — `⏳ WORKING` means YOU keep checking; it is a promise to re-verify, not a licence to wait blindly
- `complete-planned-work.md` — work isn't done until verified; a silently-dead background job is unfinished work, not a finished one
- `subagent-continuation.md` — `SendMessage` reaches only a still-alive/resumable subagent, and a dead one's goes nowhere; its liveness signal is its DURABLE state (branch / PR / files / gh), not an in-process check

**Anything long-running you LAUNCH — a background Bash, a build, a processing/verdict/encode job, a `Monitor`, a dispatched subagent/worker/workflow — you OWN keeping alive. Verify on a cadence that it is STILL RUNNING. NEVER infer "still running" from the ABSENCE of a completion signal: a process that crashed, was OOM-killed, segfaulted, or hung — or a subagent that died — emits no "done" and no "failed", so silence looks IDENTICAL to healthy progress. This rule exists because (1) a worker waited on a job's success event, the job died silently, the event never came, and the session sat for 8 HOURS believing it was "still decoding"; and (2) one morning the user had to hand-type "stucked?" into NEARLY EVERY running session — each was parked on `⏳ WORKING` claiming a subagent/subprocess was running, but NONE had internally re-checked why that subagent/subprocess had been silent for HOURS. Silence is not success. Silence is not even liveness. A turn that ends `⏳ WORKING` is a PROMISE to re-verify on a cadence — not a licence to wait until the user pokes you.**

#### The hard rule — never wait on a success-ONLY condition

A wait that only terminates on SUCCESS waits FOREVER when the work dies, because death is not success. Every wait MUST also terminate on failure / death / timeout, so you get re-invoked and NOTICE:

1. **`Monitor`** — the filter MUST cover failure signatures, not just the happy marker (per the tool's own "silence is not success"): `grep -E "progress=|Traceback|Error|FAILED|panic|Killed|OOM|exit"`. For an OUTCOME wait set a bounded `timeout_ms` (default 5 min) — do NOT use `persistent: true` for "wait until X finishes" (persistent removes the timeout → a dead job hangs the watch indefinitely). `timeout_ms` maxes at 1 h (3600000 ms); for a job that can run longer than 1 h, a single `Monitor` cannot span the wait — use a self-re-invoking `run_in_background` loop that re-arms instead.
2. **Background Bash `until` loop** — bound it so it ALWAYS exits and re-invokes you (on success, death, OR timeout), never only on the marker that a dead process can't write:
   ```bash
   PID=$!; START=$SECONDS
   until grep -q DONE out.log || ! kill -0 "$PID" 2>/dev/null || (( SECONDS-START > 1800 )); do sleep 10; done
   ```
   `until grep -q DONE out.log` ALONE is the trap — it spins forever if the job dies before writing `DONE`.
3. **Explicit liveness poll** — check the process is ALIVE (`kill -0 $PID` / `ps -p $PID`) AND PROGRESSING (output file growing, heartbeat / mtime advancing, row count climbing). Dead OR stalled (no progress for N minutes) → **INTERVENE NOW** (read the log, find why it died, restart or re-route) — do NOT keep waiting.

#### Bound the wait, schedule the re-check, return to the session

- **Every wait has an expected duration.** Exceeding it by a margin is a SIGNAL to check, not a reason to assume "still going". A 2-minute job silent for 30 minutes is dead, not slow.
- **End a turn `⏳ WORKING` only with a scheduled re-check armed that SURVIVES session events, OR one you will actively RECOVER on your next turn.** A background waiter's session-linkage MAY not survive — context compaction can drop the in-process task-handle registry (`ci-monitoring.md` #107 re-check: the underlying OS process usually keeps running; anthropics/claude-code #29193 is the actually-reproduced mechanism — the two citations this rule used to lean on, #25188/#43944, don't hold up: #43944 is the OPPOSITE failure, orphaned/leaking processes, not killed ones). **And a SECOND, more urgent death mode: the memory-pressure REAP.** On a memory-tight box Claude Code proactively SIGTERM→SIGKILLs a MAIN-session background shell on a Node `memoryPressure` event (`task_local_shell_pressure_reap`; main-session only — `agentId===undefined` — a subagent-launched bg shell is EXEMPT; verified in the installed 2.1.232 binary), killing the OS PROCESS outright and in MINUTES, not just at a compaction boundary — so the relaunch below is genuinely re-CREATING a dead waiter, never merely re-linking one. Two cheap mitigations: run the long waiter inside a subagent doing FOREGROUND bounded polls (a subagent's foreground call is exempt from the reap), or set `CLAUDE_CODE_DISABLE_BG_SHELL_PRESSURE_REAP=1` on the CLI env to restore the documented waiter semantics (the managed launcher already exports this fleet-wide, #460, so on a managed box it is set by default — this manual set only matters on an unmanaged box). For a SHORT wait, a **foreground bounded poll loop** (in-turn — nothing to kill) needs no recovery step and stays the default. For a LONG wait, ONE background waiter is the RIGHT tool — never chunked foreground polling — but ONLY when paired with a mandatory recovery check: on your NEXT turn, verify from the DURABLE resource being waited on (not the possibly-orphaned handle) and relaunch a fresh waiter if the wait genuinely isn't over. NEVER a blind indefinite wait, and NEVER a background poll you fire-and-forget with no recovery check.
- **The result must come BACK to your session** (re-invoking mechanism), so a silent death is caught within a bounded time — never a fully-detached wait you can't observe.

#### Killing your own waiter — ALWAYS scoped to YOUR OWN process, NEVER a broad pattern (#701)

Sometimes a waiter must be cancelled — you `&`-detached one by mistake, a fresh waiter supersedes an orphaned one, a superseded run no longer needs its watch. **The kill is ALWAYS scoped to a unique identifier of YOUR OWN process — never a generic kill-by-pattern.** The recipes in this skill and in `ci-monitoring.md` deliberately mint byte-IDENTICAL waiter bodies on EVERY stream fleet-wide (`sleep 60`, `sleep 10`, `gh run view` polls), so any generic fragment of that recipe text matches a sibling stream's waiters too — a fleet-wide friendly-fire vector on a shared box. The incident this section exists for: montalu1 (odoo-erp, 2026-08-25) ran `pkill -f "sleep 60"` to kill its own detached CI waiter on the SHARED subdev box and matched montalu3's live waiters with the identical body — a killed foreign waiter leaves that stream waiting forever (a dead process sends no "done").

In order of preference:

1. **The PID you already hold** — `$!` at launch, or the harness's own task/shell id from the tool output: `kill "$PID"`. The launch handed you the exact handle; use it. (`kill -0 "$PID"` liveness probes are untouched by this rule — they signal nothing.)
2. **A unique discriminator IN the command body** — the run-id you baked into the waiter (`gh run view 17234567890`), a per-run marker token, your own log path: `pkill -u "$USER" -f "gh run view 17234567890"`. If the body you launched carries NO unique token, that is a launch-shape bug — embed one next time (the run-id already does this naturally); this time find the PID via `pgrep -u "$USER" -a -f "<narrowest fragment>"` and READ the listing to pick YOUR process before killing by PID.
3. **`-u "$USER"` is defense-in-depth, never sufficient alone** — it bounds the blast radius to your own uid, but shared-uid boxes (several streams under one user) exist, so the unique discriminator is the load-bearing part and `-u` the belt.

**BANNED (all rewordings):** `pkill -f "sleep 60"`, `pkill -f sleep`, `pkill sleep`, `killall sleep`, `pkill -f "gh run view"` (no run-id) — or ANY kill-by-pattern whose pattern would also match a sibling's recipe-minted waiter. The highest-confidence shapes are hook-enforced (`hooks/block-broad-pkill.sh`); the intent — kill only what you can PROVE is yours — applies to every rewording and semantic equivalent.

#### A subagent / subprocess that has gone SILENT is presumed DEAD — re-check it, don't trust it

The specific failure that keeps recurring: you dispatch a subagent (a worker / workflow / `Agent`) or launch a subprocess, end the turn `⏳ WORKING`, and then **never internally re-check why it has not reported back**. Hours pass. The thing died silently and you sat waiting because nothing told you it died.

- **A dispatched subagent's liveness signal is its DURABLE state, NOT a notification** (`subagent-continuation.md`): its transcript advancing, the branch/PR/files/gh it should be producing. If that state has not moved past the subagent's expected duration, presume the subagent is DEAD — re-dispatch a fresh one with the full context, do NOT keep waiting on the silent one. (`SendMessage` cannot tell you a silent subagent is alive — a dead one's message just goes nowhere with no error; you re-check its DURABLE output, not "ping" it.)
- **A foreground subagent BLOCKS you** — you cannot poll while it runs. So before a long dispatch, know its expected duration; a foreground worker that runs WAY past it is the case you CANNOT self-detect (you're blocked) — which is exactly why the watchdog backstop below exists. Prefer a bounded dispatch and durable-state resumption over an unbounded foreground block.
- **"It said it was working N hours ago" is NOT evidence it is working NOW.** The last progress line may have been its dying breath. Re-derive liveness from current state every cadence, never from the staleness of the last update.

#### Safety net — the watchdog now NUDGES you to self-check (the autonomous "stucked?")

The api-watchdog backstops this — and it no longer merely pings. A turn that ended `⏳ WORKING` and then sits idle ≥30 min with no advancing subagent gets an automatic **`stuck-check` self-check NUDGE** typed into the session (the autonomous equivalent of the user hand-typing "stucked?"): "verify the liveness of your launched work — ps / log mtime / subagent transcript / dashboard / gh run — and intervene if it died." This is safe where a blind `continue` was not: it does not auto-fix or decide liveness for you — it DELEGATES the healthy-vs-dead judgment back to YOU (you have eyes: the PID, the logs, the subagent's durable state). A landed nudge that you answer resets the idle clock, so the episode self-resolves in one nudge with NO Discord ping; only if the nudge produces NO response across 3 retries (your Claude process is itself wedged) does it escalate to ONE "needs you" ping. The user explicitly WANTS this even when it fires on a still-healthy wait — answering "checked, still alive, CI at 60%" is a welcome confirmation, far better than hoping nothing is wedged and losing a whole day; so an occasional nudge that resolves to "not stuck" is working as intended, never a false alarm to suppress. Consequences for your discipline: (1) the net keys STRICTLY on a `⏳` last-line marker — if you mislabel a still-running job `✅ DONE` (banned by `message-status-marker.md`), the watchdog will NOT nudge you; honest `⏳` is what arms it; (2) the nudge fires at 30 min and only triggers the self-check you should already run yourself on a tighter cadence. **Build your in-session liveness poll so the nudge never has to fire — but when it does, treat that `stuck-check` prompt as a hard order to re-derive liveness NOW and intervene, not as a cue to re-assert "still working" without checking.**

#### A LIMIT-death is NOT a reason to idle-park — PROBE first; your own working turn is proof of capacity (#520)

A 429 limit that kills YOUR OWN turn, or kills a subagent/worker you dispatched, shows Claude Code's banner `… limit · resets HH:MM`. **That printed reset time is a HINT, never an authoritative "do nothing until then" wall** — and treating it as one is the exact convergent failure this section exists to kill: on 2026-08-16 sessions across THREE unrelated projects each INDEPENDENTLY set a timer to the printed reset and idle-parked, one even staying parked AFTER the limit had already released (the worst form). No rule ever told them to wait — each invented the wait from the same wrong reading of the banner. Two facts make the idle-park always wrong:

- **Your own working turn is direct proof capacity exists RIGHT NOW.** If you are producing this turn at all, the account is not actually blocking you this instant — so a dead worker's 429 means "re-probe / re-dispatch NOW", never "wait until the printed clock". (The owner's own words when a session parked: *"ved ten limit uz neplati inak by si mi neodpisal?"* — if you could reply, the limit was already not holding.)
- **The window can free EARLIER than the printed reset** (a 5-hour session limit) or the moment the owner raises the cap (a monthly spend cap) — neither of which the printed clock predicts.

**So on ANY limit-death of your own turn or a dispatched worker: PROBE IMMEDIATELY** — resume the still-resumable agent (`SendMessage`, progress saved — `subagent-continuation.md`), re-dispatch fresh from durable state, or, when it is your own supervisor turn, simply continue. Do NOT set a timer for the printed reset and wait on it.

- **If the probe ITSELF returns 429** → bounded PERIODIC re-probes on a ~10–15 min cadence, backing off on a returned 429 — NEVER a single blind wait to the printed reset, and NEVER a tight `continue`-hammer (a `continue` fired repeatedly BEFORE the window frees just re-hits the limit — the watchdog job-6 frozen rationale; the bounded ~10–15 min re-probe is the safe middle ground, not that hammer).
- **Meanwhile keep doing ALL answer-independent, non-dispatch work** — the critical path, integration, reading, reviewing, planning. A limit blocks NEW model capacity; it does not block work you can do with what you already have.
- **BANNED: declaring "I won't work until the reset" / "robiť nebudem" / any timer-park on the printed clock** — and the worst form, staying parked AFTER the limit has released. The moment a real reset or cap-raise lands, resume / dispatch IMMEDIATELY.

**Two limit CLASSES, handled differently** (the SAME classes the watchdog already distinguishes in `watchdog/decide.py` — `is_usage_cap` / `pane_session_limited` vs `is_account_dispatch_block` / `_MONTHLY_SPEND_RX` — reconcile with those, never invent a parallel classification):

1. **Session limit** — `… session limit · resets HH:MM` (the 5-hour window). Probe-first / early-probe as above: the printed reset is a hint, your own turn is proof, the window may free early. Bounded periodic re-probes; never blind-wait to the clock. (This is the class the watchdog job-6 already auto-resumes AFTER the reset — the probe-first doctrine adds the "may free EARLIER, and idle-parking a session that BELIEVES a limit that no longer holds is banned" half that job-6's own frozen wait-for-reset behaviour deliberately does not cover.)
2. **Monthly spend cap** — `… monthly spend limit · raise it at claude.ai/settings/usage` (no reset clock; the OWNER must raise the cap — a user-only action). So: STOP dispatching (a fresh worker just dies at Step 0), fire ONE `❓` owner ping (the cap needs raising — user-only), then bounded PERIODIC probes (~10–15 min) to detect the raise, and the MOMENT a call works → IMMEDIATE full continuation. A permanent "won't work" after the cap is raised is the exact banned outcome from the incident (the camera-box case).

#### Anti-patterns (intent — all rewordings and semantic equivalents)

- Inferring "still running / still processing / still decoding" from the absence of a notification — **WRONG.** Run `ps`. Read the log's mtime. Prove it's alive.
- `until grep -q SUCCESS file` (or a success-only `Monitor` filter) with no death / timeout branch — **WRONG.** Waits forever on a silent death.
- `Monitor` with `persistent: true` for an "until it finishes" wait — **WRONG.** Bound it with `timeout_ms`.
- Launching a detached `run_in_background` waiter for a long (CI / rebuild) wait and blindly ASSUMING its notification will always arrive with NO recovery check — **WRONG.** Context compaction can orphan the notification linkage; the wait then hangs silently. The waiter itself is the RIGHT tool for a long wait (see `ci-monitoring.md` #107) — the missing piece is checking on your next turn whether it's still tracked and relaunching if not, not avoiding backgrounding altogether.
- Repeating a foreground bounded poll loop every ~9 minutes for a wait that will run HOURS — **WRONG.** Each repeat is a separate full-context turn (#107); launch ONE background waiter instead once the wait is genuinely long.
- Ending `⏳ WORKING` and then never re-checking the thing — **WRONG.** `⏳` is a promise to re-verify on a cadence.
- Trusting a subagent's "it's processing" / a launched job's last "progress" line as proof it's STILL alive minutes later — **WRONG.** Re-poll; the last line may be its dying breath.
- "Poll the running subagent for liveness" via `SendMessage` — **WRONG.** A dead subagent's `SendMessage` goes nowhere with no error, so it cannot tell you "alive" from "dead" (`subagent-continuation.md`); a foreground dispatch blocks until it returns, a background one re-invokes you on exit. For a subagent you can't observe live, the liveness signal is its DURABLE state (the branch/PR/files/gh it should be producing), not an in-process ping.
- Treating absence-of-error as proof-of-progress — **WRONG.** A hung process emits neither.
- Killing a stray waiter with a generic pattern (`pkill -f "sleep 60"`, `killall sleep`) — **WRONG (#701).** The recipes mint identical bodies on every stream; on a shared box that pattern kills a SIBLING's waiter and strands that stream forever. Kill by the PID you hold, or a run-id-scoped `pkill -u "$USER" -f "<run-id>"` — never a pattern a sibling's waiter also matches.
- Answering the watchdog's `stuck-check` nudge by re-asserting "⏳ still working" WITHOUT re-deriving liveness — **WRONG.** The nudge is an order to `ps` / read the log mtime / check the subagent's durable state RIGHT NOW and intervene if dead, not a cue to repeat your last claim.
- Waiting on a dispatched subagent/worker whose durable state (transcript / branch / PR / gh) has not moved past its expected duration — **WRONG.** Silent past-duration = presumed dead → re-dispatch fresh, don't keep waiting.
- Making the user type "stucked?" to discover a stall you should have caught — **WRONG.** That is the exact failure this rule kills; the watchdog now types it for them, but you reaching that state at all is the failure.
- Reading a 429 limit banner's `resets HH:MM` as a fact and setting a timer to idle-park a worker's limit-death until then — **WRONG (#520).** Your own working turn proves capacity exists NOW; probe / re-dispatch immediately, and if the probe itself 429s, bounded periodic re-probe (~10–15 min) — never a single blind wait to the printed clock.
- Declaring "I won't work until the reset" / "robiť nebudem", or staying idle-parked AFTER the limit already released — **WRONG (#520).** Keep doing all non-dispatch work meanwhile, and resume the instant a real reset / cap-raise lands.

The intent: every long thing you launch is polled for real liveness on a bounded cadence, and a silent death is caught in minutes — never hours, never by the user. Applies to all rewordings and semantic equivalents.
